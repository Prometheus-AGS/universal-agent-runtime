## Context

See `proposal.md` for motivation and `specs/dev-portal-2026/spec.md` for the
behavior contract. The publication inventory already assigns six product
screens to stable routes, while provider, inference, agent, skill, knowledge,
and memory guidance remains fragmented across one top-level skills page,
repository documents, API summaries, current OpenSpec capabilities, runtime
source, UI feature packages, and private-synthesis-only KBD evidence.

This change is documentation-only. It must preserve Round 3 ownership: it owns
the provider, agent, skill, knowledge, and memory guide roots plus a bounded
manifest and validator, but not the runtime, React application, shared global
navigation/theme, publication route inventory, READMEs, raw history, dependency
graph, or deployment workflow. Routine checks remain local, and the complete
site build and browser gate remain deferred until all phase content is complete.

## Goals / Non-Goals

**Goals:**

- Establish one seven-guide workflow sequence for provider configuration,
  models, genuine inference, agents, skills, knowledge, and memory.
- Give every guide explicit current authorities, classified provenance,
  packaged surface coverage, profile limits, and realtime-versus-durable-state
  boundaries.
- Preserve the exact safety distinctions already delivered for genuine model
  evidence, skill provenance/reconciliation, and knowledge versus memory.
- Make omissions and unsafe wording fail locally through bounded deterministic
  validation and isolated negative controls.
- Preserve the existing `/docs/skills` entry while moving current detailed
  authority to `/docs/skills/overview`.

**Non-Goals:**

- Changing provider compatibility, model routing, agent execution, skill
  behavior, retrieval, memory, runtime events, or React state.
- Re-certifying inference or transferring retained `server-full` observations
  to another provider, model, profile, checkout, or date.
- Publishing raw `.prometheus`, KBD, certification, session, event, credential,
  or machine-local material.
- Editing shared Docusaurus branding/navigation, the product route inventory,
  README files, API/SDK/deployment content, security/operations content, or
  architecture/testing history.
- Running the production build, browser, accessibility, deployment, or public
  Pages gate in this change.

## Decisions

### 1. Publish seven guides in one dependency-ordered sequence

Create these current-authority documents:

1. `website/docs/providers/configuration.md`
2. `website/docs/providers/models.md`
3. `website/docs/providers/inference.md`
4. `website/docs/agents/overview.md`
5. `website/docs/skills/overview.md`
6. `website/docs/knowledge/overview.md`
7. `website/docs/memory/overview.md`

The first six inventory-backed routes remain exactly as declared in
`docs/publication/routes.json`; `providers/inference` is a workflow guide rather
than a separate operator screen. Each category receives local metadata and each
page links forward or back so autogenerated Docusaurus navigation exposes the
sequence without changing shared global configuration.

This sequence follows actual dependencies: a reader configures an executable
provider and model before proving inference, then uses that inference through an
agent whose skills, knowledge, and memory have separate lifecycle rules.

**Alternative considered:** keep broad guidance in `configuration.md`,
`api-reference.md`, and the top-level `skills.md`. Rejected because route
coverage would still be satisfied by fragments that do not form a reproducible
product workflow or state their evidence limits consistently.

### 2. Add a product-workflow authority manifest without modifying the screen inventory

Add `docs/publication/product-workflows.json` with exactly the seven guide IDs,
files, routes, positions, applicable profiles, classified source records,
current source authorities, required concept markers, and whether a diagram
requires a prose equivalent. The existing `routes.json` remains the authority
for operator-screen coverage; the new manifest is the authority for content
depth, order, and truth dependencies.

Representative current authorities include:

- providers/models/inference: `src/uar/api/providers.rs`, `src/server.rs`,
  `src/uar/runtime/manager.rs`, the provider/model/chat frontend feature paths,
  `docs/PROVIDER_CONFIGURATION.md`, and current provider/model capabilities;
- agents: `src/uar/api/discovery.rs`, `src/uar/domain/agent_store.rs`,
  `src/uar/runtime/manager.rs`, and the agents/chat frontend feature paths;
- skills: `src/uar/api/skills.rs`, `src/uar/runtime/skills/`, `src/skills_api.rs`,
  the skills frontend feature, and the built-in, governance, reconciliation,
  hot-reload, and distribution capabilities;
- knowledge: `src/uar/api/knowledge.rs`, `src/uar/domain/knowledge.rs`,
  `src/uar/api/sse.rs`, the knowledge/chat frontend feature paths, and current
  RAG provenance and product-certification capabilities;
- memory: `src/uar/memory/`, `src/uar/api/memory_admin.rs`,
  `src/uar/api/sse.rs`, the memory/chat frontend feature paths,
  `docs/MEMORY_SYSTEM.md`, and `docs/CONVERSATION_MEMORY.md`.

The implementation must resolve every path from the checkout rather than copy
this representative list blindly. `versions.toml` is absent and cannot be named
as inspected authority.

**Alternative considered:** extend `routes.json` with content markers and source
authorities. Rejected because that file is the frozen cross-lane screen coverage
contract and mixing content-level assertions into it would create shared-file
ownership and conflate a screen with a workflow.

### 3. Use current source for behavior and retained evidence only for bounded observations

Present-tense behavior comes from current implementation and canonical OpenSpec.
The retained functional record at
`.kbd-orchestrator/phases/perform-the-soak-run-candidate-tag-external-installs-and-ga-promotion/functional-verification.md`
may inform a reviewed, bounded example of genuine `server-full` inference, skill
activation, knowledge grounding, Kimi configuration, and agent execution. It is
classified `private-synthesis-only`: public prose may summarize the provider,
model, packaged boundary, observed output, source SHA, and explicit limit, but
must not copy raw logs, credentials, local paths, commands containing secrets,
or internal event/session payloads.

A guide must distinguish:

- catalog metadata from configured provider execution;
- saved configuration from a healthy or usable provider;
- model-route resolution from a completed model response;
- an illustrative response from retained genuine-inference evidence;
- the one observed provider/model/profile path from every unobserved path.

**Alternative considered:** rerun live inference during this documentation
change. Rejected because runtime certification is not being changed, retained
evidence already supports bounded historical observations, and the phase rules
reserve this change for completed content plus local source validation. If a new
present-tense inference claim lacks retained evidence, omit or qualify it rather
than silently launching a new certification effort.

### 4. Use a repeated guide contract with profile and state matrices

Every guide carries frontmatter `source_records` and `current_authority`, then
uses the relevant subset of these sections:

- boundary statement;
- prerequisites;
- packaged UI workflow;
- API workflow;
- embedded-host workflow where delivered;
- observable success and failure;
- realtime state versus reloadable authority;
- profile limits;
- evidence limits and related guides.

Providers and agents receive Mermaid workflow diagrams with a `Diagram in
words` section. Skills use a provenance/scope matrix. Knowledge and memory use a
side-by-side boundary matrix. This repetition is intentional: readers should not
have to infer whether a server-only action, live event, or retained observation
applies to embedded-mobile.

**Alternative considered:** one long product-workflows page. Rejected because it
would weaken stable route coverage, search granularity, source ownership, and
profile-specific maintenance.

### 5. Encode skill safety as provenance and scope, not generic CRUD

The skill guide treats origin and scope as separate axes:

- origin: built-in, configuration-provisioned, or API-created;
- effective state: conversation, explicit durable agent, then global;
- timing: next-request live effect versus unchanged in-flight execution;
- durability: restart persistence and built-in re-registration;
- reconciliation: configuration removal tombstones and can be restored;
- destructive boundary: reconciliation never hard-deletes and never tombstones
  built-in or API-created skills.

The existing `website/docs/skills.md` becomes a concise compatibility landing
page that points to `/docs/skills/overview` and the separate installation and
authoring authorities. It must not remain a second divergent lifecycle source.

**Alternative considered:** preserve the current page as a second full guide.
Rejected because two current authorities would drift and the route manifest
already names `skills/overview`.

### 6. Separate durable knowledge, selected context, and opt-in memory

The knowledge guide follows resource creation, document ingestion/processing,
retrieval, attachment to execution, citation/context visibility, and bounded
genuine-model use. The memory guide separately covers opt-in initialization,
capture, recall/context injection, mutation, admin/API surfaces, and the memory
MCP endpoint. Both link to architecture state boundaries and state explicitly
that model context and event history are not the durable resource authority.

The guides must not imply that every runtime profile shares the same database,
HTTP routes, embedding provider, memory configuration, or host persistence.

**Alternative considered:** combine knowledge and memory under a generic RAG
page. Rejected because their configuration, lifecycle, persistence, API, and
operator semantics differ materially, and the product inventory exposes them as
separate surfaces.

### 7. Compose a fail-closed local validator only after content is complete

Add `scripts/validate-documentation-product-workflows.mjs` and
`scripts/test-documentation-product-workflows.mjs`, expose bounded root package
commands, and compose the validator into
`scripts/validate-documentation-publication.mjs`. The validator checks the
manifest, exact guide set and order, file/route existence, source classification,
authority existence, frontmatter, required headings/markers, profile vocabulary,
local links, diagram prose, compatibility landing page, and forbidden public
material.

Isolated controls must observe failures for at least:

- a missing guide;
- an absent or unclassified authority;
- missing packaged UI/API coverage;
- missing profile or realtime/durability limit;
- synthetic material represented as genuine inference evidence;
- missing skill origin/scope or tombstone safety;
- knowledge and memory conflation;
- missing diagram explanation;
- an unsafe private-history excerpt.

The controls are authored before the guides but executed only after all seven
guides and the compatibility page are complete. This preserves the phase rule
that code/content completion precedes verification.

**Alternative considered:** rely on Docusaurus broken-link checking alone.
Rejected because it cannot prove provenance, semantic safety boundaries, or
that a plausible but unsafe statement is absent.

## Risks / Trade-offs

- **[Risk] Current source and canonical specs disagree with older narrative
  docs.** → Treat current implementation and canonical specs as behavior
  authority, qualify unresolved conflicts, and leave historical reconciliation
  to its owned later change.
- **[Risk] Private functional evidence leaks machine or credential material.** →
  Use it only as reviewed synthesis input, run the publication sanitizer and a
  dedicated unsafe-excerpt control, and never place raw evidence in public
  assets.
- **[Risk] Catalog breadth is mistaken for execution compatibility.** → Require
  the catalog/configured/healthy/routed/inferred distinctions in the manifest
  markers and negative controls.
- **[Risk] A compatibility page creates another stale authority.** → Keep
  `website/docs/skills.md` deliberately short and link all lifecycle detail to
  `skills/overview`.
- **[Risk] The seven guides compile individually but break the complete portal.**
  → Run bounded TypeScript/source checks here and defer the one production
  build/browser/accessibility gate until every content lane is complete.
- **[Trade-off] A strict marker validator cannot prove prose is permanently
  correct.** → Pair deterministic controls with a source-authority audit and
  state the temporal limit in verification evidence.

## Migration Plan

1. Add and parse the product-workflow manifest; verify every named source path
   and classified record exists without executing the controls.
2. Add the validator/control composition and root local commands, leaving the
   control suite unexecuted until content completion.
3. Write provider configuration, models, and inference in dependency order.
4. Write agents, skills plus the compatibility landing, knowledge, and memory.
5. Add category metadata and cross-links without editing shared global
   navigation or the route inventory.
6. Audit every present-tense statement and every retained observation against
   current authority and publication-safety limits.
7. Run isolated negative controls, bounded TypeScript/source checks, strict
   OpenSpec validation, artifact-refiner content review, and the permitted-scope
   audit; write row-form evidence.
8. Transition the canonical KBD change, refresh the human handoff, and commit
   this change independently without pushing the partial phase.

Rollback is a revert of this documentation commit. No runtime data, public API,
dependency, storage migration, or deployed artifact changes in this unit.
