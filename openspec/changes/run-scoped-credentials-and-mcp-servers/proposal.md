## Why

the-boss will run UAR as a fourth agent runtime and keep ownership of provider credentials and tools (decision D1, revision 3). UAR has no way to receive either for one run. A run's provider key comes from UAR's own registry and credential store (`src/uar/runtime/manager.rs:3232-3347`, `src/uar/security/credentials/resolver.rs:55-98`), and no route writes session- or agent-scoped credentials. MCP servers come from the process-wide registry (`src/uar/api/mcp_admin.rs`, persisted), and `CreateRunRequest` has no field for either (`src/uar/api/routes.rs:38-47`). Writing the-boss's keys and servers into UAR's global stores would leak them across sessions and leave them on disk after the run.

## What Changes

- `POST /api/uar/runs` accepts `run_credentials`: a list of `{ provider_id, provider_kind, base_url, api_key, default_model? }` (operator decision 2026-09-23). A run credential is a whole run-local provider — kind, endpoint and key — not a key for a provider UAR already knows. That is what lets the-boss's custom-endpoint providers (local model servers, gateways) work. The key and the base URL are held as secret types. Neither is ever serialized, persisted, checkpointed, logged or traced. The credential is applied after provider routing and after `apply_credential_layer`, so it wins over every stored or configured key and endpoint for that provider id.
- `base_url` is validated before the run starts: `https`, or `http` only when the host is loopback; no userinfo. `provider_kind` must be one UAR can drive with an explicit endpoint: `openai_compatible` or `anthropic`. Any other kind is rejected with `run_credential_provider_kind_unsupported` and no run starts.
- A run that carries run credentials may only call providers it has a credential for. Model routing, failover and child runs never switch to a provider without a run credential, and never fall back to UAR's registry, credential store or environment key or endpoint for it. Failures under a run credential do not put the shared provider into cooldown.
- Child runs reuse the parent's captured model clients in memory. Remote A2A peers never receive a run credential.
- `POST /api/uar/runs` accepts `mcp_servers`: a list of `{ name, url, headers }` Streamable HTTP servers. They are connected for that run only, never written to the global registry, settings or disk, torn down when the root run ends, and are the only MCP servers the run and its children may list or call. The global registry and skill-declared servers are outside such a run's tool universe. A policy that selects a server the run did not supply fails the run before it starts.
- Run-scoped server URLs must match a host allowlist that defaults to loopback. Redirects and proxies are not followed.
- **BREAKING (host protocol, host-owned runs only).** Resume and continuation fail closed. `POST /runs/{id}/resume`, `POST /runs/{id}/resume/{checkpoint_id}` and `POST /runs/{id}/a2ui/actions` must re-attach the same run credentials and MCP servers when the source run had them; without them the request is rejected and no run starts. A2UI continuation of a run whose artifact was posted inline must also carry that artifact, because UAR never persists runs-API artifacts. Runs that never carried host resources behave exactly as today.

## Capabilities

### New Capabilities
- `run-scoped-credentials`: per-run provider credentials supplied by the host: precedence, provider containment across routing, failover and children, fail-closed resume and continuation, and confinement (no serialization, persistence, logs, traces, checkpoints or error text).

### Modified Capabilities
- `mcp-runtime-projection`: adds run-scoped host MCP server definitions as a third, run-local source. When present they are the run's entire MCP universe, are never cached or persisted beyond the run, and end with it.

## Impact

- **Code:** `src/uar/api/routes.rs` (`CreateRunRequest`, `ResumeRequest`, both resume handlers), `src/uar/a2ui/routes.rs` (`A2uiActionPayload`, `submit_action`), `src/uar/runtime/turn/request.rs` (`RunExecutionRequest` fields), `src/uar/runtime/manager.rs` (credential application after `apply_credential_layer`, routing and failover constraints, run-scoped MCP registry lifecycle, `continue_with_interaction`), `src/uar/runtime/turn/bindings.rs` (fallback capture), `src/llm/orchestrator.rs` (`build_driver` selects the driver from the run credential's kind), `src/config.rs` (`LlmConfig` marker that redacts a host-supplied `base_url` in `Debug`), `src/llm/health.rs` (failures under run credentials), `src/mcp/` (a run-local, non-serializable server definition and connector using rmcp's `auth_header`/`custom_headers`), `src/config.rs` (run-scoped MCP host allowlist).
- **APIs:** additive request fields on four routes; new 422 error codes `run_credential_required`, `run_credential_invalid`, `run_credential_provider_kind_unsupported`, `run_mcp_servers_required`, `run_mcp_server_invalid`, `mcp_server_not_run_scoped`; new run error code `run_credential_provider_unavailable`. Existing callers that send none of the new fields see no change.
- **Provider compatibility:** a run credential reaches any endpoint that speaks the OpenAI-compatible chat API or the Anthropic Messages API at the given base URL, whether or not UAR's registry knows the provider. Other wire protocols (Google, Bedrock, Vertex, Azure deployments, Cohere) are refused by kind, not guessed. When `provider_id` equals a registry id, the run credential replaces that registry entry for the run; registry key, endpoint and model list are not merged in. Local-only mode still applies: `build_driver` refuses a non-loopback base URL when it is on (`src/llm/local_only.rs:117-136`).
- **Realtime state:** run records gain a `host_resources` marker naming provider ids and server names (never keys or base URLs), used to fail resume closed. MCP lifecycle events for run-scoped servers carry the server name only.
- **Runtime UX:** none for the UAR SPA. the-boss must send credentials and servers on every create, resume and continuation request.
- **Dependencies:** none. `secrecy` 0.10 (`Cargo.toml:505`) and rmcp 3.1.2 (`Cargo.toml:296`, which exposes `auth_header` and `custom_headers` on `StreamableHttpClientTransportConfig`) are already direct dependencies.
- **Depends on:** `sidecar-session-principal` for per-session owners (MCP binding cache and credential store are owner-keyed); `sidecar-launch-security` for the authenticated host channel that carries the secrets.
- **KBD workflow state:** yes. This change belongs to the-boss child phase `the-boss-universal-agent-runtime` (step 2); that phase's `progress.json` in `prometheus-skills-mini` must list it. This repository's `.kbd-orchestrator/` is not updated by this authoring pass.
