## Useful deliverable and explicit limits

Carry an admitted current user message containing inline base64 PNG/JPEG parts through the two existing ordinary OpenAI chat aliases (`/v1/chat/completions`, `/api/chat/completion`) into the pinned Liter generic OpenAI-compatible chat adapter. Preserve text/image order, multiple images, image-only input, streaming/nonstreaming replies, warm continuation, and governed cold checkpoint restoration. Enforce hard capabilities and existing agent/owner destination authority on actual primary/retry/fallback sends. Text-only callers keep their current constructors and payload meaning.

Exclude remote image retrieval, upload-ID resolution, native Anthropic image conversion, AG-UI/A2A/native-run image convenience inputs, multimodal caller-owned tool history, audio/video, new provider policy DSL, and learned routing. These exclusions must be explicit in admission/support documentation; they cannot be disguised as successful text-only processing. This is a coherent partial delivery of #463/#464, not closure of either issue's full surface matrix or #388.

The uncomfortable limit: a deterministic endpoint can prove correct bytes and routing while a real model still cannot understand the image. The current exact final-budget contract also cannot establish real image-token capacity. Neither result may be promoted from fixture evidence.

## Implementation order and decisions the team can make now

1. **Freeze ordinary current-turn representation.** Use the last user message, consistent with the existing ordinary handler. A nonblank `message` convenience string keeps existing precedence; reject a request that would thereby discard supplied image parts instead of silently choosing text. Parse allowed part types explicitly; preserve their order and detail (`auto`, `low`, `high`). Reject malformed/unknown parts, remote/relative URLs, unsupported MIME, invalid base64, declared-type/signature mismatch, and image attachments before provider dispatch. Image-only content is nonempty input; its derived text may be empty. Do not parse arbitrary string content as JSON parts. Do not accept caller-supplied model-capability claims.
2. **Use existing resource bounds first.** The current 10 MiB JSON body cap already bounds per-turn encoded payload, total inline bytes and finite part count. Decode only after checking encoded length against that envelope; validate PNG/JPEG signature using the existing `base64` dependency (`Cargo.toml` selects `0.23`). Do not borrow upload's 50 MiB/file, 100 MiB/10-file limits: those are a different storage contract. This slice does not decode pixels, so it need not invent a pixel limit or add an image codec merely to establish provider pass-through. State that pixel/decompression limits and semantic image validity are not qualified. A future requirement to decode/transform images would require explicit dimension/resource limits. Retained request size is constrained again at final preparation, not inferred from the latest turn's body cap.
3. **Keep canonical content and derived prose distinct.** Add the host-only current-content input, initialize every `RunExecutionRequest` construction/destructure, and use typed content at all three manager append seams. Preserve `input` as aggregated text for existing matching/guardrails; join every text part in order rather than using `as_text()`. Never place base64 in memory-matching input or public run-context `input`. Existing typed history/checkpoint serialization is reused; do not create a parallel image store or schema migration. Inspect actual checkpoint projection so image URLs are not credential-redacted into broken canonical bytes. Store images only where canonical conversation history already belongs; safe diagnostics contain hashes/byte counts/order and destination disposition, not raw data URI.
4. **One evaluator, separate requirements from authority.** Extend the existing router with one reusable candidate-admission result/reason API (new API, name to be chosen by its owner), shared by route query and dispatch. Resolve runtime registration metadata first; explicitly disabled runtime provider/model vetoes catalog supplementation. Unknown capability is not positive evidence for a required capability. Apply cooldown and existing scoped exclusions before ranking. Keep advisory preferences separate from the hard boolean requirements and authority restriction. Do not introduce a second routing service.
5. **Derive requirements from actual send.** Vision is required when any retained/current canonical provider message has an image. Tools are required when the final request carries nonempty tool declarations or a required/named tool contract; mere existence of a global tool registry is irrelevant. Structured output follows `ResponseFormat::is_structured()`. Explicit requested reasoning controls require the destination support already represented by the current config; do not equate optional reasoning output with a user requirement. Preserve existing context/cost requirement semantics; final destination capacity is still decided by preparation, not a catalog context-window comparison alone. Recompute request-derived requirements after tools/history grow; capture authority immutably per run.
6. **Intersect, never enlarge, the existing destination scope.** Exact target selections/team bindings are validated or refused, never substituted. Bound agent allowed identities/credentials and artifact fallbacks remain hard boundaries. Configured failovers for an ordinary unbound run remain subject to their existing scope plus capability admission; a default/preferred model is not a new implicit deny-all policy. If an agent supplies an explicit fallback list, no rescue through an unrelated global fallback may escape that list. Retain owner/tenant, verified-model proof, selected billing identity, and continuation bindings. Existing exclusion/resource constraints are subtractive; do not add public provider/model allow/deny fields in this slice. No-match and config-resolution race become explicit zero-dispatch refusal for hard requirements, never `preferred_llm_config` rescue. The no-registry branch must also validate metadata or refuse required capabilities; it cannot bypass admission.
7. **Enforce at every actual send.** Manager chooses an admitted primary and admitted fallback candidates; final orchestrator/graph boundary guards validate the prepared destination and actual payload again. A retry of the same destination retains the same requirements and authority; failover revalidates capability/health/scope and calls the destination preparation anew. Do not route after model/credentials/budget profiles were captured. A refusal is not a provider outage and must not trigger an unconstrained fallback. Preserve existing response-format adapter refusals.
8. **Preserve #388 without inventing vision billing.** Keep `DestinationRequestPreparations`, exact settings, output/reasoning reserves, protected continuity, final-wire body validation and per-fallback compilation. For a real destination with no proven image counting rule, retain an explicitly estimated/no-fit-guarantee lane; never relabel the base64 JSON token count as provider-exact. If the caller/run requires strict guaranteed-fit or finite accounting that depends on a proven full input count, refuse images before dispatch unless its destination has a validated image-aware counting contract. A synthetic fixture may keep its explicitly synthetic JSON counting contract and prove overflow/zero-dispatch. Do not claim a real image fit guarantee from that fixture. A new real counting contract is a separate evidence-backed amendment, not a flat token allowance.
9. **Publish only exercised support.** Update support matrix/release prose and add narrow OpenSpec deltas for typed OpenAI image input and hard dispatch admission. Separate implemented, deterministic-wire-exercised and real-vision-qualified rows. Document unsupported forms/paths and the budget limitation. Existing `/v1/messages` base64 conversion means it must not be described as universally text-only; its native/bound/direct branches remain independently unqualified for this slice.
