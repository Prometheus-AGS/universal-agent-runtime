The direction is appropriate: an actual edited model reaches the admitted native continuation through a typed domain action, and the existing stream processor owns the response. Four details need a concrete contract before implementation can safely claim this outcome.

## Findings

1. **P1 — The operation key does not yet distinguish generated surface instances.** The receipt is keyed by source run + surface, but the UI promises that a new generated surface is a new operation. A source can update or recreate the same surface ID; a component remount is also not evidence of a new operation. Define an authoritative generation identity and include it in the operation/receipt identity, or explicitly restrict this change to one action for that source/surface. Keep identity stable across content refresh/remount so neither unknown outcomes nor completed actions become accidentally resubmittable. Fixture: same ID updated, same ID deleted/recreated, remount after unknown result, two different generations, and action from an obsolete surface.

2. **P1 — Global stream ownership needs an atomic reservation shared with ordinary chat.** “Serializes one pending submission globally” and “does not cancel an unrelated live stream” describe intent but not the critical ordering. Reserve ownership synchronously before source inspection/POST; ordinary chat starts must consult the same reservation, including during asynchronous admission. Release only on a defined safe transition, retain accepted identity after attach failure, and do not turn failed acquisition into an uncertain POST. If another chat owns the stream, show a truthful local busy explanation without posting. Fixture: action versus ordinary send in both orders, two surfaces clicking simultaneously, known refusal releasing reservation, unmount while admission is pending, accepted run whose attachment fails. An uncertain admission needs a separately defined reservation lifetime; permanently blocking all chat and releasing into a competing stream are both meaningful product outcomes.

3. **P1 — Retry eligibility must come from a definite refusal contract.** The proposed distinction between rejected and unknown is correct, but “known refused” must identify which transport outcomes prove non-admission. A malformed 202 receipt, response-body parse failure, disconnect, timeout or unexpected server error cannot silently become “Try again.” Persist the in-flight marker before I/O where feasible, record the actual receipt before attachment, and retain the operation's uncertain/accepted state across rerender/remount. The acknowledged process-crash window remains real; do not claim local graph persistence solves host exactly-once admission. Fixture each definite refusal, ambiguous response and successful receipt followed by attach/persistence failure; all ambiguous/accepted outcomes must issue no second POST.

4. **P2 — Disabled controls alone do not close the event/input contract.** Native fieldset disabling may not suppress custom catalog handlers or non-form action emitters. Keep the synchronous domain guard authoritative and bind callback handling to the current surface/generation and selected native source identity. Snapshot and detach the current model at the click boundary so later edits cannot change the in-flight payload. Ignore stale callbacks after content replacement and clean up the exact subscribed processor. Source normalization must occur only after project-profile/component validation; retain original source and diagnostics when conversion/parsing fails. Fixtures: callback twice in one tick, late old-processor callback, two surfaces with distinct model values, edited nested field versus initial value, absent source binding, invalid component/profile and parse failure.

5. **P2 — State feedback must stay accessible after controls are disabled.** Put polite status and role=alert feedback outside the disabled fieldset; use a named surface group and preserve focus instead of moving it. Distinguish pre-admission rejection, unknown admission and accepted-response failure in the visible text. For accepted stream failure, say the response could not be confirmed/completed and retain its actual continuation identity in inspectable metadata; do not suggest resubmission. One stable live region should announce transitions, not every streaming token or replay. Later browser/assistive-technology evidence must establish keyboard activation, actual disabled custom controls, wrapping/zoom, focus retention and one intelligible announcement.

## Strengths and acceptance limits

Pure UI rendering plus typed `@/platform/entities` access respects the graph/domain/transport boundary. Keeping raw action payload and private input values out of the receipt is appropriate; public error categories must likewise avoid leaking arbitrary upstream errors. Attaching the admitted run without a second POST or invented user message is essential to preserving conversation truth. Terminal success, cancellation, error, EOF and persistence failure are explicitly separated, which prevents a 202 from masquerading as completion.

The uncomfortable limitation is larger than visual polish: an accepted action may continue on the host while the client has no usable receipt or stream. This design can prevent blind resubmission, but cannot prove server-side exactly-once behavior. A concrete uncertain-state ownership/recovery contract is therefore required even when no recovery endpoint is added.
