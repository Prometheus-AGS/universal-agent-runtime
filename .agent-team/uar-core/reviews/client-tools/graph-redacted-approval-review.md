## [HIGH] HTTP error body bypasses graph absolute EOF deadline

File: `scripts/release/client_tools_acceptance.py:43–71` (`http`), called through `graph_owned_request` at `:335–342`, and executor join in `graph_send`.

Exact source: successful urlopen response checks `time.monotonic() < request_deadline` between `response.read1(65536)` calls. But `except urllib.error.HTTPError as error:` immediately executes `raw = error.read().decode()` with no absolute-deadline check or chunk loop. The socket timeout bounds an individual stalled I/O wait, not the total duration of successive bytes. This error path therefore does not satisfy the newly stated absolute EOF bound.

Unexecuted reproducing scenario: an owned native graph request receives an HTTP error whose body keeps trickling bytes within each 10-second I/O wait. Its error.read can stay active after the 90-second graph deadline. The coordinator may cancel its identified root, but future.result timeout does not stop the thread, and ThreadPoolExecutor exit physically waits for that same outstanding worker. Thus bounded failure cleanup can still be defeated. No claim is made that the current server has emitted such an error body; the defect is the explicit unbounded error branch in the helper's required deadline mechanism.

Fix: consume and close HTTPError response bodies through the same absolute-deadline chunk/read1 mechanism as successful responses, retaining status/content type and existing failure reporting. Preserve physical executor joining; do not hide the gap with detached or daemon workers. Apply the bounded reading to both JSON and SSE bodies whenever the graph deadline is active, without broad unrelated changes to ordinary requests.
