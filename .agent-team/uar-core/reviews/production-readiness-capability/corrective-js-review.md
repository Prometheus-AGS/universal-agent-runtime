## Remaining finding

### P2 — Cleanup deadline exhaustion suppresses the reconciliation receipt

Location: `scripts/behaviors/steps/capability-dispatch.steps.mjs:313`–`:325`.

The hook records original IDs, confirmed DELETE responses, and unresolved IDs in memory, then requires the same cleanup lifetime to remain live before creating/writing the receipt. If a slow DELETE consumes the shared 100-second cleanup budget, its rejection is caught, subsequent cleanup calls reject immediately, and those unresolved fields are assembled. `requireLive(cleanup)` at line 321 then throws before `writeFileSync` at line 324. The catch only poisons the process and rethrows. Nothing persists that case's exact agent/session IDs for the external reconciliation required after uncertain remote effects. A successful deletion response followed by another stalled operation has the same evidence loss. The README explicitly promises retained reconciliation identities, so failing the hook and blocking later cases alone does not satisfy this contract.

Minimal correction: persist a safe ownership/reconciliation record before cleanup can exhaust its deadline, then preserve that record if final cleanup reporting cannot finish; or provide an equivalently owned durable failure-receipt path that remains available after cleanup expiry. Keep exclusive ownership, safe fields, bounded client lifetimes, and the poison latch. Do not clear uncertainty on a 404 following an uncertain create.

Later authorized falsifier: let an owned cleanup DELETE consume the real cleanup deadline after an agent ID has been tracked. The hook must fail, later cases must refuse, and a durable receipt must still identify the original owned agent/session and uncertainty. This counterexample was reasoned from source and was not executed.
