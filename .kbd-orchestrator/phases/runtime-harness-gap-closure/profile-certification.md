# Local runtime harness profile certification milestone

Milestone phase ID: `runtime-harness-profile-certification`. Parent delivery: `runtime-harness-gap-closure`. This is a separate local verification milestone; no deployment, publishing or release is included. It will be registered after Plan review, before the Execute handoff. Completion of this milestone is a mandatory dependency of parent phase completion, recorded through the typed KBD decision ledger. It is not a dependency of the first implementation task.

Entry: all six changes' implementation units and the parent Tier 2 readiness checks pass on the candidate revision. Parent task harness-governed-evaluation/3.1 owns the transition into this milestone; /3.2 consumes its receipt. Implementations stay pending while Plan runs. The milestone gets its own reviewed execution plan and exact environment/command manifest before any Tier 3 run. Do not mark the parent complete to make the milestone eligible: unit readiness and the phase completion checkpoint are sufficient.

## Required coverage matrix

Linux and macOS are stable and blocking. Windows is experimental and non-blocking; a skipped Windows row is labeled experimental, never passed. Every applicable profile/OS row includes preserved history, budget arithmetic/overflow, exact template preparation, activation, evidence, governance, limits/cancellation and host evaluation. Include protocol/graph surfaces where compiled. Missing live environments are BLOCKED, never substituted by a mock pass.

Cargo command families name existing feature flags. The exact applicable target list and platform prerequisites must be checked against the candidate tree in this milestone's plan; compile errors, unsupported platform toolchains or missing infrastructure block the corresponding required row. They are not invitations to weaken a gate or upgrade pins. One target directory per profile, one writer each; keep CARGO_HOME shared and never cargo clean. No release build is required merely to exercise these debug-profile behavior contracts.

For mobile, Linux/macOS host tests prove transport-free library semantics only. Android/iOS host/device claims additionally need their configured SDKs, host callback bridge and retained integration traces; mark absent environments BLOCKED for those supported claims. Do not label desktop-host execution as device certification. Read the repository's current product support matrix when scoping the exact targets; required supported targets cannot be silently omitted.

## Integration and live requirements

Use the existing local `pnpm test:e2e:real-provider-route`, `pnpm test:e2e:real-knowledge-rag` and `pnpm test:bdd` entry points only within this milestone after inspecting their candidate scripts and required environments. The BDD feature contracts include tests/bdd/features/chat-kb-retrieval.feature and chat-skill-activation.feature. A script named real-provider may still use a stub: retain fixture identity, and never count stub coverage as the separately required live row. Running with CI=1 locally does not mean GitHub Actions.

Live provider rows require credentials supplied through existing configuration, reachable exact endpoint, alias/upstream and profile revisions, supported settings/roles, a proven count bound, output/reasoning semantics, declared price revision and actual usage. The six observed defaults and unknowns are in provider-profile-matrix.json. Expand the inventory from effective persisted settings before claiming completeness. Record secrets nowhere. Run deterministic synthetic profiles first and separately retain actual deployment captures with payloads redacted and canonical private evidence access-controlled.

Persistence evidence needs Memory semantics and durable Surreal/Postgres fixtures; only the latter can establish restart recovery. Desktop evidence requires native build prerequisites and a local graphical session. Browser journeys require the existing local runtime/stub fixtures plus frontend/browser dependencies. Knowledge evidence needs ingestion/index fixtures, embedding provider identity and source/access versions. Record platform, toolchain, dependency-lock and configuration digests for every row.

## Exit receipt

The receipt lists each required profile/OS/surface row, exact command and exit, test count, source/config/fixture hashes, logs, traces, actual versus predicted usage and its supported or blocked state. Attach acceptance-contract.json metric outputs, unchanged coverage denominator, seeded-fault nonzero outcomes and F1–F8 evidence links. It must prove no denied/replayed tool effects, no lost protected payload, no invalid final request and no hidden required skip. Do not update baselines to obtain a pass.

The uncomfortable constraint: this machine may not supply every stable-platform or device environment. That prevents phase completion; it does not justify running product tests in GitHub Actions or relabeling a missing row as inapplicable. A verified inapplicable surface needs a feature/support-contract citation.

### Durable backend ownership and completion receipts

Change harness-task-graph-lifecycle task 2.2 owns both provider crash fixtures; its task 3.1 retains ordinary local unit evidence. The separate milestone runs both durable backend supplements at Tier 3 on each stable OS. Surreal uses server-full (which includes surreal-backend); Postgres uses server-full,postgres-backend. Each fixture starts with an isolated namespace/database and retained durable storage, injects all six acceptance-contract.json crash boundaries, kills/restarts the host against the same storage, and verifies identity, intent recovery, receipts and publication. Never truncate production storage. Exact disposable connection configuration is recorded without credentials when the fixture is materialized.

Keep backend receipts at evidence/certification/<os>/surreal/crash-receipt.json and evidence/certification/<os>/postgres/crash-receipt.json relative to the parent phase. Both receipts are required; a generic profile pass is not a replacement. The milestone publishes evidence/profile-certification-receipt.json with status=PASS, candidateRevision, acceptanceContractSha256, requiredRows and rows. Each required row ID must have status=PASS, command, exitCode=0, testCount greater than zero and evidence paths. Required rows include both backend crash supplements on Linux/macOS plus every applicable stable profile/live/device row frozen in the milestone plan. Unknown/blocked/skipped required rows prevent parent task 3.1 from passing. Its check also reads canonical KBD child-phase status; a receipt alone cannot claim a pending milestone completed.

The milestone plan freezes its complete applicable environment inventory in evidence/certification-required-rows.json before execution. Its requiredRows array includes the four stable-OS backend IDs linux/surreal/crash, macos/surreal/crash, linux/postgres/crash and macos/postgres/crash, plus all other required rows above. The final receipt carries requirementsSha256 and must match this inventory exactly; self-selecting only passing rows cannot pass the parent gate. Candidate source/config/fixture digests in row evidence must describe the actual tested tree, including uncommitted source changes if any; matching HEAD alone is insufficient.
