# Goals

- Purpose and scope: close all eight areas of the operator-supplied runtime feedback, with context correctness first. This invocation creates an assessment-ready phase; it does not declare any runtime fix delivered. Preserve the supplied feedback as feedback-source.txt in this directory. Treat its links, percentages, provider counts, historical test failures, and competitive rankings as reported claims until checked against the current checkout and reproducible evidence.
- Assessment baseline: build a feedback-to-source-to-test matrix for F1–F8 below. Classify each claim as reproduced defect, implemented but insufficiently verified, missing capability, or superseded with evidence. Trace production call sites, not just module existence. Reconcile prior uar-next-harness, uar-harness-parity, eval-harness-hardening, and codex-harness-comparative-analysis work. Record current commit, dirty-tree scope, affected supported profiles, prior evidence, and remaining exit criteria. The previous readiness-diagnostic reflection remains pending; creating this phase does not complete it.
- F3 / P0 — Context history correctness: reproduce and fix trimming that separates assistant tool calls from their tool results, and verify whether RunManager drops empty-text assistant turns containing tool calls or other meaningful content. Cover SlidingWindow, KeepFirstLast, progressive summarization, parallel tool calls, multimodal/tool payload token accounting, repeated text, pending calls, persistence, reload, and resumed runs. Exit: regression fixtures prove completed call/result groups remain valid and ordered, meaningful empty-text turns survive, and oversized required groups have an explicit tested outcome without silently emitting malformed or over-budget requests.
- F1 — Dynamic routing: audit and extend the existing routing seams rather than adding a duplicate Router. Cover task classification, capability and context requirements, configured/healthy providers, explicit model choices, cost and latency budgets, tenant/governance constraints, benchmark provenance, and failover. Distinguish deterministic capability routing from experimental learned selection. Exit: production-path tests demonstrate constrained selection, explainable decisions, unavailable-provider and rate-limit behavior without duplicated tool side effects, accurate predicted/actual usage accounting, and evaluated quality/cost/latency deltas against a recorded baseline. Learned routing remains experimental until its evaluation criteria pass.
- F2 — Prompt dialects: audit the existing dialect module and its production dispatch integration for routed, explicitly selected, and failover models. Verify all outbound provider parameters and endpoint-specific wrappers against current official documentation and versions.toml before changing them; do not copy example flags or model-performance assertions from the feedback as facts. Cover prompt structure, structured output, supported reasoning controls and continuity, descriptor overrides, and unknown-model behavior. Exit: request-level fixtures prove the selected provider/model receives supported settings, unsupported settings are omitted or rejected explicitly, failover reapplies the destination dialect, and governed instructions/tool schemas survive adaptation.
- F3 / P1 — Model-aware context: extend existing model-aware token counting and summarization with measured per-model budgets, output/reasoning reservations, compaction triggers, retrieval chunking and placement, and continuity across model switches. Preserve system constraints, tool groups, provenance, durable decisions, and pending work. Name summarizer failure and a smaller failover context window as required failure scenarios. Exit: long-conversation production-path evaluations stay within the resolved model budget, retain required task facts and valid history, expose truthful compaction telemetry, and compare quality, cost, and latency against the existing strategy. Apply model-specific placement or chunking only when supported by documentation or measured evidence.
- F4 — Unified AG-UI/A2A task lifecycle: assess current integration and define one host-owned task/run identity and lifecycle with protocol adapters. Cover parent/child relationships, tenant ownership, approval state, cancellation, failure/completion, artifacts, persistence, and replay/resume without duplicate execution. Preserve existing supported protocol behavior. Exit: local cross-protocol contract and integration scenarios correlate both views of a task, converge on the same terminal outcome, retain artifacts across restart, reject cross-tenant access, and replay without duplicated side effects.
- F5 — Activation-centric skills: evaluate actual discovery, selection, activation, and successful use, preserving conversation > agent > global scope precedence and governed execution. Use labeled positive, negative, ambiguous, explicit-invocation, and long-context cases. Measure precision, recall, unnecessary activations, actual tool use, task success, latency, and prompt-token overhead; do not treat tool use alone as evidence of success. Exit: freeze the dataset and numerical acceptance thresholds during planning, then demonstrate improvements over the current baseline without violating scope, permissions, or explicit user selection.
- F6 — Orchestration depth and graph observability: assess current loop, graph, and subagent execution before accepting the historical ten-iteration claim. Close gaps in host-owned bounded execution, parent/child budget accounting, approval suspension/resume, cancellation and cleanup, and inspectable workflow state. Extend RuntimeStep coverage to graph/subagent paths with correlated run/node/iteration/tool identities. Exit: linear and graph integration fixtures exercise success, approval, failure, budget/iteration exhaustion, cancellation, and resume with truthful ordered events, one terminal result, and no leaked child work. Keep mutation authority in trusted hosts, never agent kernels.
- F6 + F8 — Tool-inclusive agentic evaluation: exercise the production governed orchestration path with deterministic local tools and provider fixtures, and separately report live-provider runs when available. Score tool selection, argument validity, tool results, multi-step completion, approval/deny behavior, graph/subagent execution, history integrity, cancellation, and budgets. Exit: seeded behavioral regressions are detected by the local baseline/delta gate with nonzero exit; success/failure traces and reproducible artifacts are retained. Tool-less completion suites remain useful but cannot certify agentic behavior.
- F7 — Integrated knowledge runtime: connect retrieval, access checks, evidence verification, reasoning inputs, citation provenance, and audit through existing governed runtime seams. Preserve hybrid retrieval and embedding support. Cover conflicting/stale documents, revoked access, tenant separation, unsupported claims, and retrieved prompt injection. Exit: end-to-end fixtures trace answers to authorized source evidence, make insufficient/conflicting evidence explicit, prevent unauthorized content from reaching model context or user-visible audit output, and retain an inspectable retrieval/verification decision trail.
- F8 — Verification debt and supported-profile evidence: reproduce the two reported eval failures and remeasure the reported 33.68% frontend coverage against the existing 60% target with the same declared metric/denominator; resolve reproduced failures and meet the applicable target using meaningful behavior tests, without weakening exclusions or thresholds. Inventory supported runtime profiles and exercise affected behavior on each supported profile, explicitly recording unsupported or environment-blocked cases. Close historical pending-live-environment items for streaming resume/dedup, graph RuntimeStep events, telemetry/cost, cancellation, and shutdown using local integration and live evidence where required. Exit: a claim/evidence matrix records exact commands, outputs, commit/profile/environment, and coverage; unavailable evidence remains an explicit blocker rather than a pass.
- Delivery order and contracts: assessment baseline → P0 context correctness → routing/dialect/model-context integration → shared task/graph lifecycle and skill activation → governed knowledge integration → tool-inclusive evaluations and affected-profile evidence. Establish deterministic evaluation fixtures early enough to assess each change. Before implementation, create a dependency-ordered plan and OpenSpec change(s), each with at least one spec delta and scenario-level exit criteria. Every F1–F8 item must map to a change or a demonstrated already-satisfied requirement. Preserve capability inversion, typed protocols, tenant isolation, Cedar deny-final semantics, existing dependency pins, and the current UI. No dashboard removal, marketplace/channel expansion, dependency upgrade, deployment, or release is implied by this phase.
- Verification policy and uncomfortable scenario: run Tier 0 after each edit, Tier 1 at unit completion, and Tier 2 at phase completion using applicable repository rules; Tier 3 is reserved for a separately scoped milestone/release. All non-deployment verification runs locally. GitHub Actions remain deployment execution/validation only; historical eval-nightly or CI-test suggestions must be corrected in the new plan. Obtain fresh-context artifact-critic review before accepting planning/delivery artifacts. The uncomfortable scenario is that individually passing modules are disconnected from production or only tested on server-full, while long-running tool histories still fail. Phase completion therefore requires production-path and affected-profile evidence for all eight feedback areas, not module counts or a claimed percentage of harness parity.
