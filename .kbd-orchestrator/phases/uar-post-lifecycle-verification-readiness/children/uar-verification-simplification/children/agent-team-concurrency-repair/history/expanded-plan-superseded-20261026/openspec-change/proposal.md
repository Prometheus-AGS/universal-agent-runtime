# Proposal

## Why

The real math/writing team BDD created its team and tasks but both member runs failed skill admission, and one terminal settlement remained unconfirmed. The source suggests a filesystem-provider reconciliation mismatch; the retained error does not prove that precise branch or a scheduler defect.

## What Changes

- Reconcile configured filesystem skill sources with durable selection state before admitting runs, preserving API overrides and scoped enablement.
- Retain safely categorized admission and catalog-result errors rather than losing the cause behind a generic failure.
- Make same-attempt terminal settlement converge without replaying model/tool work, duplicate artifacts or duplicate usage revisions; retain unknown reservations and visible unresolved outcomes.
- Keep existing per-member Tokio execution and the portable math/writing BDD. Acceptance must show real overlap and a writer consuming both completed outputs.

## Capabilities

### New Capabilities

- `durable-team-execution`: add bounded requirements for same-attempt terminal reconciliation and overlapping task/result integration. This capability is not yet in canonical specs; the parent `afc-c09-team-admission-runtime` change also has a pending delta for it. Use distinct requirement names and reconcile that shared capability's archive order during Plan; do not mark the broader parent work complete.

### Modified Capabilities

- `skill-governance`: add configured-source startup reconciliation and private admission-cause requirements, preserving its existing scoped configuration behavior.

## Impact

Scope: Rust startup, skill registry/service admission, collaboration storage and terminal settlement/controller, their existing REST/run-event projections, the existing Node team behavior and documentation. No new library, provider, executor, UI, database schema redesign or dependency upgrade is proposed.

Runtime UX: a failed team operation must identify a safe actionable cause or unresolved settlement, rather than silently appearing to run forever. Existing successful run/event shapes and the public admission-failure code remain compatible; diagnostics are additive and owner-scoped. Provider routing stays on the configured Liter model. Realtime state must reflect confirmed outcomes while preserving uncertainty and retained accounting.

KBD: this child receives its own spec/task and draft acceptance contract; all prior consumption, parent obligations and failed receipts remain. The running artifact differs from the inspected-source baseline. This proposal is specification authority only, not implementation, contract adoption, verification or publication approval.
