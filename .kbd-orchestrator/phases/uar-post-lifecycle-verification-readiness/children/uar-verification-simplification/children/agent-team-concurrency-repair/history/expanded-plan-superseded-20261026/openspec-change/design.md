# Design

## Context

See proposal.md for motivation and the child assessment/analysis for retained evidence. The source registers `filesystem-skills-*`, while reconciliation selects `fs-skills`/`agent-skills`; boot loaded210 filesystem/0 database skills. This supports a source invariant defect, not proof of the precise served-build error. Terminal settlement errors currently return after logging; a worker can finish while its durable attempt remains running. A result-extraction error is not a known transaction rollback.

## Goals / Non-Goals

**Goals:** align actual source registration and durable metadata; retain safe typed causes; converge same-attempt settlement; demonstrate the existing concurrent project through real inference.

**Non-goals:** replace Tokio/team architecture; upgrade dependencies; alter provider choice; implement general project decomposition, team KB parity, UI/Boss work or cross-platform certification; reset historical reservations; rerun accepted prompting/KB journeys.

## Decisions

1. **Adapt cand-001.** Reconcile actual configured sources through existing source-aware merge policy, preserving API precedence, scoped selection and explicit roots. Do not special-case this project by skipping all skill capture when its skill list is empty. Preserve known last-good settings and do not report readiness for an inconsistent registry.
2. **Separate symptom from historical diagnosis.** Add private categorized diagnostics through existing error/event boundaries, retaining the public code. A future authorized read or the repaired-path gate must identify the actual branch. The source invariant fix is independently justified; it is not labeled proof of the old binary's exact cause.
3. **Adapt cand-002.** Inspect pinned SDK statement errors before decoding, preserve typed categories across the catalog boundary, and use exact receipt/fence comparisons. Reuse ingestion conflict classification and AG-UI predicate-read ideas, not their retries wholesale. Only a proven rolled-back typed conflict can be eligible for bounded storage retry. Any ambiguous result goes to same-attempt evidence reconciliation, never agent re-execution.
4. **Make settlement idempotent with unknown usage.** Matching terminal execution with `usage=None` must return its stable prior result without bumping usage revision again. Unknown accounting remains reserved. Known usage reconciliation is a separately evidenced operation, not a side effect of repeating a terminal update. A conflicting payload/fence fails closed.
5. **Reconcile retained uncertainty through existing recovery boundaries.** Use the original attempt and persisted terminal/thread/effect evidence. If that evidence cannot establish outcome, expose the existing uncertain disposition and retain liability; do not invent a failed/succeeded outcome. Repeated terminal-settlement reconciliation and conflicting-payload controls must exercise a conclusively terminal result, not just cache a recovery-command receipt. Use the fresh TEAM-01 terminal result for the known-usage control; additionally require a genuine confirmed terminal/unknown-usage fixture for the usage=None control. Prefer the retained original when evidence supports it. If that fixture cannot be established, SETTLE-01 is BLOCKED rather than satisfied by uncertainty. No original database fault needs to be fabricated.
6. **Adopt cand-003.** Keep per-member lanes and active limits. Retain one portable Node team entry and named sub-oracles ADMIT-01/SETTLE-01/TEAM-01; it may report several scenario receipts within the same project journey. No new umbrella runner. Positive execution uses actual Liter inference and durable Surreal; task setup and mock-only checks do not count.

## Risks / Trade-offs

- Startup synchronization could overwrite operator data → preserve source ownership and merge selection independently of body updates; retain existing scopes and precedence.
- Exact cause remains partially unknown → separate new-source invariants from historical diagnosis and retain typed future evidence. Do not widen into speculative backend replacement.
- Ambiguous CAS can have committed → reconcile stable identity before any further terminal write. Retry bounds and effects must be explicit in Plan/approval; no generic retry decorator.
- Retained failed record may lack sufficient terminal receipts → classify its disposition uncertain and preserve accounting. This proves honesty, not retroactive exact diagnosis or repaired fault recovery in every condition.
- A very fast calculation can finish before overlap observations → keep strict real overlap; improve observation only for an observed false negative, never count queued tasks instead.
- Parent pending `durable-team-execution` delta overlaps capability namespace → use unique requirement names; Plan must choose archive/merge order without closing broader parent tasks or importing Boss/UI obligations.
- Current artifact is not current source → build the repaired native artifact, bind its exact bytes/config/fixture, and request the exact final gate after implementation. Historical receipts remain historical.

## Migration Plan

No schema migration or release/publication is assumed. Preserve the current live store, agents and KBs; make a recoverable owned-store snapshot only through a safe offline boundary before any destructive fixture action. Implementation, source review, build, restart and verification each retain their own authority. Plan must provide the concrete startup/fixture/credential bindings and source inventory; this Spec does not authorize them. Rollback restores binary/config while retaining new receipts and unknown accounting; it does not erase confirmed durable mutations.

## Open Questions

The exact historic selection cause and CAS commit outcome are evidence questions. They do not change the normative invariant or prohibit specifying safe uncertainty. They must be recorded as unknown unless future exact authorized evidence resolves them. No disputed library/stack choice is deferred.

Persist stable terminal result separately from command audit receipts and keep cold/missing usage unknown. Details and owned files: child plan.md. These are planned changes, not current API claims.
