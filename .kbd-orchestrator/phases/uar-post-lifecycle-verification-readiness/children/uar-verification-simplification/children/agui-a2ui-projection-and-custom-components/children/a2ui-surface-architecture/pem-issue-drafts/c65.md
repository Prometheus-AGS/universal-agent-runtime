**UAR requirements for this issue** (A2UI surface-architecture review, 2026-10-28; context: UAR will use `a2ui-react` 4.2.0 as its client runtime over AG-UI `a2ui-surface` activities, and must test the same surfaces in React and Flutter).

1. **Flutter AG-UI transport.** The Flutter A2UI path today is the `flutter-riverpod` showcase, which is keyless and deterministic, with no AG-UI transport and the basic catalog only (`examples/flutter-riverpod/lib/a2ui/showcase_runtime.dart`). UAR needs a published Dart path that consumes `a2ui-surface` activities over AG-UI SSE, including a persistent `connect()` stream, with the same policy gates as React.
2. **Parity with the React runtime.** Flutter needs the same activity semantics as the new React issues: idempotent redelivery, deltas, surface versions, held-version reporting, resync, unique action ids and drafts.
3. **Entity-bound data.** A declarative projection of graph entities into a surface's data model, with write-back through the existing default-deny action policy, in React and Flutter. Application data then stays out of the A2UI operation stream. This matches this issue's criterion that views "stay live from canonical subscriptions, not static model JSON".
4. **Drafts.** Unsent input per surface persists locally and survives a full restatement or reconnect.
5. **Application catalog implementations** for Flutter equivalent to React's application-supplied implementations, so one catalog can declare both target renderers.
