## Problem

`PrometheusA2uiRuntime.processAgUiEvent` treats every activity `messageId` as a delete handle. Any `ACTIVITY_SNAPSHOT` without `replace:false` first deletes the surfaces that the same `messageId` created earlier, then re-applies only that message's operations (`packages/a2ui-react/src/official/runtime.ts:289-315`). AG-UI's `replace` defaults to true. A `replace:false` snapshot for a known `messageId` is silently ignored (`:289-291`).

Redelivery is normal in AG-UI clients. It happens on reconnect replay, when `MESSAGES_SNAPSHOT` restates a thread, and when two streams (a run stream and a `connect()` stream) carry the same activity.

## Failure sequence

1. Activity m1 creates surface S. Activities m2..mn update S. The user types into an input bound to S's data model.
2. m1 is delivered again.
3. S is deleted and rebuilt from m1 alone, so the typed input and m2..mn are lost.
4. When m2..mn are re-delivered, each one deletes S (its prior set) and then sends `updateComponents` to the deleted surface. That throws in `web_core` (`message-processor.js:570`), so S stays at its creation state.

No error reaches the user.

## Expected

- Applying an activity is idempotent. Redelivering identical content (same `messageId` and same content digest or version) does nothing.
- A `replace:true` restatement of a surface the runtime already holds reconciles instead of deleting and recreating. At minimum it must not discard the data model or later updates without an explicit signal from the producer.
- The `replace:false` rule for known messages is documented.
- How activities appear in `MESSAGES_SNAPSHOT` and in replay is documented.

## Acceptance criteria

- [ ] Fixtures cover duplicate delivery of a create activity, duplicate delivery of update activities, out-of-order redelivery, and `MESSAGES_SNAPSHOT` replay of a thread that holds live input. None of them changes a surface the runtime already holds, and none loses input.
- [ ] A genuine restatement (new content for a held surface) follows a documented rule with no silent data loss.
- [ ] Behavior on two concurrent streams carrying the same activity is specified and tested.
