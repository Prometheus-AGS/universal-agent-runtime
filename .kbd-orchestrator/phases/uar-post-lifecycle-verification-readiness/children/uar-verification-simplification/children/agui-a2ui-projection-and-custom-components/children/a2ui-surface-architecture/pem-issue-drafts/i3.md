## Problem

The A2UI v0.9.1 client action has no id. The schema defines only `name`, `surfaceId`, `sourceComponentId`, `timestamp` and `context` (`@a2ui/web_core` 0.12.0 `src/v0_9/schema/client-to-server.js:19-33`). PEM creates an action id only for v1 actions with `wantResponse`, as `surface:component:++counter`, and the counter belongs to one runtime instance (`packages/a2ui-react/src/official/runtime.ts:362-367`).

A server cannot make action handling idempotent with that id. Two tabs, or one tab after a reload, produce the same id, so a legitimate second action would be dropped as a duplicate.

## Proposed

- Every dispatched action carries a globally unique id (for example a UUID), for v0.9.1 and v1 alike, in a documented extension field. Existing v1 `wantResponse` correlation keeps working.
- The action envelope can carry the surface version the runtime held when the action fired (see the versioned-activities issue).
- A helper builds the upstream AG-UI envelope `forwardedProps.a2uiAction.userAction`, with the data model attached when the surface sets `sendDataModel` (`getClientDataModel()`, `runtime.ts:335`).

## Acceptance criteria

- [ ] Ids are unique across runtimes, tabs and reloads. Retrying one action reuses its id; a new action gets a new id.
- [ ] Envelope fixtures cover v0.9.1 and v1, with and without `sendDataModel`.

## Context

Requested by the Universal Agent Runtime (UAR) A2UI surface-architecture review (KBD child `a2ui-surface-architecture`, 2026-10-28). UAR intends to use `@prometheus-ags/a2ui-react` 4.2.0 as its client A2UI runtime for chat surfaces, full applications and per-user surfaces that change shape at runtime, delivered as AG-UI `a2ui-surface` activities. Findings come from reading source at `28a500d6`; nothing was built or run.
