## Problem

`processAgUiEvent` handles only `ACTIVITY_SNAPSHOT` (`packages/a2ui-react/src/official/runtime.ts:272-316`). A producer that updates a long-lived surface incrementally has two options today:

- resend the cumulative operation list (`replace:true`), which resets the surface (see the redelivery issue);
- open a new activity `messageId` per batch, which multiplies activity messages in `MESSAGES_SNAPSHOT`.

There is also no way for a reconnecting client to say which surface versions it already holds, and no way to recover when the client rejects a batch.

## Proposed

1. **`ACTIVITY_DELTA` for `a2ui-surface`.** Append-only (`add /a2ui_operations/-`) operations applied to the held surface, without deleting it.
2. **A surface version in activity content.** Stale snapshots and deltas are ignored. A gap is detected and reported.
3. **Held-version reporting.** The runtime exposes the versions it holds per surface, so a host can send them on reconnect or `connect()` and receive only the missing operations.
4. **Client error and resync reporting.** When the runtime refuses a batch that the producer accepted (catalog, topology, caps), it reports the A2UI validation error and requests a resync instead of silently stalling at its last version.
5. **Applying operations returned with a stale-action rejection.** The host gets back the operations since the version it held.

## Acceptance criteria

- [ ] Delta, stale-version, gap, resync and reject-then-resync fixtures pass. Typed input survives deltas and version-based catch-up.
- [ ] The AG-UI version this targets is stated (`@ag-ui/core` 0.0.59 peer versus the AG-UI 1.0 activity specification).
