## Governing model

The acceptance unit is a user journey: configured client → supported mounted entry → effective saved agent/policy → actual provider/model and collaborators → useful result → durable continuation. For orchestrator work insert current authorized roster → intent-based agent decision → selection event delivered to client → selected agent execution. Skill candidate matching is a different decision and cannot stand in for agent routing.

A positive completion requires an input-dependent model response satisfying a fixed task predicate plus a successful protocol terminal. Use a freshly generated fact or structured transformation whose expected answer is known independently of the model. A two-turn sentinel tests retained context. A custom-agent marker instruction tests whether the saved prompt is actually effective. For tools/KB/teams, use facts available only through the intended collaborator and retain actual collaborator receipts. Validate routing and source provenance as well as answer content, so a lucky response cannot mask wrong execution.

## Priority and interactions

1. Empty-store boot, explicit REST provider/model configuration, useful default-agent prompt. Establish one genuine response before spending on advanced cases.
2. Saved custom agents, protected default/orchestrator deletion, warm restart and maintenance. Preserve operator changes; deny deletion without changing either durable/live availability.
3. All supported interfaces and SDK clients; orchestrator intent/roster routing with AG-UI selection streaming; A2UI render/action/continuation. Client protocol and outbound provider protocol are independent axes.
4. Effective skill discovery/selection/activation, then context policy/budget behavior using actual selected instructions and tool groups.
5. Grounded knowledge and embedding-model regeneration, including equal-dimension model changes, changed dimension and interrupted rebuild.
6. Teams: dependency and concurrency, permissioned handoff, multiple calls, durable reassembly, cancellation and constrained recovery. Tool approval, ownership and duplicate-effect controls are embedded user requirements throughout.

Postgres and durable Surreal run the same outcome predicates in each slice. Use a named representative interface for deep backend journeys, then interface parity for prompting/routing; add cross-products only for an identified interaction. This avoids certifying one backend by inference without multiplying every setting by every protocol, provider, platform and model.

## Fixed planning decisions

- Cover all supported prompting surfaces and all customer-selectable strategies. Keep advertised-but-incomplete rows in the required denominator; an unsupported classification requires explicit support-contract disposition, never a silent exclusion.
- Use the configured real primary chat model, a second real configurable binding for selection/persistence effects, and real embedding models. Credentials are resolved by reference at execution. No keys or environment dumps in artifacts.
- Three fresh-session repetitions of each positive instantiated case, distinct input facts; add a true process restart in each durability case. This is 3/3 observed reliability, not a statistical production SLO. A first failure stops the packet; no silent rerun until it passes.
- Fault injection is bounded and labeled; positive branches still need real inference. A2UI needs actual rendering and an actual user action round trip. Selection events need client-visible semantic content and correct run/agent correlation, not a trace log alone.
- Fix existing promised behavior rather than broad refactoring. Planning does not authorize the future product or harness edits listed here. Where a source gap requires implementation, the full-phase boundary expands.
- Builds, review and Issue426 integrations remain supporting obligations linked to relevant outcomes. Build matrices are not the primary acceptance metric. Existing broader release/profile obligations remain pending until explicit signed disposition; this plan does not waive them.

## Evidence and failure retention

The coverage matrix defines inputs, expected/failing outcomes and owners. Every receipt identifies exact source/artifact/configuration revision, entrypoint, backend, provider/model/embedding fingerprint, agent/roster/thread/run IDs, requested/effective strategy, input and redacted output, timing/limits, persisted before/after state and actual terminal status. Do not retain chain-of-thought or secrets. Store bounded error envelopes, typed causes and job/record metadata before exact-owned cleanup; if redaction removes a decisive fact mark the cause unrecovered.

Retain both protocol outcome and user outcome. PASS requires every predicate. FAIL, BLOCKED, NOT_RUN and explicitly UNSUPPORTED stay distinct. No absent DB/provider/worker produces PASS. Cleanup is judged against processes/resources actually created plus owned residuals; an unreached optional launch is not automatically a leak, but any unconfirmed active resource blocks completion.
