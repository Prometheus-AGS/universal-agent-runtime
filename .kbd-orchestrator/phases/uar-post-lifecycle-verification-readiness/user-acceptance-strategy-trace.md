## Team ordering and thread context

The inspected team planning API describes tasks with `depends_on`, not a sequential/parallel execution-mode enum (`domain/team_planning.rs:54,139`). Planning creates ready versus dependency-blocked tasks (`compiler/collaboration/team_planning.rs:260–280`). Admission requires assigned member, role, ready status and every dependency succeeded (`team_execution/admission.rs:98–115`); settlement advances dependents (`team_execution/settlement.rs:222`). Therefore dependency-ordered tasks and independently admissible tasks are source-backed forms. An actual concurrent overlap claim still requires the controller's configured capacity and observed overlapping real calls. Do not invent “swarm”, “round robin”, or “hierarchical team mode” cases from generic expectations. Other workflow execution schemas/modes were not exhaustively mapped in this bounded trace.

Team selected context is attributed task/team input, authorized inbox, authorized referenced artifacts and skill references (`team_execution/context.rs:36–167`). Artifact access checks exact owner/workspace/team and directed edge at `:91–102`. A continuation carries prior attempt/wait/input and target outcomes as untrusted attributed data (`:72–89`); this is not unrestricted predecessor conversation history. Workflow context uses a distinct reduced payload and omits ordinary team inbox (`:72,163`). Selected skill references explicitly do not prove body activation (`:120`). `runtime_semantics.rs:409` rejects required `authorized-fork` context; automatically promising parent-history fork would contradict current source.

`runtime/team_execution/execution.rs:257–284` reselects context, records selection, creates an ordinary bound-agent run from serialized context data, attaches guidance separately and gives each attempt `session_id = team-attempt:<attempt-id>`. Session identity therefore changes across distinct continuation attempts. Same-attempt tool/model rounds and cross-attempt attributed handoff are distinct acceptance subjects. Parent/child inherited run bindings explicitly contain captured models, skills, policy, thread, controls and resources (`runtime/turn/bindings.rs:87`), but their presence does not prove arbitrary team-history inheritance. `runtime/manager.rs:6300` restores checkpoint/inherited history excluding system messages before appending input; ordinary session history is the alternate path.

Recovery is conditional: `runtime/team_execution/recovery.rs:24–95` requires matching persisted run/root/yield control, a nonempty fully terminal thread tree, canonical tool receipts and no ambiguous/unknown unsettled effects before confirming a joined yield. A saved wait is not a restored live future. Broad “restart resumes everything” is not supported by this path.

Authoring task T1: define a dependency pair and two independent tasks using actual team/task/attempt APIs; dependent cannot dispatch early, independently admitted tasks contribute once, and each child has correct model/member/root/owner identity. T2: carry a unique fact through a permissioned artifact or inbox, wait/continuation and at least two real rounds; show exact selected and consumed context receipts, fresh attempt session, canonical call/result sequence, final grounded integration and another team's secret absence. Do not infer raw thread inheritance from final answer. T3: author workflow-specific context separately if workflows enter the denominator. T4: bind restart/recovery to persisted yielded root/terminal-child/canonical-effect criteria; unknown effects must remain explicit unresolved state with no duplicate execution. Configured concurrency, complete workflow mode enumeration, exact UI entry points and full cold-restart durable-adapter behavior remain unresolved source tasks.
