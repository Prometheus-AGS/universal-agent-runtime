First complete run of the capability matrix. Every prior number in this repo's
notes predates ~15 commits and is stale; this supersedes all of them.

## Exact command

```bash
UAR_LIVE_INTEGRATION_BACKEND=recorded \
  cargo test --locked --no-default-features --features server-full \
  --test integration live::capability_cases -- --test-threads=1
```

**Backend mode: `recorded`** — the in-process OpenAI-compatible stub
(`tests/integration/live/stub_llm.rs`). No API keys, no token spend, no network.
Recording the mode is not decoration: results differ between `recorded` and
`live`, so a baseline that does not name its mode is not reproducible.

`--test-threads=1` is required. Every booting case is `#[serial]`, and
`harness.rs:283-289` records a full run passing module-by-module while failing
7/16 concurrently on health-check timeouts.

Profile: `server-full`. **This baseline says nothing about any other profile**,
and in particular nothing about `embedded-mobile`, where GAP-04 states the Rust
library API is the whole contract.

## Both failures are instrument defects, not runtime defects

**`l3_c04_credentials_listing`** — `capability_cases.rs:356`

```
assertion `left == right` failed: C-04: expected 200,
got: {"error":"Authentication required"}
  left: 401   right: 200
```

The credentials endpoint guards unconditionally, which is correct behaviour for
a credentials surface. The test never sent a token and asserted 200.

**`shape_only_c13_sessions`** — `capability_cases.rs:511`

```
assertion `left == right` failed: C-13: expected 200, got:
{"error":{"message":"Session history route disabled. Reuse X-UAR-Session-ID
with POST /api/chat/completion","code":"legacy_route_disabled"}}
  left: 404   right: 200
```

The route was deliberately retired and the runtime says so precisely, naming its
replacement. The test asserts a contract the runtime intentionally does not
honour.

**The honest reading is 18 of 19 capabilities behaving correctly, with zero
runtime defects surfaced.** Reporting "2 failures" would overstate the runtime's
problems by 100%.

This is the second consecutive run where the instrument's error rate exceeded the
runtime's — the previous run produced 5 failures of which only 3 were defects.
**That is a finding about the measurement, and it is why "27 of 27 have a case"
is not an acceptable exit criterion for this phase.**

## What this baseline does NOT establish

Carried from the MiniMax-M3 / k3 adversarial review, unchanged and unclosed:

1. **No L4.** `boot_test_server` uses a fresh temp SurrealKV path per boot and
   `start_server` has no shutdown hook, so write→reboot→read cannot be
   expressed. C-12 and C-13 are exactly where L3 without L4 is nearly worthless.
2. **No semantics.** Assertions check response shape. C-03 returning the wrong
   model passes.
3. **One profile.** `server-full` only.
4. **No tenant isolation.** C-21 needs two tenants and a cross-read attempt;
   `#[serial]` single-tenant cases cannot express it.

The `l3_` label is overstated on C-03, C-05, C-08 and any capability whose
correctness depends on model output: against a stub whose fixtures the test
author wrote, "did my code parse my own canned output" is L2-wired, not
L3-exercised.

**The claim this baseline supports, in full:** *on `server-full`, against a stub
LLM, in a throwaway database, 18 of 19 exercised capabilities return
correctly-shaped responses, and the 2 failures are miscalibrated assertions
rather than runtime defects.* It is not a doneness measurement and must not be
reported as one.
