## Harness decisions the reviewers should know

- The operator always acts on a second page of the same browser context (`s1.operatorPage()`), at `/admin/providers`. That is also the "from another page" of scenario 6. The held-route checks run on that page.
- A thread has no sidebar row until its first message, so a "conversation" is a harness handle: its agent and override are recorded, the thread is renamed to the conversation's name (sidebar Actions, Rename) after its first message, and a not-yet-sent conversation that is switched to is recreated on a fresh thread with its recorded agent and override.
- Reply text is captured at send time from the Conversation section (`bdd-reply-...`, newest after the count grew). `the reply to ... came from ...` requires exactly one stub request across all three stubs whose last user message equals the message, the expected provider's stub, a wire model that equals the id or ends in `/<id>`, and the captured reply text `bdd-reply-<id>`.
- Refusal steps record texts as `HTTP <status> <body>` plus visible errors. When the picker does not offer a pair (disabled provider), the harness sends the same `POST /api/uar/providers/<id>/default` the console would, to observe the server's reason. For an override the picker does not offer, it sends the `agent-config` request from the page.
- `purgeBddAgents` deletes agents whose title starts with `BDD Agent` at the start of each S1 scenario (other features leave such agents with explicit models, which would be listed as pinned). `s1.dispose()` releases held replies and restores providers (B back on stub A, one model) and the openai default.
