## Exact response shapes (W4 depends on these)

- `POST /api/uar/providers/{id}/default`
  - 200, empty body: success.
  - 404 `{"error":"Provider '<id>' not found"}`: unknown id (unchanged).
  - 409 `{"error":"Provider '<id>' is disabled"}`: disabled provider. No persistence, no registry change.
  - 500 `{"error":"Failed to persist default provider: <e>"}`: unchanged.
  - 404 `{"error": "<registry error>"}` if the registry swap fails after the existence check (race; unchanged).
- Settings API for key `llm.default_provider` (PUT single, PUT bulk with a `default_provider` field in the `llm` payload, DELETE reset): 422
  `{"error":"unsupported_setting","key":"llm.default_provider","message":"'llm.default_provider' is managed by the provider registry and cannot be changed here; use POST /api/uar/providers/{id}/default to change the system default provider"}`.
  Note: the 422 fires before the revision check, so a stale-revision PUT now gets 422, not 409.

## 1.8 findings: writers of `llm.default_provider`

Every write goes through `SettingsManager::set_value` (`manager.rs:1257` `set_default_provider_id`) or a config seed:
1. `providers.rs:~381` default route (intended).
2. `manager.rs:~1020` boot seed in the provider seeding path, only when no persisted value exists.
3. `manager.rs:~2948` core schema seed (`build_core_schema`), applied by `initialize`: first boot insert; later boots overwrite only when the row has no `updated_at` (config-controlled), otherwise drift is flagged. This is the config-derived seed at boot.
4. **Not named by the task:** `providers.rs:335` provider delete route writes `""` via `set_default_provider_id("")` when the deleted provider was the default (error ignored with `let _ =`). It does not swap the registry default itself. This is a third runtime writer. It is outside the 1.7/1.6 asks, so I left it. Decision for lead: accept as a documented clearing path, or route it through a shared "clear default" action. Note it also does not call `record_effective`, so after deleting the default provider the effective map still holds the old id.
5. Settings API generic writers (`update_setting`, `update_namespace`, `reset_setting`, `set_value_if_revision`, `reset_to_default_if_revision`) could write the key; now blocked by 1.6.
Readers/other: `provider_sync.rs:21` reads it to set the registry default at boot. No console code writes it. `tests/settings_persistence.rs:1175` calls `set_default_provider_id` (test only).

## Decisions

- Kept `set_value` semantics. `llm.*` is `NextTurn`, so `set_value` still records effective at persist time, before the registry swap. `record_effective` after the swap is therefore redundant today; it becomes the sole recorder once SET 1.2 classifies the key. Residual window: persist ok, then registry swap fails (provider removed between the existence check and the swap) - effective would already claim the new id. Closing it needs the 1.2 table.
- Used `serde_json::json!` fully qualified in `providers.rs` (the non-test module has no `json` import).
- Added one test (authored, not run) for the 409 path asserting no registry or durable change.
