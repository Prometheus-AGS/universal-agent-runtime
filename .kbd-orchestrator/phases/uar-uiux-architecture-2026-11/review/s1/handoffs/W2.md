## 2. Wire contract for W6 (exact field paths)

Receipt object (one per completed assistant turn):

```json
{
  "version": 1,
  "served_provider": "bdd-provider-b",
  "served_model": "claude-5-haiku-20261101",
  "model_origin": "system_default",
  "model_origin_since": "2026-11-20T10:11:12Z"
}
```

- `served_provider`, `served_model`: from the provider's own response (last completed model call of the turn). `served_provider` is the registry provider id (prefix of the driver's qualified model). Render as `served_provider + "/" + served_model`.
- `model_origin`: `system_default | conversation | agent | turn | configured_fallback`, or `null` when no origin can be stated truthfully (Global-scope route, or availability routing / skill preference replaced the admitted route). Render nothing for `null`, never a guess.
- `model_origin_since`: RFC 3339, UTC, second precision (`...Z`). Non-null only when `model_origin == "system_default"`. Frozen at admission; a default change during the turn does not alter it.
- A refused, failed or cancelled turn emits NO receipt.

Where it arrives:

1. Live stream: AG-UI `agui.artifact` event (`src/uar/api/sse.rs:622`) with `artifact_type === "model_receipt"`, `artifact_id === "model-receipt-<run_id>"`, receipt object in `metadata`, same JSON string in `content`. On the official AG-UI wire it is custom `uar.artifact.available` with `value.artifactType`, `value.metadata`. Emitted once, before the terminal event. NOTE: the existing frontend turns every `agui.artifact` into a `__a2ui_display__` tool-call chip (`frontend/src/stores/chat-stream-store.ts:1228-1246`); W6 must intercept `artifact_type === "model_receipt"` there and render the receipt instead of a chip. The event is emitted after the answer text, so it can attach to the turn's message.
2. Reload: `GET /api/uar/sessions/{id}` -> `history_runs["<run_id>"].model_receipt` (same object, or `null`). `frontend/src/services/chat-sessions-api.ts:25` already spreads `history_runs[run_id]` into each message's `run_metadata`, so it is `run_metadata.model_receipt`. The same entry's `policy` now also carries `model_origin` and `model_origin_since` (admission values; prefer `model_receipt`).
3. Effective view (7.4/7.5): `GET /api/uar/sessions/{id}/effective-config` (still 404 when the conversation has no stored policy). Added:
   - `effective_policy.model` / `effective_policy.model_origin` / `effective_policy.model_origin_since`: bound the way chat admission binds a route (see section 5, finding F1). `model_origin` and `model_origin_since` are omitted from `effective_policy` when absent (skip-if-none).
   - `model_unavailable_reason`: `string | null`. Non-null means admission would refuse the turn and `effective_policy.model` is `null`.
   - `inherited_model`: `{ "model": {provider_id, model_id} | null, "model_origin": ..., "model_origin_since": ..., "unavailable_reason": string | null }` = what the conversation would use if its model override were cleared (agent model -> origin `agent`, else the system default). This is the 7.5 clear-preview source.
4. Agents read (4.2): `GET /api/agents` -> `runtime_agents[i].explicit_model`: `"provider/model"` or `null`. `AgentArtifact.extensions` was already exposed in the same payload, so a derived field was not strictly required; it was added so the browser does not re-implement the predicate (malformed `uar.run_policy` extension handling cannot be mirrored in TS). Federated agents are unchanged.
5. Override refusal (7.8): `POST /api/uar/sessions/{id}/agent-config` (the console path) and `PUT /api/uar/conversations/{id}/policy` now answer `422` with `{"error": "<reason>", "code": "model_not_offered", "provider_id": "...", "model_id": "..."}` when the provider is unknown, disabled, does not list the model, lists it disabled, or admission would refuse it (unverified). Nothing is persisted on refusal. Reasons: `Provider 'x' is not configured`, `Provider 'x' is disabled`, `Provider 'x' does not offer model 'y'`, `Model 'y' is disabled on provider 'x'`, or the admission text `Selected model is disabled, unverified, or its configuration changed; verify it in UAR settings`. Clearing (null model / DELETE) is never validated. NOTE: `saveAgentSessionConfig` (`frontend/src/platform/entities/session-configuration/api/session-configuration-api.ts:171-196`) discards the body; the reason is not shown until it reads `error`.

## 5. Findings the lead must decide on

F1. **Disabled system default: the console path refuses the turn, it does not serve the YAML fallback.** `server.rs` `resolve_requested_model` with no scoped route takes `registry.default_id()` plus that provider's `default_model` and calls `verified_model`, which returns `None` for a disabled provider (`model_verification.rs:31-35`) and so yields `422 model_not_verified`. `llm_config.model` (the YAML fallback) is only reached through `RunManager::default_model_source` (embedded/no pre-resolved policy, and `backfill_effective_model`). So SCN-SYS-012 as written ("the preview names the configured fallback and the next reply is served by it") does not hold on the console path today, and plan decision P-4 ("keep the fallback as today") does not describe this path. I did NOT change admission. The effective view and `inherited_model` mirror real admission: they report `unavailable_reason` and a `null` model instead of naming the fallback. To meet S1-R4 as designed, either admission must fall back to `llm_config.model` when the default cannot be verified (a behavior widening, operator call), or S1-R4/SCN-SYS-012 must say "refuse the clear / show the unavailable reason". `ModelOrigin::ConfiguredFallback` is implemented for the manager path.
F2. **Verified-model requirement.** Admission and now the override save require the model to be listed, enabled and to carry a current verification proof (`model_verification::current`). W3's provider helpers (`ensureSecondTestProvider` style) must create that proof for `bdd-provider-b/claude-5-haiku`, `bdd-provider-c/qwen-5-turbo` etc., or every turn and the override save returns 422.
F3. **Receipt time window.** The live route writes the `llm.default_provider` row before it swaps the registry (`providers.rs` set_default). A turn admitted in between sees a mismatch and gets `model_origin_since = null` (honest, not wrong). When an operator changes only the default model of the current default provider (`PUT` then `POST .../default`), turns admitted between the two calls use the new model with the previous row time. `system_default_activation_time` does not see the `PUT`.
F4. `model_origin` is `null` when `run_llm_config.qualified_model_name()` differs from the admitted route (health failover or skill preferred model). Intentional: the origin would describe a model that is not serving.

## Round 2 (lead decisions on F1 and F3; source only, not compiled)

### F1 implemented: configured fallback on the console path
Rule: only when NO scope named a route (system default path) and the registry default cannot be verified (no default, provider disabled/missing, or its model fails `verified_model`), `llm_config.model` serves IF it passes `verified_model` itself. Origin `configured_fallback`, `model_origin_since = null`. If the fallback is unconfigured or also unverifiable, the original 422 `model_not_verified` (or `model_not_configured`) stands. Scoped (agent/conversation/turn) models that fail verification still 422 with no substitution; they never reach the fallback code.
- `src/uar/runtime/manager.rs`: new `pub(crate) fn configured_fallback_model()` (the YAML model as `(provider, model)`), `default_model_source` now calls it (~11429-11455). Behavior of `resolve_default_model`/`backfill_effective_model` unchanged.
- `src/server.rs`: new `resolve_unscoped_model` (before `ChatStreamCursor`, ~7099-7130) returns `(ResolvedModel, fell_back)`; admission uses it only when `route_from_system_default` and sets origin `configured_fallback` (no time) or `system_default` + time (~7729-7765). Scoped routes still go through `resolve_requested_model` unchanged.
- `src/uar/api/discovery.rs`: `bind_admitted_route` rewritten to mirror it (~1155-1215): default verifies -> `system_default` + time; else fallback verifies -> `model = fallback route`, `model_origin = "configured_fallback"`, no time, `unavailable_reason = null`; else `model = null` and the default's refusal reason. Both `effective_policy` and `inherited_model` (and `model_unavailable_reason`) use it, so the clear preview names `openai/gpt-5.4-mini` from `configured_fallback` when the default's provider is disabled.
- The receipt for such a turn carries `model_origin: "configured_fallback"`, `model_origin_since: null` (manager guard `admitted_route_serves` holds because the run is admitted on that exact route).
- F2 residue: the fallback model also needs a current verification proof (W3).

### F3 checked: no code change needed
`set_default` (`providers.rs` ~367-411) calls `sm.set_default_provider_id(&id)` on every successful call, even when the provider id is unchanged. That goes to `SettingsManager::set_value` -> `set_value_locked` (`settings/manager.rs` ~606-640), which builds the row with `updated_at: Some(Utc::now())` unconditionally, upserts it, and replaces the cache entry. The three stores persist the supplied `updated_at` (memory inserts the struct; Postgres `updated_at = EXCLUDED.updated_at`; Surreal binds `setting.updated_at`). `get_with_meta` reads that cache entry. So the live route always refreshes the time: the picker flow (`PUT` provider default_model, then `POST .../default`, including the same provider) shows the POST time as the activation time. Decision: keep as is. Not covered by design: a `PUT` that changes the current default provider's `default_model` WITHOUT a following `POST .../default` changes the serving model without a live-route call; adding a second writer of `llm.default_provider` would break S1 1.8 / SET 1.6, so it is left. The row is stamped just before the registry swap (millisecond gap, second precision; a turn admitted inside the gap gets `since = null` only if the provider id differs).
No edits to `providers.rs` or `settings/manager.rs` in this round.

## Round 3 (verification fingerprint; source only, not compiled)

Defect (W3): the console default action does `PUT` provider with a new `default_model`, which changed `model_verification::fingerprint`, staling every proof of that provider (422 `model_not_verified`).

Change: `src/uar/api/model_verification.rs` `fingerprint` (~line 17-22) removes `default_model` from the serialized `ProviderConfig` before hashing. Still hashed: `id`, `display_name`, `base_url`, `api_key` (or the protected credential revision), `protocol`, `enabled`, and the whole `models` list (ids, enabled flags, pricing identity, execution profile, capabilities).

Consumers checked (no semantic change besides the intended one):
- `fingerprint` is verification-only: `current` (proof check), `providers.rs` ~474 and ~626 (initial vs final digest during the explicit verify call, so a mid-verification edit of any other field still returns 409), and the proof's `configuration_digest` is only echoed by `server.rs`, `routes.rs`, `targets.rs`.
- The concurrency revision (`TEAM_REVISION_CONFLICT`) comes from `prepare_provider_update` in `providers.rs`, a separate path that does not call `fingerprint`. Untouched, so no split was needed.
- Consequence: proofs recorded before this change carry the old digest (it included `default_model`) and read as stale once; they need one re-verification after upgrade. Proofs recorded after it survive `default_model` changes.
- Limit: a proof binds a model id, not the default; switching `default_model` to a model that was never verified still returns 422 for that model.
