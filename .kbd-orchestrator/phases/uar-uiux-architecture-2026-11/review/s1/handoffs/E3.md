## Fixes

### 1. Effective-model view (steps.ts `expectEffectiveView` ~615; s1-ui.ts `openEffectiveView` 488-494)
- `openEffectiveView` now waits for `session-config-effective` to have `aria-busy="false"`
  (`frontend/src/features/chat/session-model-view.tsx` sets `aria-busy={stored === undefined}` and
  shows "Checking which model answers…" while loading). The failure state (Retry alert) has no
  `aria-busy`, so it fails the wait.
- `expectEffectiveView` requires `session-config-effective-model`, `session-config-effective-origin`
  and (when expected) `session-config-requested` by testid with exact text. The whole-block
  `toContainText` fallbacks are removed.
- Why no false pass: the requested model and the sentence "Nothing is saved for this conversation
  yet… system default" are outside those fields. A build whose effective model never resolves (the
  "No model can answer" branch renders no `session-config-effective-model`) or that reports another
  origin now fails.

### 2. Refusal (steps.ts `the change is refused with a reason mentioning` 715-731; s1-ui.ts `tryOverride` 389-470, `RefusalObservation` 341, `errorCodeOf` 355)
- Each refusing When step records a structured `RefusalObservation` (WeakMap `refusals`, steps.ts 78)
  holding the response of the specific refused request. The picker's label is kept for the failure
  message only and can no longer satisfy the step.
- Override (SCN-SYS-016): `tryOverride` arms `page.waitForResponse` for `POST
  /api/uar/sessions/<that session id>/agent-config` whose JSON body `model` equals the refused model,
  then sends a minimal body `{agent_id, model}` (so the model is the only possible refusal reason,
  per the reviewer's suggestion; `AgentSessionConfig` needs only `agent_id`). It reads `GET
  .../agent-config` before and after (200 or 204 required). The step asserts status exactly 422,
  body `code` exactly `model_not_offered`, saved model after == before and != the refused model, and
  the needle in the response body (underscores read as spaces, so "not offered" matches the code
  `model_not_offered`; the server's `error` text is "Provider 'x' does not offer model 'y'").
- Live-route refusals ("disabled", "not found"): 4xx status and the needle in that response body
  (server: 409 "Provider '…' is disabled", 404 "Provider '…' not found", `src/uar/api/providers.rs`
  `set_default`).
- Why no false pass: an unrelated 4xx (for example a 400 body-shape error) fails the 422/code check,
  and a server that accepted the model fails the status check and the persisted-model check.

### 3. SCN-SYS-007 settle window (steps.ts `the console wrote none of the settings` 803-; constant `POST_ACK_SETTLE_MS` 72)
- Before asserting, the step waits until `s1.latestChangeEnd()` (harness clock at the live route's
  acknowledgement, recorded by `operatorChange`) + `POST_ACK_SETTLE_MS` (3000 ms, equal to the
  existing `NO_WRITE_WINDOW_MS` of CTL-SYS-001-HELD-500), then scans the whole write log of the
  scenario.
- Why no false pass: a forbidden settings write sent within 3 s after the acknowledgement is now in
  the log when the step checks it.

### 4. Receipt model comparison (steps.ts helpers `parseReceiptModel` 96, `servedModelId` 110; steps 549, 590, 600)
- Source read: `answer-receipt.tsx` renders `answer-receipt-model` as `${provider}/${model}` from
  `served_provider`/`served_model` (`model-receipt.ts` `parseModelReceipt`); the stub reports the
  request's wire model (`stub_llm.rs` 389-401), except `served_model` fixtures, which report the
  fixed id `claude-5-haiku-20261101`; fixtures key on both bare and `<provider>/<model>` wire models.
- The label is split at its first slash into serving provider and served model. Provider is
  compared exactly. The served model is compared exactly after removing only the serving provider's
  own prefix (`openai/openai/gpt-5.4-mini` -> provider `openai`, model `gpt-5.4-mini`), the same rule
  `wireModelMatches` applies. Any other prefix is left in and fails the exact comparison.
- "does not name X as the serving model" compares the last path segment of the served model, so no
  prefix form hides X.

### 5. Receipt tied to the message just sent (s1-ui.ts `noteRepliesBefore` 85, `assistantTurns` 519, `answerTurnOf` 541, `receiptOfLastMessage` 550, `receiptModelsInConversation` 575; steps 549-612)
- At send time (`noteRepliesBefore`, used by both send paths) the harness records the message and
  the `data-message-id`s of the assistant turns (`[data-role="assistant"]`, `enhanced-thread.tsx`
  AssistantMessage) already in the transcript.
- `receiptOfLastMessage` polls (15 s) one atomic DOM snapshot until the newest assistant turn that
  is new since the send and shows the reply text captured for that message has its own receipt, and
  requires exactly one receipt there. It returns that receipt's field texts; the old `.last()` +
  one-shot `innerText` is gone (`newestReceipt` removed).
- "no answer's receipt names X" first calls `receiptOfLastMessage`, so it cannot pass before the
  answer's receipt rendered, then checks every receipt model field in the conversation.
- Why no false result: an earlier turn's receipt cannot stand in for the new one, and a negative
  check needs the new receipt to exist first.

## Why M1 and M2 still fail

- M1 (`m1-receipt-from-request.patch`: receipt `served_model` = requested model with the provider
  segment stripped, provider still `served_provider`). In "The receipt names the model the provider
  reported…", M1 renders `bdd-provider-b/claude-5-haiku`. `names the serving model
  "claude-5-haiku-20261101" on "bdd-provider-b"` requires the served model to be exactly
  `claude-5-haiku-20261101` after removing only `bdd-provider-b/`; `claude-5-haiku` fails. The next
  step would fail too (last segment equals `claude-5-haiku`). The prefix rule cannot make M1 pass:
  M1's served model has no extra prefix to remove, and the comparison stays exact. In the health
  scenarios requested == served, so M1 is not distinguishable there, as before.
- M2 (`m2-receipt-time-from-send.patch`: `since` = admission time). The since-time comparison
  (`parseClock`, `clockInsideWindow`, 2 s tolerance, 5.25 s wait) is unchanged; only the source of the
  text changed (the `answer-receipt-since` field of the tied receipt instead of `.last()`). M2 still
  renders a since time, so the step is reached and fails on the time window, as before.
