## Rules applied (task summary)

- Vercel React Best Practices: `rerender-derived-state` (`useProviderMetaField` returns one primitive; no hook
  returns a derived object per render), `rerender-split-combined-hooks` (separate hooks for models, providers,
  meta, load state), `rerender-defer-reads` (actions read the graph with `getState` inside the action, never
  through a subscription), `bundle-barrel-imports` (domain reached only through the existing
  `@/platform/entities` entry; the raw store is not re-exported through the domain), `js-set-map-lookups` and
  `js-index-maps` (ingestion builds id sets and per-provider maps once per payload).
- Vercel Composition Patterns: `state-decouple-implementation` and `state-context-interface` (components see
  hooks and actions, not the store or transport; transport, projection, ingestion and action are separate modules).
- Prometheus Entity Management and the project rule: Provider, ProviderMeta and Model are graph entities reached
  through typed domain hooks; one `batchGraphWrites` per payload (precedent `teams/commands.ts:63`); no per-row
  writes; transports own I/O and are only called by the load actions; zustand keeps only workflow state
  (`refreshing`, `saving`, `busyModelKey`, `error`, health flags). `pem-local-first`: its "transport reads the
  local store" rule is for synced entities; the catalog is server-fetched, so the domain registers schemas but no
  entity transport (same choice as `teams`), and the load actions are the only ingestion path.

## Error type shapes

`SystemDefaultModelError extends Error` (the only error the two actions throw; the system default is unchanged
whenever it is thrown):

```ts
kind: "invalid_selection" | "provider_fetch_failed" | "provider_not_found" | "provider_disabled"
    | "revision_conflict" | "model_save_failed" | "default_route_failed"
stage: "fetch_provider" | "save_model" | "set_default"
providerId: string; modelId: string | null
status: number | null     // HTTP status of the failing call
detail: string | null     // server `error` text verbatim
modelSaved: boolean       // provider default_model write succeeded, then the route failed
refetched: boolean        // revision_conflict: provider registry reloaded
message: string           // starts "Model saved, system default not changed." or "System default not changed."
```

Mapping: update 404 or route 404 -> `provider_not_found`; route 409 -> `provider_disabled` (also raised before any
write when the fetched provider has `enabled === false`, so the model is not saved for a provider the route will
refuse); update 409 `TEAM_REVISION_CONFLICT` -> `revision_conflict` plus a registry reload, picker stays open;
other update failure -> `model_save_failed` (no route call issued); other route failure -> `default_route_failed`.
After a route failure that followed a successful model write the registry is reloaded best-effort so
`ProviderMeta` shows the server's truth.

`ModelCatalogIngestionError` (`code`: `invalid_payload | invalid_record | missing_provider_id | missing_model_id`)
is thrown by projection and ingestion before any write. `ProviderApiError` (`status`, `detail`, message text
unchanged: `Update provider failed: 409`) is what the transport throws.

## Behavior changes to know about

- The Models-page star now changes the SYSTEM default (provider and model), per S1 1.6; it used to save only the
  provider's `default_model`.
- `ProviderMeta` is no longer written optimistically. UI that wants a pending state keeps it locally.
- `setSystemDefaultProvider` on a provider with no `default_model` still calls the route (as before) and
  publishes `default_model: null`, so the status reads "unavailable" truthfully.
- A load whose response arrives after a newer load started, or after a default change was published, is dropped
  silently (it resolves without ingesting).
