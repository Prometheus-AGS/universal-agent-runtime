## PICK 1.1: how the virtualizer attaches (Base UI 1.9.0, read from source)

- `Combobox.Root virtualized` (source: `combobox/root/AriaCombobox.mjs`, `store.mjs:72`). When set, `ComboboxList`
  skips `CompositeList` registration (`list/ComboboxList.mjs:95`) and `ComboboxItem` registers itself in
  `store.context.listRef[index]` (`item/ComboboxItem.mjs:58-67`). An item without an `index` prop derives it from
  `flatFilteredValues` (`ComboboxItemVirtualizedIndex`, `:185-200`); this change passes an explicit `index` (the
  option's position among options only), which the d.ts documents as the cheaper path (`ComboboxItem.d.ts:32-34`).
- `virtualized` must be stable for an item's lifetime (the two branches are different component types,
  `ComboboxItem.mjs:209-225`). It is derived from the total option count, never from the filtered count.
- The scroll element is the `ComboboxList` div (it already owns `overflow-y-auto` and `max-h`). The virtualizer is
  `useVirtualizer` from `@tanstack/react-virtual` 3.14.23 (pinned in `frontend/package.json`) inside
  `VirtualPickerList`; `getScrollElement` returns the parent of an inner sized div (callback ref). Rows are
  absolutely positioned (`translateY`), fixed 36px options and 28px group headings, `overscan: 8`,
  `initialRect` fallback for jsdom (same pattern as `features/chat/ui/run-trace-timeline.tsx:2,119-132`).
- Group headings are presentational rows (`role="presentation"`), not `Combobox.Group`, because Base UI groups
  cannot be windowed. Items carry `aria-setsize` and `aria-posinset`.
- Keyboard highlight scrolls into view through `Root.onItemHighlighted` (reason `keyboard` or `none`, not
  `pointer`) which calls `virtualizer.scrollToIndex(rowIndex, {align: "auto"})`; the option index is found by
  value in the flat filtered list rather than from `details.index`. Opening scrolls to the stored value; a new
  query scrolls to the top.
- Filtering is external: `filter={null}` and `filteredItems` (flat or grouped), so the same filtered array feeds
  the count, the list and the virtualizer. Search is case-insensitive substring over display name, raw id, `detail`
  and `searchText`; the group heading (provider name) is NOT searched, so `gpt` over `nano-gpt` is 54, not 597.

## SET 2.2 and the lead's extra scope (hidden properties never sent)

`generic-schema-panel.tsx`: a property with `x-uar-ui-hidden: true` (type also carries `x-uar-ui-reason`) is filtered out
of the rows, so it is not rendered, does not count in the subtitle, and does not enable Save. Every `setSetting`
call from the panel (control change and Reset) goes through a guard that ignores a key not in the visible set, so
the panel can never create a draft for a hidden key. `llm.model` and `llm.default_provider` are therefore never
added to the dirty set by this panel.

The save payload itself is built OUTSIDE files I own, from the module draft cache, with no filter:
- `frontend/src/features/settings/model/use-settings.ts` `saveAll` (~line 96-100): `getDirty(namespace)` ->
  `saveNamespace(namespace, submitted.values)`
- `frontend/src/features/settings/model/settings-store.ts` `save` (~line 108-114): `Object.entries(values)` -> `putSettingsNamespace`

Residual risk, named: the schema comes from `useSettingsTypesMeta`. Until it has loaded the panel cannot know a
property is hidden, so for that moment a hidden row can render and be edited, and a draft made then would survive
into the payload. If that matters, the owner of `use-settings.ts` should drop keys the schema marks hidden inside
`saveAll`, or the panel should render rows only after the type meta has loaded. I did not edit either file.
No other code in `frontend/src` references `llm.model` or `llm.default_provider` as a draft key (searched).
