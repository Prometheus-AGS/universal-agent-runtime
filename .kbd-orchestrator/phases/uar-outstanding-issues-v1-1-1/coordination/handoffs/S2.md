# S2 source handoff — durable ingestion admission and recovery guidance

Changed paths:

- `src/uar/api/knowledge.rs`
- `src/uar/rag/ingestion_worker.rs`
- `docs/operations/durable-ingestion.md`
- `docs/operations/knowledge-principal-isolation.md`

`upload_document` captures `PersistenceLayer::durable_store_eligibility()` at
request admission and returns the existing `503 Durable ingestion storage is
unavailable` before the knowledge-base lookup, multipart reads, document
construction, source write, or job write when the captured category does not
permit durable work. It retains the existing durable-ingestion support check as
the compatibility gate. The dispatcher uses the same captured category before
starting its durable loop, so an unattested remote store does not begin
background discovery.

The HTTP response body and accepted-upload `202` contract did not change. A
`202` still means the selected namespace committed source, document, and job;
uncertain transport outcomes remain reconciled by owner-scoped inventory before
resubmission.

The operations documentation now gives the authenticated reupload sequence and
states that legacy rows are retained, never adopted based on matching text.
It records the only recovery authorities: authenticated joined quiesce/reclaim
and qualified trusted-supervisor exclusion. Both leave active effects and
accounting for reconciliation. It rejects force, timeout, deletion, Pod
absence, and replica count as substitute evidence.

No test, build, formatter, lint, import probe, schema validation, or review
ran. HTTP admission ordering, dispatcher behavior, restart, retrieval, and
recovery controls remain unverified until the full phase gate.
