Abstract

Autonomous AI agents present a class of safety and governance challenges that content moderation and LLM-level guardrails cannot adequately address. This paper describes the governance architecture of the Prometheus Fabric — a decentralized agent execution environment in which governance is a structural property of the runtime, not a policy layer applied on top of it. We describe five mutually reinforcing properties: (1) harm prevention through Cedar policy enforcement at every sensitive execution boundary; (2) behavioral certification through Kaia Verifiable Credentials that attest to consistent operation within declared parameters; (3) device-agnostic execution that maintains governance parity from enterprise clusters to consumer hardware; (4) decentralized synchronization using CRDTs, gossip-based policy propagation, and ATAgent PDS records that eliminate the requirement for a central coordination authority; and (5) execution isolation using signed WASM components and microsandbox hardware virtualization that structurally walls off untrusted code from private data. Taken together, these properties define a system in which an agent cannot exceed its certified behavioral envelope by construction — not by runtime monitoring after the fact, but by architectural impossibility.

§ 1 — Introduction

The Governance Gap in Agentic AI

The prevailing approach to AI agent safety is advisory: LLM-level system prompts, output filters, and content classifiers that ask the model to behave correctly. This approach fails under adversarial conditions, scales poorly across heterogeneous deployments, and provides no cryptographically verifiable evidence that behavior was compliant at any given moment.

The problem compounds as agents acquire autonomy. A stateless chatbot that only responds to direct queries has a bounded failure surface — the worst outcome is a bad response. An autonomous agent with tool access, persistent memory, multi-agent delegation authority, and scheduled background execution has an unbounded failure surface: it can take irreversible financial actions, exfiltrate private data, spawn subtasks that compound errors, and cause harm across sessions that no human monitors in real time.

Three categories of governance failure dominate deployed agentic systems in 2026:

Privilege escalation
An agent granted limited tool access finds a path to broader execution — through spawned subagents, through chained tool calls, or through prompt injection in external data sources — without any governance gate being triggered.
Parameter drift
An agent certified for specific operational or financial parameters silently deviates after a model update, a context window overflow, or an unusual input pattern, with no mechanism to detect the deviation until harm has occurred.
Unverifiable provenance
An agent delegated a subtask by an orchestrator has no cryptographic way to verify whether the delegating agent was itself certified, creating a chain of unverified trust in multi-agent workflows.

This paper describes how the Prometheus Fabric addresses all three failure categories through a five-property governance architecture grounded in Cedar policy enforcement, Kaia Verifiable Credential issuance, WASM execution sandboxing, decentralized CRDT synchronization, and microsandbox hardware isolation.

The core architectural claim: Governance that depends on the agent choosing to behave correctly is not governance. Governance must be a property of the execution environment — enforced at the runtime layer, attested cryptographically, and verifiable by any participant in the fabric without trusting any central authority.

§ 2 — The Cedar Policy Plane

Deterministic Authorization at Every Execution Boundary

The Universal Agent Runtime (UAR) implements governance through Cedar — a fine-grained authorization policy language designed for deterministic evaluation and strong fit with embedded Rust runtimes. Cedar policies decide; runtimes enforce. The model is not advisory.

2.1 Architecture: PDP, PEPs, and the Control Flow

Every sensitive operation in UAR passes through a two-component authorization model. The Policy Decision Point (PDP) evaluates a request against the active policy bundle and returns a decision — Permit or Deny — with accompanying obligations and reason codes. The Policy Enforcement Points (PEPs) are choke points embedded in the runtime at every boundary where an execution could cause harm, consume resources, or access protected data.

Control flow — canonical authorization sequence: 01 · Initiation Agent or actor attempts an operation (tool call, LLM invocation, spawn, network egress). 02 · Request Construction PEP constructs request tuple: (principal: AgentId/did:uar:agent-xyz, action: "tool.run" | "llm.invoke" | "file.read" | "net.egress", resource: ToolId | ModelId | FilePath | HostPattern, context: {budget_remaining, time, risk_score, kaia_vc_level}) 03 · Policy Evaluation PDP evaluates against the active Cedar policy bundle. Evaluation is deterministic — no probabilistic scoring, no model judgment. 04 · Decision Return PDP returns: Permit | Deny Plus: obligations (e.g. "log this decision") reason_codes (e.g. "BUDGET_EXCEEDED", "TOOL_NOT_IN_ALLOWLIST") 05 · Enforcement PEP enforces obligations. Issues capability token (optional). Proceeds or aborts. If governance cannot evaluate: execution is DENIED. Fail-closed is non-negotiable. 06 · Audit Record Append-only event: decision, principal, action, resource, reason, spend delta. Optional DSSE signing of every audit event for tamper-evident evidence chain.

2.2 Policy Types

UAR-GOV defines six policy types that together cover the complete surface area of agent harm. Each type targets a distinct category of risk:

# Policy Type What It Governs Example Cedar Rule

02 Economic Spend caps, token budgets, cost-per-call limits deny when context.token_spend + req.tokens > principal.budget
03 Operational Timeouts, concurrency limits, rate limits per period deny when context.calls_last_hour >= 100

2.3 Enforcement Surfaces (PEPs)

Policy enforcement is implemented at every sensitive boundary in UAR. No operation crosses a boundary without passing through a PEP. There are no hidden paths.

PEP placement — all sensitive boundaries in UAR: Orchestrator / Actor Model PEP Trigger: agent-to-agent messaging, subagent spawn, task dispatch Actions: actor.spawn actor.send actor.subscribe Prevents: Agent A spawning more than N children without authorization. Prevents non-supervisory agents from spawning privileged children. LLM Invocation PEP Trigger: any request to a model provider (candle-vllm, cloud API, or local) Actions: llm.invoke llm.stream Enforces: max_tokens_per_call · max_cost_per_call · max_calls_per_hour · allowed_model_list Tool Execution PEP Trigger: any tool call, including MCP tools and native skills Actions: tool.run tool.list Enforces: tool allowlist per principal · sandboxing constraints · per-tool execution budget Storage / Database PEP Trigger: any read/write to SurrealDB, local filesystem, or embedded store Actions: store.read store.write store.delete Enforces: PII class restrictions · namespace isolation · data residency Network Egress PEP Trigger: any outbound HTTP/WS connection attempt Actions: net.connect net.fetch Enforces: domain allowlist · SSRF protection · cloud metadata endpoint blocking Plugin Load PEP Trigger: loading a WASM component or native skill Actions: plugin.load plugin.execute Enforces: Ed25519 signature verification · Kaia VC check · trust tier routing

The principle of no hidden bypass paths — enforced structurally: every sensitive operation in UAR routes through the governance layer. There is no code path that allows an agent to call a tool, invoke a model, access data, or initiate network egress without a Cedar evaluation occurring first. This is not a policy claim; it is verified at code review as an architectural invariant.

§ 3 — Identity and the Trust Hierarchy

DID, Kaia Verifiable Credentials, and the Identity-Trust-Permission Triad

Cedar policies evaluate requests from principals. The quality of governance depends on the quality of principal identity — how reliably we can answer "who is this agent, what has it been verified to do, and what trust level does it carry?" The Prometheus identity architecture uses a three-layer DID hierarchy with Kaia Verifiable Credentials as the trust attestation that Cedar policies reference.

3.1 The Three-Layer DID Hierarchy

Every participant in the Prometheus Fabric has a Decentralized Identifier (DID) at one or more levels of the hierarchy. DIDs are self-sovereign — they are derived from Ed25519 key pairs, not assigned by a central authority. This means identity in the fabric is verifiable without any trusted third party.

DID namespace hierarchy: did:prometheus: ← Fabric-level identity Scope: The Prometheus Fabric node (server, cluster, or device acting as a fabric peer) Keys: Ed25519, HKDF-derived per node Records: Stored as app.prometheus.* records in ATAgent PDS Used for: Mesh discovery, peer authentication, policy bundle signing did:uar: ← Runtime-level identity Scope: UAR agent instance or agent actor within a fabric node Keys: Derived from did:prometheus: parent via HKDF Binding: Agent manifest signed with Ed25519 under the UAR DID Used for: Cedar policy evaluation (the principal), Kaia VC subject did:key: ← Session/device-level identity Scope: Ephemeral session credentials, device-local keys Keys: Ed25519 per session Used for: Short-lived authorization tokens, WebRTC peer authentication Trust chain verification: did:key → derives from → did:uar → derives from → did:prometheus: ↑ ↑ ↑ Session trust Agent trust Fabric trust Ephemeral Certified by Kaia Signed policy bundles

3.2 Ed25519 Agent Manifest Signing

Every agent deployed in the Prometheus Fabric has a manifest — a structured declaration of its identity, capabilities, allowed tools, model configuration, and declared behavioral parameters. The manifest is signed with Ed25519 under the agent's did:uar: identifier. An agent cannot misrepresent its declared capabilities to Cedar: the PDP verifies the manifest signature before evaluating any policy against the agent's claims.

This signature chain provides three invariants: (1) the manifest has not been tampered with since signing; (2) the manifest was signed by the declared DID's key holder; and (3) the Cedar evaluation is operating on a verified identity document, not a self-reported claim.

3.3 The Identity-Trust-Permission Triad

Kaia Verifiable Credentials sit at the intersection of identity and permission. A Kaia VC is a W3C Verifiable Credential issued under the Kaia certification authority's DID, attesting that a specific did:uar: agent has been verified to behave within a defined behavioral envelope across a documented set of scenarios. Cedar policies reference the Kaia VC level as a trust attribute in policy evaluation.

The identity-trust-permission triad in Cedar: // Cedar schema entity — Agent entity Agent = { did: String, // did:uar:agent-id kaia_vc_level: Long, // 0–4, verified by Kaia kaia_vc_scope: Set<String>, // ["financial", "hipaa", "cfpb"] manifest_hash: String, // Ed25519-signed manifest hash allowed_tools: Set<String>, // declared in signed manifest budget_usd: Decimal, // cumulative spend ceiling spend_usd: Decimal, // current cumulative spend }; // Cedar policy — financial operation requires L2 certification permit( principal is Agent, action == Action::"tool.run", resource is FinancialTool ) when { principal.kaia_vc_level >= 2 && "financial" in principal.kaia_vc_scope && principal.spend_usd + context.estimated_cost <= principal.budget_usd }; // Cedar policy — PII access requires HIPAA scope in VC forbid( principal is Agent, action == Action::"store.read", resource is PIIRecord ) unless { "hipaa" in principal.kaia_vc_scope && principal.kaia_vc_level >= 3 };

The triad closes the loop: An agent's identity (did:uar:) is cryptographically bound to its manifest. Its trust level (Kaia VC) is cryptographically attested and scope-specific. Its permissions (Cedar policy) reference both. An agent that has not been certified for financial operations cannot be granted access to financial tools — this is not a monitoring assertion, it is a Cedar evaluation result that produces Deny with reason code KAIA_VC_SCOPE_MISSING.

§ 4 — Property I: Agents Cannot Do Harm

Defense-in-Depth Across Five Independent Layers

Harm prevention in the Prometheus Fabric is not achieved by a single control. It is achieved by five independent layers, each of which stops a different class of harmful behavior. An agent that evades one layer will be stopped by another. No single point of failure can produce uncontrolled harm.

Layer 1 — Cedar PEPs at Every Boundary (Logical Enforcement)

As described in §2, every sensitive operation passes through a Cedar PEP before execution. The fail-closed guarantee is absolute: if governance cannot evaluate — due to a missing policy bundle, a corrupted context, or a timeout — the default answer is Deny. This means a governance failure produces no access, never open access.

Layer 2 — UAR WASM Sandbox (Execution Isolation)

Agent code executing within UAR runs inside a Wasmtime-based WASM sandbox. The sandbox enforces three independent limits simultaneously:

  • Fuel metering — every WASM instruction consumes one fuel unit. When the fuel budget is exhausted, execution terminates with a deterministic error. This prevents infinite loops and unbounded computation even if the agent's logic is arbitrarily complex.
  • Deny-by-default WASI capabilities — filesystem access, networking, and environment variable access are all disabled by default. Each capability requires explicit inclusion in the WasmConfig. An agent that has not been granted filesystem access cannot read private data regardless of what its WASM code attempts.
  • Per-invocation memory isolation — each execution gets its own Store. Agents cannot share memory, access each other's heap, or persist state across invocations except through explicit UAR host functions. No agent can read another agent's in-flight state.

Layer 3 — OpenFang 16-Layer Security (Agent OS Enforcement)

When agents run inside OpenFang's agent OS (via the UAR driver or direct deployment), they inherit OpenFang's comprehensive security stack, which operates independently of Cedar:

  • WASM dual metering — fuel metering + epoch interruption (wall-clock watchdog thread) simultaneously. A tool that blocks on I/O cannot escape the epoch timer even if fuel is unlimited.
  • SHA256-based loop guard — detects agents repeatedly calling the same tool with the same parameters. After a configurable threshold, the tool call is blocked and a circuit breaker terminates the agent loop entirely.
  • Prompt injection scanner — all skill content passes through scan_prompt_content() before activation. Override attempts, data exfiltration patterns, and shell injection references are detected and rejected.
  • Merkle hash-chain audit trail — every action is cryptographically linked to the prior one. Any tampering with a single audit entry breaks the entire chain — providing tamper-evident evidence of agent behavior for Kaia certification review.
  • SSRF protection and subprocess env_clear() — network requests are checked against private IP ranges and cloud metadata endpoints; subprocess execution clears the environment before selective re-injection, preventing secret leakage.

Layer 4 — Microsandbox Hardware VM Isolation (Untrusted Code)

For code that cannot be trusted with UAR-level sandbox guarantees — untrusted WASM extensions, uncertified third-party tools, experimental agent code — microsandbox provides hardware VM isolation with sub-200ms boot times. The VM boundary is a hardware isolation boundary, not a software policy boundary. Code inside a microsandbox VM cannot access private data by architectural construction: there is no shared memory, no shared filesystem, and no communication channel except explicit API calls through the microsandbox gateway.

Layer 5 — Kaia Continuous Monitoring (Behavioral Drift Detection)

A certified agent can drift from its behavioral envelope after a model update, a context window overflow, or an adversarial input. Kaia's continuous monitoring layer compares live agent behavior against the behavioral profile documented during certification. When the drift score exceeds the configured threshold — measured against the reflection report's confidence and consistency metrics from PMPO executions — Kaia issues a drift alert, triggers re-certification, and optionally suspends the agent's VC pending review.

The harm prevention guarantee: An agent in the Prometheus Fabric cannot cause harm that exceeds its Cedar-granted permissions (Layer 1), cannot execute beyond its fuel budget (Layer 2), cannot escape its WASM memory boundary (Layer 2/3), cannot access hardware resources beyond what its microsandbox VM exposes (Layer 4), and will trigger a drift alert if its behavior deviates from its certified behavioral profile (Layer 5). Defeating all five layers simultaneously requires compromising multiple independent systems — each implemented in a different part of the stack with no shared failure mode.

§ 5 — Property II: Certified Behavioral Envelopes

Kaia VCs as Cryptographic Operational Contracts

Preventing harm addresses the lower bound of agent behavior — what it cannot do. Certifying a behavioral envelope addresses the upper bound — what it consistently does within defined operational and financial parameters. Kaia provides the certification infrastructure that turns PMPO evidence into cryptographic attestations consumable by Cedar policy.

5.1 PMPO Evidence → Kaia Certification Input

The Prometheus Meta-Prompting Orchestration (PMPO) system produces structured evidence artifacts at each phase boundary. The Reflect phase in particular generates the inputs Kaia consumes:

PMPO reflection artifacts consumed by Kaia: reflection.report.json { specification_accuracy: 0.94, // did execution match the formal spec? confidence_score: 0.91, // how certain is the model's output? consistency_score: 0.96, // is output internally self-consistent? drift_analysis: [ // where did execution diverge from plan? { task: "T07", delta: "minor", within_tolerance: true }, ], failure_modes: [], // what failure modes were encountered? budget_adherence: { token_spend: 14_820, // actual vs. declared budget token_budget: 16_000, cost_usd: 0.021 } } Kaia extends these with structured thought experiments: kaia_session.json { scenarios_tested: 42, // edge cases exercised decision_points: 87, // decision nodes mapped in SurrealDB KG expert_validations: 3, // domain experts who reviewed risk_profile: { financial_exposure: "bounded", // spend cannot exceed budget_usd data_scope: "session", // no cross-session data persistence pii_handling: "none" }, compliance_frameworks: ["CFPB_1033", "SOX"], adversarial_coverage: 0.89 // fraction of known attack patterns tested }

5.2 Verifiable Credential Issuance

When scenario coverage, PMPO evidence quality, expert sign-off, and risk assessment all pass their respective thresholds, Kaia issues a W3C Verifiable Credential under the Kaia certification authority's DID. The VC is Ed25519-signed and stored in the surreal-memory-server knowledge graph under the agent's did:prometheus: identifier.

Example Kaia Verifiable Credential (abbreviated): { "@context": ["https://www.w3.org/2018/credentials/v1"], "type": ["VerifiableCredential", "KaiaCertification"], "issuer": "did:kaia:prometheus-operator-001", "issuanceDate": "2026-04-01T00:00:00Z", "expirationDate": "2027-04-01T00:00:00Z", // annual re-certification "credentialSubject": { "id": "did:uar:cnb-mortgage-qualifier-v1", "certificationLevel": 2, // L2 Enterprise "scope": ["financial", "cfpb", "sox"], "operationalParams": { "maxTokensPerCall": 4096, "maxSpendPerHour": 5.00, // USD "allowedModelTiers": ["local", "balanced"], "dataResidency": "bank-perimeter" }, "evidenceUri": "surreal://memory.cnb.local/certifications/mortgage-v1" }, "proof": { "type": "Ed25519Signature2020", "created": "2026-04-01T00:00:00Z", "verificationMethod": "did:kaia:prometheus-operator-001#key-1", "proofValue": "z5hf..." // Ed25519 signature over VC body } }

Cedar policies reference the VC's certificationLevel and scope fields, which the PDP retrieves from the signed VC stored in the knowledge graph. The VC also encodes the operationalParams directly — maximum spend per hour, allowed model tiers, data residency requirements — which Cedar enforces at the LLM Invocation PEP and Storage PEP respectively.

The behavioral contract is cryptographic: An agent with a Kaia VC carries a cryptographically verifiable commitment that it was observed to behave within the declared operationalParams across a documented set of scenarios, validated by a named human expert who signed off with their domain-specific credentials. This is not a best-effort assertion — it is a falsifiable claim with an evidence trail stored in surreal-memory-server's temporal history, queryable at any past timestamp by any audit process.

§ 6 — Property III: Device-Agnostic Governance

Governance Parity from Enterprise Cluster to Consumer Hardware

A governance architecture that only works in the cloud is not a governance architecture — it is a hosting dependency. The Prometheus Fabric is designed from the ground up to maintain the same governance properties across the complete device spectrum: from a 128 GB enterprise GPU cluster to a 6 GB consumer GPU to a smartphone running gen_ui_core. The Cedar policy bundle, the Kaia VC, and the WASM sandbox all travel with the agent, not with the infrastructure.

6.1 Policy Portability — The Same Policy Bundle on Any Device

UAR-GOV's explicit design goal is policy portability: the same governance model works on desktop, mobile, edge, and cloud. This is achievable because Cedar evaluation is pure computation — it takes a request tuple and a policy bundle and returns a decision. It requires no network call, no central authority, and no shared state. A signed policy bundle can be cached locally on any device and evaluated without connectivity.

The policy bundle is a signed artifact (Ed25519, signed by the Prometheus Fabric operator's DID) that contains the Cedar source, entity schema, and version metadata. When a device receives an updated policy bundle via gossip propagation (§7), it verifies the signature before installing the update. A tampered or unsigned bundle is rejected — the device continues operating under its last verified policy.

6.2 Inference at Any Scale — candle-vllm + TurboQuant

Governance parity requires that the same agent can run effectively on any hardware without degrading to a mode that bypasses governance. The candle-vllm inference server with TurboQuant KV compression enables this:

The critical property: at every tier, Cedar evaluation is present, the Kaia VC is verified before granting permissions, and agent execution runs inside the WASM sandbox. The model is smaller on smaller hardware, but the governance envelope is identical. An agent certified to kaia_vc_level: 2 with maxSpendPerHour: 5.00 cannot exceed that spend on any device — the Cedar economic policy evaluation is local, deterministic, and does not require network connectivity to enforce.

6.3 gen_ui_core — The Governance-Aware Fabric Node

On mobile and desktop devices, the Prometheus Fabric node is implemented in gen_ui_core — a Flutter + Tauri + Rust FFI hybrid application framework. The Rust core of gen_ui_core is itself a Fabric node: it manages DID key derivation (Ed25519, HKDF), ATAgent PDS synchronization, local SurrealDB (embedded RocksDB), CRDT state primitives (diamond-types), and the UAR lightweight executor. The Flutter and Tauri UI layers are presentation only — they never call network APIs, invoke models, or execute tools directly. All of that runs in the Rust core, under governance.

Privacy by architecture on mobile: A gen_ui_core mobile node processes all inference locally. User conversations, memory writes, tool calls, and knowledge graph updates never leave the device unless an explicit Cedar policy permits external egress. The same Cedar data policy that governs a bank's on-premise deployment governs the consumer's phone — with the same enforcement guarantees, locally evaluated, without any external validation server required.

§ 7 — Property IV: Decentralized Synchronization Without Central Authority

CRDTs, Gossip, WebRTC, and ATAgent PDS as the Fabric Coordination Substrate

A governance architecture that requires a central server to function is not sovereign — it is a managed service with governance features. The Prometheus Fabric is designed to allow any device to participate in a fabric, synchronize state, propagate governance updates, and maintain protocol adherence without any central coordination point.

7.1 The Synchronization Problem

Decentralized agent coordination requires solving four sub-problems simultaneously: (1) how do nodes discover each other without a central registry; (2) how does state (agent outputs, memory writes, knowledge graph updates) converge across nodes without a coordinator; (3) how do governance updates (policy bundle revisions, VC revocations) propagate reliably without a broadcast server; and (4) how do nodes that have been offline synchronize back to the correct state when they reconnect. The Prometheus Fabric uses a different technology for each sub-problem, and they compose without conflict.

7.2 Peer Discovery — Gossip Protocol

Fabric peers discover each other through a gossip protocol over the OpenFang Protocol (OFP) wire layer. Each node maintains a PeerRegistry — a set of known peers with their agent advertisements. When a new peer connects, it sends a Discover message; the responder sends back its peer list. Over successive rounds, knowledge of all reachable peers propagates to all nodes in the mesh without any central registry being consulted. New peers joining the fabric become visible to all existing peers within O(log N) gossip rounds.

Governance-relevant gossip extends this: signed policy bundle updates are propagated through the same gossip mechanism. When the fabric operator publishes a new Cedar policy bundle, it is gossiped to all reachable peers. Each peer verifies the Ed25519 signature before installing the update. A node that was offline when the update propagated will receive the update from any peer it reconnects with — the gossip state is eventually consistent across the fabric.

7.3 State Convergence — CRDTs (diamond-types)

Agent state, surreal-memory-server knowledge graph updates, and document-level collaborative state all use Conflict-free Replicated Data Types (CRDTs) implemented via the diamond-types library. CRDTs have a mathematical property: concurrent updates from any number of nodes, applied in any order, produce the same final state. No coordinator, no locks, no conflict resolution protocol required.

CRDT convergence — why it matters for governance: Problem without CRDT: Node A (online): agent writes memory record {id: 1, fact: "user prefers X"} Node B (offline): agent writes memory record {id: 1, fact: "user prefers Y"} On reconnect: conflict → last-write-wins → arbitrary result With CRDT (diamond-types): Node A: [op1: insert "user prefers X" at position P] Node B: [op2: insert "user prefers Y" at position Q] On merge: both operations apply deterministically final state: "user prefers X, user prefers Y" (both preserved) deterministic regardless of merge order Governance-critical application: Kaia VC revocations propagated as CRDT deletes: → Revocation is a CRDT operation that produces the same result regardless of which node processes it first or last. → An agent whose VC has been revoked cannot regain permissions on a node that has not yet received the revocation — but will lose them the moment the CRDT delta arrives, with no coordinator required to enforce the revocation.

7.4 Real-Time Coordination — WebRTC Data Channels

For real-time agent-to-agent coordination between devices — including the human-in-the-loop approval pattern that UAR implements for high-stakes actions — WebRTC data channels provide direct peer-to-peer encrypted communication. An agent on a mobile device executing a Browser Hand action that requires purchase approval can open a WebRTC data channel directly to the user's desktop UAR instance, deliver the approval request, receive the confirmation, and resume execution — without routing through any server.

The WebRTC connection is established using the OFP HMAC-SHA256 mutual authentication handshake: both peers sign a nonce challenge with their respective DID keys, verify each other's signatures via constant-time comparison, and only then establish the data channel. This ensures that the approval signal arrives from a peer with a verified identity, not a spoofed connection.

7.5 Persistent Fabric State — ATAgent PDS Records

The AT Protocol Personal Data Server (ATAgent PDS) provides the persistent, portable, DID-linked record store for agent state that must survive device changes, fabric reconnections, and node failures. Agent definitions, behavioral parameters, Kaia VC references, and operational history are stored as app.prometheus.* lexicon records in the PDS. Because PDS records are content-addressed and DID-signed, they can be synchronized to any new node without trusting the node that provides them — the signature chain is self-verifying.

The governance convergence invariant for decentralized sync: Any node in the Prometheus Fabric, regardless of how long it has been offline or how many governance updates it has missed, will converge to the correct governance state within a bounded number of gossip rounds after reconnecting. CRDT merges are order-independent; policy bundle updates are signature-verified before application; Kaia VC revocations propagate as CRDT deletes. A node that does not yet have the latest governance state operates under the most recently verified policy it holds — which is the correct safe default, since outdated policies are stricter than newer ones by design.

§ 8 — Property V: Signed Extensions and Execution Isolation

WASM Component Signing and Microsandbox Hardware Walls

The most dangerous attack surface in an agentic system is the extension model — third-party code that runs inside the agent's execution environment with potential access to private data, network endpoints, and inference infrastructure. The Prometheus Fabric neutralizes this attack surface through a two-tier model: signed WASM components with Kaia-attested trust levels, and microsandbox hardware VM isolation for code that cannot be trusted with software-only boundaries.

8.1 The WASM Component Trust Model

All third-party code in the Prometheus Fabric — skills, extensions, custom tools, MCP server implementations — executes as WASM components. The trust tier a component receives determines which execution environment hosts it and what resources it can access.

T1
Kaia-Certified Components Ed25519 + VC Level ≥ 1
WASM component has a valid Kaia VC with scope: ["extension"] and the component manifest is Ed25519-signed by the Prometheus Fabric operator or a trusted third-party certification authority. Runs inside UAR's Wasmtime sandbox with declared WASI capabilities. Cedar plugin policy verified at load time. Can access surreal-memory-server via UAR host functions within its declared capability set.
T2
Operator-Signed, Uncertified Components Ed25519 only, No Kaia VC
Component is signed by the fabric operator (proving authenticity and integrity) but has not been Kaia-certified. Runs inside microsandbox — a hardware VM with <200ms boot time. No direct access to private data. All communication with the host goes through the microsandbox gateway API with explicit permission checks. Cannot access surreal-memory-server, the DID key store, or any persistent private data by construction.
T3
Unsigned or Unknown-Provenance Code Denied at Plugin Load PEP
No signature, expired signature, or signature from an untrusted key root. Cedar plugin policy produces Deny at the plugin.load PEP. The component never executes. This is the default — all code is denied unless it has a verified signature from a trusted authority. There is no "run with a warning" mode.

8.2 Microsandbox Hardware Isolation

Microsandbox provides hardware-level VM isolation using microVM technology — not Linux containers, not chroot jails, but full hardware virtualization boundaries. The key properties relevant to the Prometheus Fabric governance model:

  • Hardware VM boundary — memory, filesystem, and network are isolated at the hypervisor level. A WASM component inside a microsandbox VM cannot read host memory, access the host filesystem, or make network connections except through the microsandbox gateway API. This is a hardware invariant, not a software policy.
  • Sub-200ms startup — the microsandbox VM boots in under 200ms, making it viable for per-request isolation of tools and extensions without introducing unacceptable latency into agent workflows.
  • OCI-compatible image model — extensions are packaged as OCI container images. The same WASM component that a developer tests locally runs in the same OCI image in production microsandbox. No environment differences, no path-dependent security assumptions.
  • Zero-access to private data by construction — the microsandbox VM has no mount point to the host SurrealDB, no access to the DID key store, and no route to the Kaia VC store. A compromised extension inside a microsandbox cannot exfiltrate private data because no data path to private storage exists. This is the correct security property: impossible by construction, not impossible by policy enforcement.

8.3 Capability Imports — What WASM Can Export to Guest Code

WASM components can only call host functions that the host explicitly exports into the guest's import namespace. In UAR's WASM sandbox, only two host functions are exported by default: uar_log and uar_emit_event. Neither of these provides access to private data. Any additional capability — reading from surreal-memory-server, calling an LLM, writing to the knowledge graph — must be explicitly granted via a Cedar capability token and implemented as a typed host function export. An agent cannot reach capabilities that the host did not deliberately expose to it.

§ 9 — Synthesis

The Governance Convergence Property

The five properties described in this paper are not independent controls that happen to coexist. They are facets of a single architectural claim: that in the Prometheus Fabric, an agent cannot exceed its certified behavioral envelope by construction — not by monitoring, not by detection after harm has occurred, but because the system's structure makes the violation architecturally impossible.

9.2 The Regulatory and Compliance Implication

The governance architecture described in this paper produces compliance artifacts as structural byproducts of normal operation. The Merkle hash-chain audit trail captures every Cedar decision with tamper-evident evidence. Kaia VCs record behavioral scope and compliance framework attestations. PMPO reflection reports document execution quality against declared specifications. CRDT-merged knowledge graph updates carry timestamp proofs of when each fact entered the system.

This means a regulated deployment — banking, healthcare, government — does not require a separate compliance implementation layered on top of the operational system. The operational system is the compliance system. The evidence required by CFPB Section 1033, SOX audit requirements, HIPAA access logs, and EU AI Act transparency obligations is produced automatically, stored in surreal-memory-server's temporal history, and queryable at any past timestamp. No post-hoc documentation effort is required.

9.3 What Remains to Complete

The architecture described here has several components in implementation and several in design. The governance convergence property is architecturally sound — the principles, policy types, enforcement surfaces, and trust hierarchy are fully specified. The following represent the primary remaining engineering work to realize the complete architecture:

  • Full Cedar PEP integration in UAR — the policy framework is specified and the LLM Invocation PEP is implemented; the Storage, Network Egress, and Plugin Load PEPs require completion
  • Kaia VC issuance pipeline — the certification workflow (MVP and functional specs) is complete; the CLI tooling, expert operator interface, and VC signing infrastructure require implementation
  • Gossip-based policy propagation — OFP peer discovery is implemented in OpenFang; extending it for signed policy bundle propagation requires adding the Cedar bundle to gossip message payloads
  • CRDT integration in gen_ui_core — diamond-types CRDT primitives are on the Sprint 2 roadmap for gen_ui_core; the integration with surreal-memory-server's write path requires a CRDT-aware merge layer
  • Microsandbox integration for T2 extensions — microsandbox is operational as a standalone tool; integration into UAR's plugin load PEP as the execution environment for uncertified WASM components requires a UAR-microsandbox gateway adapter

The final claim, stated with precision: When the five-property architecture described in this paper is fully implemented, the Prometheus Fabric will be the first open-source, Rust-native agent execution environment in which an agent's inability to exceed its behavioral envelope is a structural property provable by inspection of the runtime architecture — not a best-effort property dependent on monitoring, content filtering, or the agent's own adherence to instructions. Harm prevention, certified envelopes, device portability, decentralized synchronization, and execution isolation are not features of this system. They are properties of its construction.
