01 — The Problem

Why Single-Shot Prompting Fails at Scale

Every AI system that relies on informal prompting carries a structural deficit: the gap between human intent, model interpretation, and actual output is managed through luck and iteration rather than discipline and verification. PMPO is the methodology that closes that gap — permanently, repeatably, and with a measurable audit trail at every step.

Without PMPO
Generative with Hope
Human intent ↓ Single informal prompt ↓ Model output ← quality is luck ↓ Accept / retry ← no systematic path

No formal contract between intent and output. No acceptance criteria. No measurable quality. Each iteration is independent — the system learns nothing and guarantees nothing.

With PMPO
Engineered with Evidence
Human intent ↓ 01 · SPEC ← formal contract artifact ↓ 02 · PLAN ← DAG with acceptance criteria ↓ 03 · EXECUTE ← stepwise, checkpointed ↓ 04 · REFLECT ← measured against spec ↓ Kaia VC issuance ← cryptographic attestation

Every phase produces an immutable artifact. Every gate has acceptance criteria. Failure modes are explicit and remediation is structured. The output is provably aligned with the original specification.

The precise definition from the spec: PMPO is not "prompt engineering." It is a meta-orchestration methodology that treats documents as inputs to compilation, requires formal constraints and validation gates, produces actionable artifacts, and closes the loop with measured outcomes and structured improvement. The distinction matters — prompt engineering optimizes a single interaction; PMPO engineers the entire reasoning process.

02 — The Canonical Loop

Spec → Plan → Execute → Reflect

Each phase has strict typed inputs, a defined artifact that gates entry to the next phase, and explicit failure modes. Nothing proceeds without a completed prior artifact. This is what makes the pipeline deterministic — the same intent, processed through the same phase templates, produces the same artifact class every time.

Phase 01
Spec
Convert ambiguous human intent into a strict formal contract. Explicit success criteria, constraint mapping, assumption inventory, and dependency graph. No informal language survives this phase.
→ spec.draft.json
Phase 02
Plan
Decompose the specification into an ordered task DAG. Each task has typed inputs, the tool or routine it uses, acceptance checks, and failure modes with remediation hints.
→ task.graph.json
Phase 03
Execute
Run the plan against the artifact. For agent compilation: Cedar policy, validated schemas, MCP config, A2A endpoints, PEP bindings, signed runtime descriptor. Checkpointed and resumable.
→ execution.ledger.json
Phase 04
Reflect
Measure every output against acceptance criteria. Detect spec-to-runtime drift. Score confidence and consistency. Produce a compile report with reason codes and remediation that feed the next loop.
→ reflection.report.json

The cost routing insight: PMPO enables per-phase model selection. Spec and Plan phases are highly structured and can run on candle-vllm with near-zero marginal cost. Execute phases can be routed by task complexity — simpler tasks stay local, tasks requiring frontier reasoning go to Claude or GPT. Reflect phases use the best available model because quality judgment is the highest-stakes step. The total inference cost for a PMPO pipeline is a fraction of running every phase on a frontier API, without quality degradation where it matters.

03 — Skills Architecture

Domain Intelligence as Compressed Context

A skill is not a tool and it is not a prompt. It is a compressed domain expert — a structured representation of what an expert knows about a domain, encoded in a form the model can use at every inference call without explicit prompting. The three-layer cognitive model from the rust-skills meta-cognition framework describes exactly how skills shape model reasoning.

The Three-Layer Cognitive Model

L3
Domain Constraints — WHY Spec Phase Input
Business rules, regulatory requirements, domain invariants, SLAs. This is what PMPO's Spec phase formalizes. When a skill encodes Layer 3 knowledge — "financial transactions must be immutable audit records," "banking agents must not persist PII beyond session scope" — the model reasons correctly about the domain from the first token, without needing the constraints re-stated in every prompt. This is the layer where KDD operates: domain experts encode their constraints directly, eliminating the translation loss of passing requirements through intermediaries.
↓ domain constraints shape design choices
L2
Design Choices — WHAT Plan Phase Output
Architecture patterns, DDD concepts, API design, trade-off decisions, mental models. This is what PMPO's Plan phase produces — the task DAG encodes design choices at the graph level. A skill that encodes Layer 2 knowledge ("use Arc<T> for shared immutable references in concurrent financial record systems, not Clone") prevents the model from making structurally correct but architecturally wrong choices. The skill eliminates an entire class of design errors before the Execute phase begins.
↓ design choices select mechanics
L1
Language Mechanics — HOW Execute Phase Context
Ownership, borrowing, lifetimes, type system, compiler rules, runtime behavior. This is the implementation layer — the HOW. A skill that encodes Layer 1 knowledge for a specific crate or framework (how SurrealDB 3.x patterns work, how Axum 0.8 route composition behaves, how Riverpod 2.6+ codegen annotations are structured) eliminates lookup latency and reduces the model's surface area for incorrect API usage. In the Prometheus stack this maps directly to codebase-specific skill files that encode the exact patterns required for each sub-system.

The critical insight: Most AI development mistakes happen at the L3→L2 boundary — domain constraints are not correctly translated into design choices — or the L2→L1 boundary — correct design choices are implemented with mechanically wrong code. Skills that explicitly encode these boundaries prevent class-level errors rather than instance-level errors. A SKILL.md that encodes 10,000 tokens of domain expertise compresses into structured context that guides every inference call, without consuming those tokens on each request.

Skills Across the Three Stack Layers

OpenFang — Agent OS Level
60 bundled + FangHub + ClawHub

SKILL.md files compiled into the OpenFang binary. Domain expertise injected into the system prompt at agent spawn. Each agent in the kernel receives the full skill context for its declared specialization. For Prometheus-specific agents: custom SKILL.md files encoding UAR architecture patterns, SurrealDB 3.x idioms, Axum 0.8 conventions, and the KDD methodology itself.

UAR — Runtime Level
Native skills + MCP tool skills

UAR's NativeSkillRegistry runs Rust skill implementations in-process — bypassing MCP serialization for hot-path operations. surreal-memory-server's 42 tools function as a memory skill layer: every agent has access to the full knowledge graph as a structured skill context that updates in real time across sessions.

candle-vllm — Inference Level
MCP-injected tool skills

Memory tools injected at the inference layer via candle-vllm's MCP client. A model that doesn't know it is inside an agent framework still has access to the surreal-memory-server knowledge graph as tool-callable context. This is the deepest layer: skill access as infrastructure, not middleware. Available on every raw API call, regardless of what is above it.

05 — Kaia

Closing the Correctness Loop

PMPO's Reflect phase produces evidence. Kaia consumes that evidence, extends it through collaborative thought experiments and systematic edge case analysis, and issues cryptographically signed Verifiable Credentials that attest to agent behavior. This is the difference between an agent that was built carefully and an agent that is provably correct within a defined behavioral envelope.

The VC in the Prometheus Fabric

A Kaia-issued VC stored under did:prometheus: is not just a certificate — it is a trust assertion that any agent in the Prometheus Fabric can verify before accepting a delegation. When an orchestrator agent delegates a subtask to a specialist agent, it checks the specialist's VC level against the task's required certification. An uncertified agent cannot be delegated tasks that require L2 or above — enforcement is at the protocol layer, not the policy layer.

The KDD alignment: Kaia closes the KDD loop. Knowledge-Driven Development means domain experts drive the build process directly. Kaia means domain experts also certify the output directly — the same expert who encoded the L3 domain constraints in the SKILL.md is the one who signs off that the agent behaves correctly within those constraints. The translation loss that exists in every traditional software development process — intent → ticket → code → test → deploy — is replaced by a direct chain: intent → PMPO spec (expert-authored) → execution → Kaia certification (expert-signed). No intermediary at any step.

07 — Strategic Implications

What This Combination Makes Possible

Taken individually, PMPO, skills, and Kaia are each valuable. Together with the sovereign inference stack they produce a category of capability that does not exist in any competing framework: AI systems that are simultaneously cost-efficient, domain-accurate, and cryptographically verified.

  • Regulated industry deployment without compromise — A Kaia L2 certification with a full PMPO audit trail and zero external API dependency satisfies the data sovereignty, audit trail, and behavioral verification requirements of banking and healthcare regulators simultaneously. The system produces compliance artifacts as a natural byproduct of its execution, not as a post-hoc documentation effort.
  • The KDD moat — domain experts encode directly — When a domain expert encodes their constraints into a SKILL.md and validates the output through Kaia's thought experiment session, they have removed every intermediary from the build-and-verify loop. The traditional waste points — requirements translation, ticket decomposition, code review, QA — are replaced by a single expert-to-artifact pipeline that PMPO and Kaia make repeatable and verifiable.
  • Continuous quality improvement as a structural property — Each PMPO Reflect artifact is stored in surreal-memory-server. Each Kaia certification session extends the knowledge graph with verified decision points and edge case outcomes. Future executions query this history through hybrid search — the system literally learns from every past execution and certification, and that learning is available to every subsequent agent in the Prometheus Fabric.
  • The certified agent marketplace — A Kaia VC is a portable credential in the did:prometheus: namespace. A Prometheus AGS client who certifies an agent for their specific domain can publish that credential to a marketplace. Other clients in adjacent domains can discover and deploy pre-certified agents with known behavioral profiles — reducing their own certification cost by building on verified prior work.
  • Prompt drift as an engineering problem, not a mystery — When a model update changes agent behavior, PMPO's Reflect phase detects the spec-to-runtime drift with a measurable score. Kaia's continuous monitoring issues a drift alert. The VC validity can be time-limited to force recertification after model updates. Behavioral drift — the silent killer of production AI systems — becomes a trackable, measurable, addressable engineering problem.
  • OpenFang's Hands with certified knowledge — OpenFang's autonomous Hands (Researcher, Collector, Lead, Predictor) gain a new property when combined with PMPO and Kaia: their knowledge accumulation strategy can be certified. A Researcher Hand that has been Kaia-certified for financial intelligence research carries an attestation that its source evaluation, cross-referencing, and citation practices meet defined standards — turning autonomous Hands from powerful-but-opaque into powerful-and-trusted.

The structural correctness claim, stated precisely: When PMPO's four-phase pipeline enforces a formal contract at every execution boundary, skills encode domain expertise at all three cognitive layers, surreal-memory-server provides factual grounding and temporal history, TurboQuant expands the reasoning context available per GPU, and Kaia issues cryptographically signed behavioral attestations — the result is a system where correctness is not a property you test for after the fact. It is a property you engineer in from the first phase template through to the final VC. The question shifts from "did the AI do it right?" to "what does the certificate say?" — and the certificate is backed by evidence, not assertion.
