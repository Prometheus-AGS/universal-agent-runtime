# Native component input policy — revision 1

Status: source-authored for #467 and the full-set production-readiness phase. No current-image execution, governed tool execution, or architecture qualification is asserted. The first Linux amd64 API promotion excludes WASM/AOT execution certification.

`WasmSkillRuntime` accepts **plain WebAssembly component source** through the existing safe `Component::from_file` API. That API is the only component-loading path in this runtime. Registration validates and compiles source for the actual host architecture and the engine constructed by `WasmSkillRuntime::new` (`wasm_component_model(true)`, otherwise the resolved runtime defaults). It does not deserialize native machine-code caches. Existing plain-component invocation and per-invocation empty WASI/isolated kv-store behavior remain unchanged.

Every `.cwasm` path, including case variants and builtin paths, receives `native_component_untrusted` before the file is opened. The actionable remedy is to provide its original plain `.wasm` component and let this runtime compile it. Stale or other-version/other-target native caches receive the same refusal; this is not a claim to have inspected or diagnosed their serialization. A user-owned directory, an adjacent JSON manifest, an asserted hash, or a renamed file is never authority to deserialize native bytes. Renaming such bytes to `.wasm` uses the safe source loader and produces `invalid_component_source` if they are not a valid component. Incompatible or malformed plain source must be rebuilt from its declared WIT/source. There is no automatic download, fallback deserialization, or native-cache migration.

Discovery still scans `UAR_SKILLS_WASM_BUILTIN_DIR` and `UAR_SKILLS_USER_DIR`. Rejected inputs are logged and omitted from registration; discovery does not turn a failed component into a successful skill. Loading a component does not itself admit a governed tool invocation or grant filesystem/network capabilities. Existing Cedar, tool admission, approval and host-resource controls remain the responsibility of the existing governed execution boundary. This change does not create a new kernel or expose an arbitrary browser executor.

The image pins the Wasmtime CLI to **50.0.1**, matching both Wasmtime and Wasmtime-WASI in the current root `Cargo.lock`. The image stages the pinned skill pack's actual `skill.wasm` files as plain components under `/opt/uar/skills/wasm-builtin`. It no longer generates distributed `.cwasm` files with a different CLI or engine configuration. Plain components carry no host-native cache target/features contract: their compilation uses the actual runtime engine and host. The resident CLI is operator tooling, not a certified AOT loading lane. Any future native-cache distribution must establish a protected authoritative provenance path binding original source, native bytes, exact runtime/compiler, architecture and engine features before reconsidering deserialization. A mutable user manifest cannot supply that authority.

The existing reference component is `crates/prometheus-skill-system/skills/react/prometheus-entity-skills/entity-graph-optimize/skill.wasm`. Its Rust source, WIT, build script and dependency lock live alongside it under `component/`; the declared artifact hash is in the pinned submodule's `substrate/exec-tier-w/versions.toml`. That submodule's separate host/version profiles do not override UAR's engine or qualify UAR execution. The owned fixture copy and its provenance/oracles are in `tests/fixtures/production-readiness-wasm/`. Its expected empty-store output is four false orchestrator markers. Tests are authored for that real component, malformed plain source, untrusted cache with a self-asserted manifest, nonexistent/cache case variants and renamed native bytes. These cases have not run.

The uncomfortable limit: this runtime remains a source facility; finding its module and shipping a component do not establish a public governed execution route. The fixture's direct runtime invocation cannot certify Cedar/approval behavior, image installation, production resource limits, or AOT support. If a governed WASM lane is later promoted, its exact-image case must bind the actual source/component/image hashes, runtime/toolchain/features/target and tool policy, and prove both allowed results and denied effects. Until then that lane is explicitly unqualified/excluded in the [finite release checklist](../releases/v1.4.0-final.md), without excusing the fixed unsafe-loading and compiler mismatch defects.
