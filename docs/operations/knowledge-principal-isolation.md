# Knowledge ownership after principal isolation

Authenticated knowledge uses the complete verified credential principal key supplied by the host. Knowledge bases, documents, chunks and durable ingestion jobs use separate `principal_knowledge_*` tables in PostgreSQL and SurrealDB, and separate maps in process-local storage. Names, logical IDs and vector-search scope remain partitioned by that principal. A subject whose text resembles another principal key cannot adopt that principal's records.

The uncomfortable upgrade consequence is that preexisting authenticated knowledge remains in the legacy `knowledge_*` tables and is unavailable to authenticated requests after upgrade. There is no automatic ownership inference, copy, fallback or reassignment based on matching strings. Preserve the old data; a future explicit ownership migration needs independent authority evidence. A user can create a fresh base and reupload content through their authenticated API. Legacy anonymous knowledge remains available only through the host's explicit anonymous boundary. Nonanonymous unqualified owner strings are rejected by the adapter.

The PostgreSQL migration `20261013010000_principal_knowledge.sql` creates composite owner/resource primary and foreign keys, owner-scoped names, discovery indexes and the existing 384-dimensional vector layout. SurrealDB initialization includes `principal_knowledge.surql` through the shared ingestion migration path, including embedded existing-client startup. It creates independent tables and indexes without copying legacy rows. The existing API response models do not change. Server snapshot/poll paths use the owner-aware persistence interface and therefore select the new tables.

New authenticated ingestion jobs persist `namespace: "principal_v1"`. A missing marker means legacy, never authenticated, even if `owner_id` starts with `v1:k:`. Discovery selects authenticated jobs from the principal table and anonymous jobs from the legacy table. Source reads, transitions, preparation and publication enforce that provenance. Legacy nonanonymous jobs remain preserved and undispatched. Old anonymous serialization omits the default marker, preserving existing serialized compare-and-swap values. Acceptance, source retention, generation fencing and publication remain one transaction within the selected namespace. Deletion only revokes rows in that same namespace.

`tests/principal_knowledge_namespace.rs` authors actual SurrealKV, networked SurrealDB and PostgreSQL adapter scenarios with a canonical-looking legacy subject, same IDs in both namespaces, name/list/read/search isolation, source and job provenance, cross-tenant and cross-issuer reads/deletes, independent publication, anonymous compatibility and raw legacy preservation. Every backend runs seed, publish and cold-read stages in three joined child processes. SurrealDB receives one freshly generated namespace shared across those stages, leaving any application's namespace untouched. PostgreSQL requires a dedicated empty database with pgvector.

The network case requires `UAR_DOT12_SURREAL_URL` with a real `ws://`, `wss://`, `http://` or `https://` server endpoint. It is not ignored and has no memory/local fallback or missing-resource skip. Optional paired `UAR_DOT12_SURREAL_USER` and `UAR_DOT12_SURREAL_PASS` supply root credentials through the actual production adapter; absent credentials use that adapter's root/root defaults. The dedicated server must permit creation of the isolated namespace. This fixture does not introduce anonymous signin, alter authentication or manufacture a remote durability attestation. Operators must provision actual durable server storage; reconnecting clients alone does not certify server crash durability. The isolated namespace remains available for inspection after execution. PostgreSQL's existing ignored case requires `UAR_DOT12_POSTGRES_URL` and explicit inclusion in the final whole-target gate.

These fixtures are source only and have not run. The broader Dot phase implementation boundary must open before any verification, including these fixtures or migrations. This change makes no claim about LKE deployment or live cluster qualification.

The SurrealQL schema forms follow the pinned 3.3.0 repository contract and the [official table documentation](https://surrealdb.com/docs/surrealql/statements/define/table) and [index documentation](https://surrealdb.com/docs/surrealql/statements/define/indexes), consulted through Context7. No dependency versions changed.
