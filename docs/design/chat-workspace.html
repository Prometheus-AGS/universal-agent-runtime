MCP filesystem timeouts on staging

Window: last 500 log lines · Runs affected: 2 of 14

Finding

Both failures occurred during fs.list over the repository root with 2,400+ entries. The server responded after 71 s and 84 s; the runtime abandoned the call at 60 s.

Evidence

  • Log lines 212–260: listing … depth=∞ entries=2412 elapsed=71.3s
  • mcp.health passes because the probe reads one file.
  • staging/config.yaml inherits the runtime default timeout_secs: 60.

Proposal

  • Set a 120 s per-tool timeout for this server only.
  • Bound listings with max_listing_depth: 2.
  • Follow-up: teach the ops skill to pass a path filter.

Filesystem server limits

Per-server limits override the runtime defaults. Unbounded listings are the most common cause of tool timeouts; set a depth and an entry cap for large roots.

limits:
  max_listing_depth: 2
  max_entries: 1000
