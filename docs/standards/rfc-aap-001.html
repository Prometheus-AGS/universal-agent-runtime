Abstract

The Agent Artifact Protocol (AAP) defines the internal structure of agentic artifacts — the fundamental units of agent-produced, agent-consumable content operating within the Agent Publishing Protocol ecosystem. AAP replaces the fragmented "lexicon" approach with a unified artifact specification that integrates schema validation, declarative UI, event semantics, and invocation contracts into a single coherent definition document.

Schema-validated content with strict type enforcement
UI-renderable via declarative A2UI component bindings
Event-emitting with lifecycle-aware payload contracts
Invocation-capable through typed A2A operation contracts
Cryptographically signed for publication integrity
§ 1 — Overview

What Is an Artifact?

An artifact is the atomic unit of structured content within the AAP ecosystem. Unlike raw data or untyped messages, an artifact carries its own schema, rendering instructions, event surface, and operational contracts.

01
JSON Schema

Defines field types, validation constraints, and serialization format. Enforced before publication.

02
A2UI Definition

Declarative UI layout specifying component bindings, field mappings, and conditional rendering logic.

03
Event Definitions

Named lifecycle events with typed payloads conforming to the APP event envelope specification.

04
A2A Contracts

Schema-validated invocation operations enabling structured agent-to-agent capability calls.

05
Governance Metadata

Policy-bound access controls, rate limits, role requirements, and execution constraints.

§ 2 — Artifact Specification Document

Artifact Specification Document (ASD)

Every artifact type must be defined by an Artifact Specification Document. The ASD is the authoritative source of truth for schema, rendering, events, invocation contracts, and governance for that artifact type.

ASD — Top-Level Structure
{ "id": "com.prometheus.report", "version": "1.0.0", "schema": { /* JSON Schema definition */ }, "a2ui": { /* UI component bindings */ }, "events": { /* Event surface definitions */ }, "a2a": { /* Invocation operation contracts */ }, "governance": { /* Policy and access metadata */ } }
§ 3 — JSON Schema Section

Schema Definition

The schema section defines the data contract for the artifact. All fields, types, and validation constraints are declared here. Validation must occur before any artifact is published into APP.

required fields
Fields that must be present for the artifact to be considered valid
field types
Standard JSON Schema type annotations: string, number, boolean, object, array
constraints
Length limits, patterns, enumerations, and format validators
serialization
Canonical serialization format required for consistent hashing and signing
Example — com.prometheus.report schema
{ "type": "object", "properties": { "title": { "type": "string" }, "content": { "type": "string" }, "author": { "type": "string" } }, "required": ["title", "content"] }
R-3.1 Schema Validation Requirements ▶

All artifacts must pass schema validation prior to publication. Validation failures must be reported with field-level detail.

Schema validation MUST occur before publication
Failed artifacts MUST NOT be published to APP feeds
Validation errors SHOULD include field path and failure reason
Implementations MAY cache compiled schemas for performance
§ 4 — A2UI Section

Declarative UI Definition

The A2UI section specifies how the artifact is rendered. Rendering engines must treat A2UI as declarative instructions — not imperative code. Field bindings map artifact data to named UI components with defined display semantics.

component layout
Named layout strategy: vertical, horizontal, grid, or card
field bindings
Maps artifact data fields to named UI components (h1, markdown, table, etc.)
interactive controls
Optional controls: buttons, inputs, or triggers that invoke A2A operations
conditional logic
Show/hide rules based on field values or artifact state
Example — A2UI definition
{ "component": "ReportView", "layout": "vertical", "bindings": { "title": "h1", "content": "markdown" } }
§ 5 — Event Definitions

Artifact Event Surface

Artifacts may emit lifecycle events. All events must conform to the APP event envelope format and carry typed payloads. Events enable reactive agent coordination across the publishing graph.

Event Definition Structure
{ "artifact.created": { "payload": { "type": "object" } }, "artifact.updated": { "payload": { "type": "object" } } }
R-5.1 Event Envelope Conformance ▶

All artifact events must conform to the APP event envelope specification, ensuring consistent delivery semantics across the protocol stack.

Events MUST conform to APP event envelope format
Event payloads MUST be schema-validated before emission
Event names SHOULD follow dot-notation namespacing (e.g., artifact.created)
Artifacts MAY define custom event types beyond the standard lifecycle set
§ 6 — A2A Invocation Contracts

Agent-to-Agent Operations

The A2A section defines callable operations that other agents or systems may invoke on the artifact. Each operation declares its input schema, output schema, and streaming capability. All invocations must be schema-validated before execution.

A2A Operation Definition
{ "operations": { "summarize": { "inputSchema": {}, "outputSchema": {}, "streaming": true } } }
R-6.1 Invocation Validation ▶

All A2A operation invocations must pass schema validation on both input and output boundaries. Streaming operations must emit schema-conformant chunks.

Invocation inputs MUST be validated against inputSchema before execution
Operation outputs MUST conform to declared outputSchema
Streaming operations SHOULD emit progress events via the artifact event surface
Implementations MAY cache operation results for idempotent operations
§ 7 — Artifact Instance Structure

Instance Format

An artifact instance is a published, signed record conforming to the type's ASD. Instances carry a content-addressed identifier (CID), cryptographic signature, and author DID alongside the artifact data payload.

Artifact Instance
{ "uri": "app://did:example/artifact/123", "type": "com.prometheus.report", "version": "1.0.0", "data": { /* artifact payload conforming to schema */ }, "cid": "bafyrei...", "createdAt": "2025-01-01T00:00:00Z", "author": "did:plc:...", "signature": "..." }
uri
Globally unique artifact identifier within the APP namespace
type
Reverse-DNS ASD identifier. Must resolve to a valid Artifact Specification Document
cid
Content-addressed identifier for verifiable data integrity
signature
Cryptographic signature from the author DID keypair, required for publication
§ 8 — Versioning Rules

Schema Versioning

Artifact version must match its ASD version. Version management follows semantic conventions where breaking changes mandate a major version increment.

MAJOR

Required for any breaking schema changes — field removals, type changes, or altered required fields.

MINOR

Non-breaking UI updates, new optional fields, or additive A2UI binding changes.

§ 9 — Execution Semantics

Artifact Execution Modes

Artifacts span a capability spectrum from passive data containers to stateful executable systems. All execution occurs within the UAR sandbox environment.

Mode 01
Passive

Data-only artifacts. No event surface, no invocable operations. Pure structured content delivery.

Mode 02
Interactive

UI-driven artifacts with A2UI controls that surface user interactions within the rendering context.

Mode 03
Executable

Exposes A2A operations. Other agents may invoke defined capabilities against the artifact instance.

Mode 04
Stateful

Emits lifecycle events across its operational lifespan. Enables reactive coordination in multi-agent flows.

§ 10 — Governance Metadata

Policy & Access Controls

Governance metadata defines the policy surface for artifact execution. Governance engines evaluate all policies prior to any invocation. This section is evaluated by the UAR Cedar policy engine at runtime.

required roles
DID-based roles that must be present in the caller's credential set for invocation
access restrictions
Namespace or identity-scoped restrictions limiting artifact visibility or invocability
rate limits
Per-caller or global invocation rate constraints enforced at the UAR boundary
execution policies
Cedar-expressed policy trees evaluated before any A2A operation proceeds
§ 11 — Security Model

Security Requirements

The AAP security model enforces validation, signing, and sandboxing as non-negotiable properties. No artifact may bypass any of these controls.

R-11.1 Data Validation ▶
Artifact data MUST be schema-validated prior to any operation
Malformed artifact instances MUST be rejected at ingestion
R-11.2 Publication Signing ▶
A valid cryptographic signature MUST be present for publication
Signatures MUST be verified against the author DID's declared keys
Signature schemes SHOULD use EdDSA (Ed25519)
R-11.3 Sandboxed Execution ▶
All artifact execution MUST occur within UAR sandbox boundaries
Invocation inputs MUST be validated before execution begins
Sandbox escapes MUST trigger immediate termination and audit logging
§ 12 — Protocol Relationship

AAP + APP — Division of Responsibility

APP and AAP are complementary layers in the decentralized agent publishing stack. APP operates at the transport and distribution layer; AAP operates at the content and capability definition layer. APP transports AAP artifacts — it does not define them.

Protocol Responsibility
APP Publishing, feed inclusion, event streaming, session coordination
AAP Artifact schema, UI structure, invocation semantics, event type definitions
APP + AAP Together form the complete decentralized agent publishing and execution ecosystem
§ 13 — Summary

Protocol Summary

AAP — What It Unifies

The Agent Artifact Protocol defines the internal structure of agentic content. It provides a single, coherent specification surface that replaces fragmented lexicon definitions with a unified document combining schema, UI, invocation, and event semantics. Together with APP, it forms a complete decentralized agent publishing and execution ecosystem capable of supporting sovereign, policy-governed, multi-agent workflows at production scale.
