Universal Agent Runtime
Governance Architecture

UAR-GOV — Governance, authorization, safety & compliance controls across local-first, embedded, and cloud deployments.
Draft v1.0 Governance Authorization Safety Compliance
// 01

Goals

1.1 Primary Objectives

  1. 01Deterministic enforcement of who/what may do what, when, and within what limits.
  2. 02Defense-in-depth across orchestration, tool execution, storage, networking, and model invocation.
  3. 03Local-first viability — run fully embedded (single binary) with minimal overhead.
  4. 04Auditability & reproducibility — every decision is explainable and re-playable from logs.
  5. 05Policy portability — the same governance model works on desktop, mobile, edge, and cloud.

1.2 Non-Goals

  • Content moderation as the primary control plane (LLM-only guardrails are insufficient).
  • A full IAM replacement for enterprise IdPs — we integrate, not replace.
// 02

Core Principles

  1. 01Policies decide; runtimes enforce. LLMs do not grant privileges.
  2. 02Least privilege by default. All capabilities must be explicitly granted.
  3. 03No hidden bypass paths. Every sensitive operation routes through a governance gate.
  4. 04Separation of duties. Policy authorship, deployment, and runtime operation can be separated.
  5. 05Fail closed. If governance cannot evaluate, execution is denied — with safe degradation modes where configured.
// 03

Definitions

3.1 Entities

Entity
Principal
The requesting identity — agent, user, system actor, or integration.
Entity
Action
An operation being requested — e.g. llm.invoke, tool.run, file.read.
Entity
Resource
The object acted upon — model, tool, file path, database table, network target.
Entity
Context
Runtime facts used in evaluation — budgets, time, environment, risk score.

3.2 Capabilities

A capability is a structured permission token derived from policy decisions and bound to:

principal — the requesting identity
action(s) — permitted operations
resource(s) — objects the action may target
constraints — limits / quotas / time bounds
provenance — policy version + decision ID

3.3 Enforcement Points (PEPs)

Policy Enforcement Points are choke points in UAR where policy decisions are required before any execution may proceed.

// 04

High-Level Architecture

4.1 Components

  1. 01

    Policy Decision Point (PDP)

    Evaluates requests against policies. Produces Permit/Deny plus obligations.

  2. 02

    Policy Enforcement Points (PEPs)

    Implemented at all sensitive boundaries — orchestrator/actor mailbox, tool execution, model invocation, filesystem, database, network egress, and plugin loading.

  3. 03

    Policy Store

    Versioned, signed policy bundles. Supports local embedded storage and optional remote fetch.

  4. 04

    Context Providers

    Provide dynamic context — budgets, rate limits, device posture, tenant settings.

  5. 05

    Audit & Evidence Pipeline

    Append-only event stream. Optional DSSE signing of decisions and actions.

  6. 06

    Governance Admin Surface

    CLI/API to validate, publish, and roll back policies. Policy simulation and explain tooling.

4.2 Control Flow — Canonical

  1. 01
    InitiationActor or agent attempts an operation.
  2. 02
    Request ConstructionPEP constructs request tuple: (principal, action, resource, context).
  3. 03
    Policy EvaluationPDP evaluates against the active policy bundle.
  4. 04
    Decision ReturnPDP returns a decision (Permit | Deny), obligations, and reason codes for audit.
  5. 05
    EnforcementPEP enforces obligations, issues capability (optional), proceeds or aborts.
  6. 06
    Audit RecordPipeline records decision event, execution event, and resulting spend/usage deltas.
// 05

Policy Model

5.1 Policy Language

UAR governance supports one or both policy backends:

  • Cedar (recommended default) — Fine-grained authorization model with deterministic evaluation. Strong fit for embedded Rust runtimes.
  • Rust DSL (optional adjunct) — Used for ultra-low-latency hot-path constraints (e.g. micro-quotas). Must compile down to deterministic checks.

5.2 Policy Bundle

A policy bundle is a signed artifact containing:

  • Policy source
  • Schema (entities / actions / resources)
  • Version metadata
  • Signatures & trust roots

5.3 Policy Types

# Type Description
01Authorization policiesPermit or forbid access operations.
02Economic policiesBudgets, spend caps, token caps.
03Operational policiesTimeouts, concurrency, rate limits.
04Data policiesPII access constraints, data residency rules.
05Network policiesAllowlists and denylists for egress targets.
06Plugin policiesWhat native plugins may load and execute.
// 06

Enforcement Surfaces (PEPs)

Trigger — agent-to-agent messaging, task dispatch, spawning sub-agents

6.1 Orchestrator / Actor Model PEP

actor.spawn actor.send actor.subscribe
Prevents Agent A from spawning more than N children. Restricts certain message types to supervisory agents.
Trigger — any request to a model provider (local or remote)

6.2 LLM Invocation PEP

llm.invoke llm.stream
Enforces: max tokens per call · max cost per call · max calls per hour · allowed model list.
Trigger — any tool execution invocation

6.3 Tool Execution PEP

tool.run tool.list
Controls which tools are accessible to which principals. Enforces sandboxing constraints and execution budgets per-tool.
