§ 1 — Abstract
This RFC formally defines the standard specification format for agent definition within the Universal Agent Runtime. It describes the structure, semantics, validation rules, and compilation requirements for agent artifacts written in Markdown under the UAR-AGENT-MD schema. This RFC does not define runtime implementation details. It defines the specification standard that runtimes MUST follow.
The objective of this RFC is to:
Establish a stable, versioned specification contract for agent artifacts
Define deterministic compilation semantics
Formalize governance, UI, MCP, and A2A contract requirements
Enable interoperability across runtimes, registries, and tooling
§ 2 — Terminology

Key Words & Definitions

The key words below are interpreted as described in RFC 2119. This document uses the following terms with specific meaning throughout.

MUST MUST NOT REQUIRED SHALL SHALL NOT SHOULD SHOULD NOT MAY
Agent Artifact
A Markdown document conforming to the UAR-AGENT-MD schema.
Descriptor
The normalized, canonical JSON representation produced by compilation.
Compilation
The deterministic transformation of an Agent Artifact into a signed Descriptor.
Capability Surface
Any runtime boundary requiring policy enforcement: LLM, tool, file, net, plugin, A2A.
§ 3 – 4 — Goals & Non-Goals

Scope

This RFC establishes what the specification standard covers and explicitly what it does not. Boundaries are as important as requirements.

Goals
Provide a deterministic agent definition format
Enable governance-first execution via Cedar policies
Support declarative UI contracts (A2UI)
Support explicit MCP infrastructure dependencies
Support typed Agent-to-Agent contracts
Enable portable, local-first deployment
Non-Goals
Defining the internal architecture of UAR
Defining UI rendering implementations
Defining MCP protocol details
Replacing external IAM systems
§ 5 — Specification Structure

Required Artifact Structure

An Agent Artifact MUST contain the following top-level sections in Markdown. All sections are REQUIRED. A compliant runtime MUST reject any artifact missing a declared section.

# Agent: <name> ## Metadata — id, version, runtime, schema ## Identity — principal · Cedar entity mapping ## UI (A2UI) — artifacts · actions · schema IDs ## Capabilities — declared runtime surfaces ## Skills — id · entrypoint · required_tools ## Tools — id · type · MCP bindings ## MCP Servers — endpoint · auth · capabilities ## Knowledge Base — symbolic references · isolation ## Memory Model — isolation scope declaration ## A2A Contracts — typed endpoints · JSON Schema IO ## Governance — embedded Cedar policy ## Budgets & Constraints — explicit ceilings ## Execution Model — model type · concurrency · timeout ## Observability — audit requirements ## Deployment Profiles — environment overrides
§ 6 – 20 — Section Requirements

Per-Section Specification

Each section of the Agent Artifact carries explicit MUST, SHOULD, and MAY obligations. Expand any section to view its requirements. Compilation MUST fail on any MUST violation.

§ 06
Metadata
▶
The Metadata section MUST contain valid YAML frontmatter establishing the agent's identity and compatibility contract.
contain valid YAML frontmatter
declare id (string, globally unique)
declare version (semver)
declare runtime (compatibility constraint)
declare schema (UAR-AGENT-MD version)
if required fields are missing or incompatible
include owner, license, checksum, ui_schema_version
§ 07
Identity
▶
Identity defines the Cedar principal that governance policies evaluate against.
define a principal object mapping to governance entities
declare type and namespace at minimum
be compatible with Cedar entity schemas
§ 08
UI (A2UI)
▶
The A2UI section establishes the declarative UI contract that frontends resolve and render dynamically.
declare artifacts referencing versioned A2UI schema IDs
declare UI actions with JSON Schema input_schema and output_schema
verify all A2UI schemas resolve via registry (at compile time)
verify all schema references are valid JSON Schema
verify all UI actions bind to either skills or A2A endpoints
§ 09
Capabilities
▶
Capabilities are declarations only. Declaration is not permission.
declare all requested runtime surfaces
NOT imply permission (capabilities are declarations only)
have a corresponding governance evaluation path for each declared surface
§ 10
Skills
▶
Skills are the executable units referenced by UI actions and A2A contracts.
declare id, entrypoint, and required_tools
verify referenced tools exist (at compile time)
verify entrypoints are valid (compile-time or runtime resolvable)
§ 11
Tools
▶
Tools form the typed interface between skills and runtime capabilities.
explicitly declare id and type
match MCP capability references to declared MCP servers
declare additional constraints (models, domains)
§ 12
MCP Servers
▶
MCP server declarations establish explicit infrastructure dependencies. No implicit server access is permitted.
declare id, endpoint, authentication method, and supported capabilities
validate structural correctness at compile time
ensure tool-to-capability mapping integrity
if an undeclared MCP capability is referenced
§ 13
Knowledge & Memory
▶
Knowledge and memory declarations govern data access isolation at the tenant boundary.
use symbolic knowledge references (resolved at runtime)
define isolation scope in memory declarations
ensure no implicit cross-tenant access is possible
§ 14
A2A Contracts
▶
A2A contracts are the typed interfaces through which agents call and are called by other agents.
each endpoint declare id, input_schema, and output_schema
schemas be valid JSON Schema
register endpoints into the actor routing layer at compile time
enforce allowed callers via governance
§ 15
Governance
▶
Governance is not optional. Incomplete or invalid governance is a compilation failure, not a warning.
embed Cedar-compatible policy text
parse policy at compile time
type-check entity references
validate referenced actions and resources
ensure all sensitive capability surfaces have explicit policy coverage or explicit denial
if governance is incomplete or invalid
§ 16
Budgets & Constraints
▶
Budgets define explicit resource ceilings that are injected into governance evaluation context.
define explicit ceilings for all budgeted resources
ensure budgets do not exceed deployment maximums
inject budget context into governance evaluation
§ 17
Execution Model
▶
Execution configuration governs concurrency and timeout behavior for the agent's runtime lifecycle.
define model type (actor / supervised / etc.)
define concurrency limits
define timeout limits
on invalid execution model declaration
§ 18
Observability
▶
Observability requirements gate the logging pipeline at compile time.
specify audit requirements
ensure logging pipeline is enabled if audit is required
§ 19
Deployment Profiles
▶
Profiles allow environment-specific configuration overrides within declared constraint bounds.
merge profile settings deterministically
validate resulting configuration against constraints
override budgets and configuration
§ 20
Deterministic Compilation
▶
Determinism is a first-class requirement. Identical inputs MUST produce identical outputs.
be deterministic: identical input → identical descriptor hash
fail closed on any validation error
emit canonical JSON descriptor (stable field ordering)
emit signature over descriptor and referenced fingerprints
§ 21
Security Requirements
▶
Security requirements apply to any conforming runtime implementation. No implicit grants are permitted.
NOT permit implicit capability grants
NOT permit bypass paths around governance
NOT permit implicit network or file access
guard all capability surfaces with a PEP
§ 22 — Versioning

Versioning Policy

This specification SHALL follow semantic versioning. Breaking changes require a new schema version and explicit migration documentation. Tooling MUST surface version incompatibility as a compilation error, not a runtime warning.

§ 23 — Conformance

Conformance Criteria

A runtime implementation is compliant with this RFC if and only if all four criteria are satisfied. Partial conformance is not conformance.

✓
Accepts valid UAR-AGENT-MD documents without error
✓
Rejects invalid documents with structured error output
✓
Produces deterministic descriptors (same input → same hash)
✓
Enforces governance at all declared capability surfaces

§ 25 — Conclusion
A Compiler-Based Agent Operating System
This RFC formalizes the UAR Agent Definition Standard as a deterministic, governance-first, specification-driven artifact model. By codifying agent definition as a strict document standard with formal compilation semantics, UAR becomes a compiler-based agent operating system — not an ad-hoc framework. Implementations that conform to this RFC provide verifiable, auditable, and reproducible agent execution by design.
The agent definition is no longer configuration — it is a contract.
