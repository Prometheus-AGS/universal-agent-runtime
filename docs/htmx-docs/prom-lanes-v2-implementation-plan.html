Concurrent Agent Orchestration Engine

prom-lanes

A Rust library and CLI that treats agent concurrency as infrastructure — not just for code. Two orthogonal abstraction axes compose freely: WorkspaceProviders handle isolation (git worktrees, SurrealDB namespaces, Postgres schemas), while AgentBackends handle execution (CLI tools, the UAR runtime, and OpenAI Agents SDK). Any workspace × any backend. One engine.

00 · Problem & Thesis

Beyond Coding Assistants

The original prom-lanes solved concurrent AI coding sessions with git worktree isolation. That was the right starting point, but it was also a specific instance of a universal pattern: any parallel agent workload requires isolated workspaces, scoped task contracts, deterministic lifecycle management, and controlled result integration.

Data pipeline agents need the same discipline as coding agents — just with database namespaces instead of worktrees. Research agents need scoped document spaces. Analytics agents need schema-isolated query environments. The orchestration primitives (lanes, state machines, merge gates, event buses) are identical. Only the isolation substrate and the agent backend differ.

prom-lanes v2 factors the architecture along two orthogonal axes. WorkspaceProviders manage isolation — git, SurrealDB, Postgres, or plain directories. AgentBackends manage execution — CLI coding tools, the UAR runtime itself, or external platforms like OpenAI's Agents SDK. These compose freely: run an OpenAI agent against a SurrealDB workspace, or a Claude Code session in a git worktree, or a UAR agent instance in a Postgres-backed environment. The engine doesn't care. It manages lanes.

Architectural Insight
Workspace × Backend is the composition matrix. The engine orchestrates lanes. WorkspaceProviders answer "where does the agent work?" AgentBackends answer "who does the work?" Neither knows about the other. The lane ties them together.

Design Principles (Updated)

Principle 01
Workspace Agnosticism
The engine never assumes filesystem isolation. WorkspaceProvider trait abstracts create, snapshot, merge, and destroy across git, databases, and plain directories.
Principle 02
Backend Agnosticism
The engine never assumes a CLI process. AgentBackend trait covers CLI tools, HTTP API platforms, and in-process runtime invocations with a unified start/poll/stop interface.
Principle 03
Free Composition
Any workspace × any backend. The lane model binds them. The engine orchestrates the lifecycle. Neither axis knows about the other.
Principle 04
Workers Deliver, Leads Merge
No agent self-merges into shared state. Workers produce results in their isolated workspace. The lead session — human or reviewer agent — owns integration.
Principle 05
Library First
The core crate is the product. CLI is a thin adapter. UAR embeds the library directly. No process boundary required.
Principle 06
Recursive Orchestration
UAR can be both the host (running prom-lanes as a NativeSkill) and a backend (prom-lanes orchestrating UAR agent instances). Depth guard prevents infinite recursion.
02 · Workspace Providers

The Isolation Axis

A WorkspaceProvider manages the isolated environment where an agent operates. It doesn't understand what the agent does — it manages creation, state capture, result integration, and cleanup. The semantics of "merge" vary by provider, but the trait interface is uniform.

WorkspaceProvider Trait

crates/core/src/workspace/trait.rs
pub trait WorkspaceProvider: Send + Sync {
    /// Unique key for registry lookup
    fn key(&self) -> &'static str;

    /// Create an isolated workspace, return a handle
    fn create(&self, config: WorkspaceConfig) -> Result<WorkspaceHandle>;

    /// Check workspace state: clean, dirty, artifacts produced
    fn status(&self, handle: &WorkspaceHandle) -> Result<WorkspaceStatus>;

    /// Capture current state for potential rollback
    fn snapshot(&self, handle: &WorkspaceHandle) -> Result<SnapshotId>;

    /// Integrate workspace results into the shared target
    fn merge_into(&self, handle: &WorkspaceHandle, target: &MergeTarget) -> Result<MergeResult>;

    /// Destroy workspace and reclaim resources
    fn destroy(&self, handle: WorkspaceHandle) -> Result<()>;

    /// The address agents use to access this workspace
    fn address(&self, handle: &WorkspaceHandle) -> WorkspaceAddress;
}

/// How agents locate and access their workspace
pub enum WorkspaceAddress {
    FilePath(PathBuf),                       // git worktrees, directories
    DatabaseUri(String),                     // surreal://db/lane_042
    ConnectionString(String),               // postgres://...?schema=lane_042
}

Provider Implementations

GitWorkspaceProvider

The original isolation model. Each lane gets a git branch + worktree checkout. Merge means git merge --no-ff. Snapshot means commit. Destroy means git worktree remove.

OperationImplementation
creategit worktree add -b lane/<task> .worktrees/<task> <base>
statusgit -C <worktree> status --porcelain + diff --stat
snapshotgit -C <worktree> commit -am "snapshot"
merge_intogit checkout <base> && git merge --no-ff lane/<task>
destroygit worktree remove <path> && git branch -d lane/<task>
addressFilePath(.worktrees/<task>)

Best for: Any task where the agent modifies source files — coding, documentation, config generation.

SurrealWorkspaceProvider

Each lane gets a dedicated SurrealDB namespace. The agent reads and writes records within its namespace. Merge copies results into the shared namespace with configurable conflict resolution.

OperationImplementation
createDEFINE NAMESPACE lane_<id>; seed from template tables
statusSELECT count() FROM lane_<id>.* — track record counts, timestamps
snapshotEXPORT lane_<id> → versioned snapshot file
merge_intoINSERT INTO shared SELECT * FROM lane_<id>.results (with upsert/conflict policy)
destroyREMOVE NAMESPACE lane_<id>
addressDatabaseUri(surreal://<host>/<db>/lane_<id>)

Best for: Data transformation, research aggregation, knowledge graph construction, any task where the agent's output is structured records.

PostgresWorkspaceProvider

Each lane gets a dedicated Postgres schema. The agent operates within its schema boundary. Merge integrates results into the shared schema with SQL-based conflict resolution.

OperationImplementation
createCREATE SCHEMA lane_<id>; clone template tables via CREATE TABLE ... (LIKE ...)
statusQuery pg_stat_user_tables for schema, count modified rows
snapshotpg_dump --schema=lane_<id> → versioned SQL file
merge_intoINSERT INTO shared.results SELECT * FROM lane_<id>.results ON CONFLICT ...
destroyDROP SCHEMA lane_<id> CASCADE
addressConnectionString(postgres://...?options=-c search_path=lane_<id>)

Best for: Analytics pipelines, ETL tasks, report generation — any task where the agent produces relational data.

DirectoryWorkspaceProvider

Simplest provider: each lane gets a plain directory, optionally seeded from a template. No version control. Merge means copying output files to a shared directory. Snapshot means tar/zip.

OperationImplementation
createmkdir -p .workspaces/lane_<id>; cp -r template/* if configured
statusfind .workspaces/lane_<id> -newer <marker> — list modified files
snapshottar czf snapshots/lane_<id>_<ts>.tar.gz .workspaces/lane_<id>
merge_intocp -r .workspaces/lane_<id>/output/* shared_output/
destroyrm -rf .workspaces/lane_<id>
addressFilePath(.workspaces/lane_<id>)

Best for: File generation tasks, document production, image processing, any task where the agent produces files without needing version control.

03 · Agent Backends

The Execution Axis

The AgentBackend trait is expanded to cover three distinct execution models: CLI processes (coding tools), platform APIs (OpenAI), and in-process runtime invocation (UAR). A new BackendKind enum lets the engine decide how to monitor each backend — process watching, API polling, or channel listening.

Expanded AgentBackend Trait

crates/core/src/backends/trait.rs
pub enum BackendKind {
    Cli,       // local process: watch PID, capture stdout/stderr
    Platform,  // remote API: poll endpoint for completion
    Runtime,   // in-process: direct channel communication
}

pub trait AgentBackend: Send + Sync {
    /// Unique key for registry lookup
    fn key(&self) -> &'static str;

    /// How the engine monitors this backend
    fn kind(&self) -> BackendKind;

    /// Start the agent with a workspace address and task prompt
    fn start(&self, req: StartRequest) -> Result<RunningSession>;

    /// Poll for current status (essential for Platform and Runtime)
    fn poll(&self, session: &RunningSession) -> Result<SessionStatus>;

    /// Stop/terminate a running session
    fn stop(&self, session: &RunningSession) -> Result<()>;

    /// Whether this backend supports session resumption
    fn supports_resume(&self) -> bool { false }

    /// Whether this backend emits streaming events
    fn supports_streaming(&self) -> bool { false }
}

pub struct StartRequest {
    pub workspace:  WorkspaceAddress,  // from WorkspaceProvider
    pub prompt:     String,            // task contract content
    pub model:      Option<String>,
    pub env:        Vec<(String, String)>,
    pub log_path:   PathBuf,
}

pub enum SessionStatus {
    Running,
    Completed { output: Option<String> },
    Failed    { error: String },
}

Platform Backend: OpenAI Agents SDK

OpenAI's Agents SDK (Responses API with native tool use, code interpreter, and file search) is the right choice for the single external platform backend. It carries the largest ecosystem weight, has a production-grade API surface, and provides a well-defined agent lifecycle: create agent → create thread → run → poll → complete.

Why OpenAI Over Alternatives
LangGraph, CrewAI, and AutoGen are frameworks — they run in your process and own the orchestration model. That conflicts with prom-lanes, which IS the orchestrator. OpenAI Agents SDK is a service: you send a task, poll for completion, collect results. Clean backend boundary. The agent runs on OpenAI's infrastructure; prom-lanes manages the lane lifecycle around it.

Runtime Backend: UAR

The UarBackend creates a recursive orchestration loop: prom-lanes orchestrates UAR agent instances, and UAR can itself run prom-lanes as a NativeSkill. A depth guard (configurable, default max depth: 3) prevents infinite recursion. Communication is in-process via channels — no HTTP, no CLI spawning.

06 · Architectural Decisions

Decision Record

DecisionChoiceRationale
External platform OpenAI Agents SDK Service model (not framework). Clean backend boundary. Largest ecosystem. Production API with tool use, code interpreter, file search. Doesn't compete with prom-lanes as orchestrator.
Recursion guard depth counter (max: 3) UAR as both host and backend creates recursive potential. Counter threaded through StartRequest. Rejected if depth ≥ max.
Workspace abstraction WorkspaceProvider trait Same pattern as AgentBackend: registry of implementations. Engine never assumes filesystem. Workspace × Backend compose freely.
Backend monitoring BackendKind → poll() Cli: PID-alive check. Platform: HTTP poll. Runtime: channel recv. Unified poll() method, engine dispatches by kind.
Workspace merge semantics provider-specific Git: merge --no-ff. SurrealDB: INSERT INTO shared. Postgres: schema-to-schema upsert. Directory: file copy. Interface is uniform; implementation varies.
Feature gating cargo features surreal, postgres, openai, uar as optional features. Core + git + directory + CLI backends always available. Minimizes dependency tree.
Default workspace git (code), directory (general) CLI auto-selects based on .git presence. If repo, default git. Otherwise, directory. Overridable via --workspace flag.

08 · UAR Integration

Bidirectional Embedding

The UAR relationship is now bidirectional. UAR embeds prom-lanes-core as a NativeSkill (prom-lanes orchestrates external agents on UAR's behalf). And prom-lanes includes a UarBackend that orchestrates UAR agent instances as lane workers. This creates a fractal orchestration model where the runtime and the orchestrator reinforce each other.

Lanes spanning multiple machines. Remote workspaces via SSH or cloud-native providers. Central engine coordinating distributed agent processes.
v2.0

Provider-aware conflict detection and resolution. Git three-way merge. SurrealDB CRDT-based merge. Postgres constraint-aware upsert. Human-in-the-loop for ambiguous conflicts.
Summary

What This Produces

prom-lanes v2 is a concurrent agent orchestration engine built on two orthogonal axes: WorkspaceProviders manage isolation (git, SurrealDB, Postgres, directories) while AgentBackends manage execution (CLI tools, OpenAI Agents SDK, UAR runtime). Any workspace × any backend. One engine manages the lane lifecycle.

The UAR integration is now bidirectional — prom-lanes embeds in UAR as a NativeSkill, and UAR embeds in prom-lanes as a backend. This creates a fractal orchestration model where coding agents, data agents, and research agents all share the same concurrency infrastructure.
