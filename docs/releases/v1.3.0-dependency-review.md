# UAR 1.3.0 Rust dependency review

Metadata retrieved 2026-10-24 from the official crates.io API. Phase: `uar-post-lifecycle-verification-readiness`. The inventory below is source inspection and dependency research. Product acceptance remains CLOSED; the operator separately authorized the image build and publication diagnostics.

## Scope and limits

Complete inventory of **119 unique direct registry crates**, covering root production/dev/build/target/workspace declarations, all four `tools/*/Cargo.toml` tool packages, the Rust SDK, desktop Tauri host, fuzz harness, and Rust SDK cookbook. Transitive packages in the lockfiles are reported for these crate names, including duplicates. Vendored upstream projects, imported skill fixtures, frontend dependency submodules, and standalone spikes are independent sources and are not silently upgraded by this inventory. This is not a transitive vulnerability certification.

The table records the declarations inspected before concurrent implementation updates. The lead is migrating reqwest to 0.13.5 and refreshing resolution; these are baseline observations, not a claim that the table is the final lockfile. Registry-compatible means allowed by the version range only, not feature-, platform-, MSRV-, resolver-, or production-build acceptance. No Cargo command, build, test, check, lint, or packaging gate ran for this review.

## Release decisions

- Explicit migration: reqwest 0.12 application/tool/SDK paths and exact MCP 0.13.4 alias converge on 0.13.5. Official 0.13.5 metadata declares Rust 1.85 and the `rustls`, `rustls-no-provider`, `query`, `form`, `json`, `stream`, `multipart`, `gzip`, and `http2` features. Legacy `rustls-tls` and `rustls-tls-native-roots` are absent; preserve each caller’s TLS and encoding behavior deliberately. [reqwest metadata](https://crates.io/api/v1/crates/reqwest/0.13.5)
- Exact-pin same-line candidates: cap-std 4.0.3; http-body-util 0.1.5; insta 1.49.0; jiff 0.2.38; jsonwebtoken 11.1.0; kreuzberg 4.10.4; libc 0.2.191; prost-types 0.14.4; protoc-bin-vendored 3.3.0; rmcp 3.7.0. Pins named in versions.toml need that authority aligned by the lead. Each candidate is linked in the inventory.
- Preserve SurrealDB 3.3.0: 3.3.4 exists but the reviewed SDK lifecycle patches, engine/KV crates, schema types, server binary and container digest form one coordinated contract. Registry availability does not replace those patches. Liter, surreal-memory, sycophancy and parking-lot source exports likewise retain their recorded source identities.
- Wasmtime and wasmtime-wasi can move together from 47.0.3 to 47.0.4 under existing declarations; major 50 is excluded. Keep Candle together and retain fastembed 5/ort rc.13/Intel macOS tract contracts. Keep OTEL 0.32 with tracing bridge 0.33, SQLx 0.8.6 with pgvector, utoipa 5 with Swagger UI 9.
- Source publication observation: the inspected SDK embedded runtime declaration was `version = "=1.0.0"` with `path = "../.."`, while runtime package version is 1.3.0. That exact requirement must be aligned if publishing the SDK embedded feature against 1.3.0. This differs from a compatible bare `"1.0.0"` caret requirement.
- The uncomfortable limit: a current registry release can satisfy a version range and still break a concrete type identity, native linker requirement, generated code, TLS behavior, mobile target, or patched persistence lifecycle. Only the separately authorized real production integration/build path can establish those claims.

## Applied compatibility decisions

All owned reqwest declarations now select `=0.13.5`; MCP uses the same concrete client type as the application, without the old alias. Tools retain their existing encoding/streaming settings. The supervisor uses `tls_backend_rustls().tls_certs_only([ca])` to preserve its private-CA-only mutual TLS boundary with the new API. The SDK preserves bundled WebPKI roots, avoiding a new Android JVM verifier initialization requirement.

The exact-pin candidates above were applied, including RMCP 3.7.0 and Kreuzberg 4.10.4. Wasmtime/WASI resolve together to 47.0.4. `versions.toml` was aligned for reqwest, cap-std, and insta. Root lock refresh used Cargo's incompatible-Rust-version fallback; Cargo reported 418 selected updates compatible with the dependency graph's Rust 1.95 requirement. This is resolver evidence, not a claim that the entire graph builds on Rust 1.95.

The first production build exposed Kreuzberg Tesseract 4.10.4's unbounded `zip >=7.0.0` build dependency selecting ZIP 9.1.0. Its build script calls `mangled_name().to_str()`, but ZIP 9 returns a Result. The refreshed root lock therefore retains ZIP 8.6.0 for this dependency, whose inspected API returns PathBuf. `cargo update -p zip@9.1.0 --precise 8.6.0` succeeded. This compatibility hold is intentional; blindly selecting ZIP 9 would prevent publication. Deployment uses `--locked`.

Independent source reviews found the supervisor API migration, SDK Android verifier initialization, and separate SDK workspace's missing SurrealDB lifecycle patches. Corrective source work addresses those findings. The SDK embedded runtime requirement now matches runtime 1.3.0, while the independently released SDK package remains 1.0.0.

No breaking-major upgrades to Wasmtime, SQLx/pgvector, fastembed/ORT, or coordinated patched persistence sources are included. Remaining transitive reqwest 0.12 packages belong to upstream dependencies and do not represent an owned client alias left behind. Desktop/fuzz/cookbook declarations were audited; their independent lockfiles and imported/vendor upstream source were not silently rewritten. Product integration acceptance, desktop/mobile builds, and phase closure remain pending.

The next production compile exposed pgvector 0.4.2 resolving its `>=0.8,<0.10` SQLx requirement to 0.9.0 while UAR uses 0.8.6. Its vector Encode/Decode/Type implementations then belong to a different SQLx trait family. Keep pgvector on the same SQLx 0.8.6 lock entry as UAR; this is another required compatibility constraint, not a reason to change production database behavior.
