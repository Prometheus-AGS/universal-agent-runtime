# UAR 1.4.0-rc.3 pilot and operator guide

**Updated 2026-11-09.** This prerelease targets the Linux amd64 container API
behind a trusted host or gateway. Start with a fresh embedded SurrealKV volume,
a controlled provider, and data that can be discarded or restored. The image
includes the full server, the web application and a restricted PostgreSQL
backend. Each interface, provider and storage lane has its own acceptance scope.
Keep production promotion tied to the [final qualification checklist](v1.4.0-final.md)
and the [support and recovery matrix](../product-support-matrix.md).

Use this guide to try the new chat and routing contracts, check team recovery,
evaluate extraction and memory behavior, or prepare an offline upgrade rehearsal.
Use the existing stable deployment for workloads that require an already
qualified production artifact, direct public multi-user access, a platform other
than Linux amd64, or a storage path outside the selected contract. The preceding
[rc.2 notes](v1.4.0-rc.2.md) retain their original scope.

## Pilot quick start

1. Prepare an isolated Linux amd64 host and a loopback listener behind the
   approved gateway. Keep the old service, its exact image digest, and an
   independent backup available. Allocate a new volume for this pilot.
2. Configure the gateway's issuer, audience, verification and ownership settings
   in a private operator-managed environment file. Configure the expected model
   and any test provider, egress, Cedar policy and tool approvals. Follow the
   [configuration reference](../configuration.md), [deployment guide](../DEPLOYMENT.md)
   and [JWT validation policy](../security/jwt-validation.md). Keep credentials
   outside Git, the image, shell history and test evidence.
3. Pull the version tag, resolve and retain its registry digest, and compare it
   with the published image identity before mounting storage. Runtime, SDK,
   package and schema versions are independent.

```sh
image=ghcr.io/prometheus-ags/universal-agent-runtime:v1.4.0-rc.3
docker pull --platform linux/amd64 "$image"
docker image inspect --format '{{json .RepoDigests}}' "$image"
docker run --rm --platform linux/amd64 "$image" universal-agent-runtime --version
```

Use the verified `ghcr.io/prometheus-ags/universal-agent-runtime@sha256:…`
reference as `UAR_IMAGE` in the launch command. Set `UAR_PILOT_ENV_FILE` to the
path of the prepared private environment file. Use unique container and volume
names if these example names are already in use.

```sh
docker volume create uar-rc3-pilot-data
docker run -d --name uar-rc3-pilot --platform linux/amd64 \
  --env-file "$UAR_PILOT_ENV_FILE" \
  -e UAR_SERVER__HOST=0.0.0.0 \
  -p 127.0.0.1:1906:1906 \
  --mount type=volume,source=uar-rc3-pilot-data,target=/var/lib/uar \
  "$UAR_IMAGE"
curl --fail http://127.0.0.1:1906/healthz
curl --fail http://127.0.0.1:1906/readyz
```

The wider bind in this example is inside the container. Docker publishes the
HTTP port only on host loopback. Keep other host and container networks
restricted and expose only the trusted gateway. The image runs as UID/GID
`65532:65532` and defaults to
`surrealkv:///var/lib/uar/data/uar.db`. Keep that data directory writable by
the runtime identity. Apply the gateway's network and owner policies before
allowing application traffic.

Liveness and readiness are separate. Once ready, use an approved gateway client
to inspect `GET /api/uar/capabilities` and
`GET /api/uar/persistence/capabilities`. Then send one bounded, harmless text
request through the intended model route. Confirm its terminal result and
original run identity. Where applicable, use a second synthetic owner to check
isolation and prove that an unapproved effect is refused. Keep provider use
within the pilot's authorization and budget. Run the functional suites against
an externally provisioned identity endpoint, using nonsecret selectors only.

## Compatibility and upgrade

| Area | Pilot contract |
| --- | --- |
| Embedded persistence | SurrealDB 4.0.0 in the UAR binary, backed by an owned SurrealKV volume. A fresh volume is the lowest-risk first launch. |
| Existing embedded data | Rehearse offline conversion only from the documented, pinned embedded 3.3.0 baseline. Keep the immutable original and convert to a separate destination. |
| PostgreSQL 18 | Restricted secondary persistence lane. Team execution, follow-ups, schedules, observers and protected checkpoint resume stay unavailable. Discover capabilities on the actual instance. |
| Memory | An independent service with its own store and policy, including with a PostgreSQL primary. Enabling memory does not move memory records into PostgreSQL. |
| Remote SurrealDB | A separate deployment and upgrade contract. The standalone server pin remains separate from the embedded engine. |
| Integrations | The image tag identifies the runtime release. Keep each SDK and protocol version on its own supported pin and exercise the exact integration before changing a production consumer. |

For an existing embedded store, freeze writes at the gateway, stop every
writer, and retain a verified immutable snapshot of each enabled store.
Inventory the source image, lockfile, configuration, store format and data
classes. Demonstrate that the pinned 3.3.0 artifact can reopen a separate
restore. Use the
[embedded 4.0 upgrade runbook](../operations/embedded-surrealdb-4-upgrade.md)
to build the pinned migration runner, rehearse refusal on a disposable copy,
convert a new destination, and compare owner-scoped records and queries.
Keep the original inaccessible to 4.0 startup. Unknown formats, real RocksDB
data and interrupted conversions fall outside the selected migration pair.

After an offline conversion, verify run and event order, checkpoint and
receipt linkage, knowledge and ingestion state, applicable memory and owner
isolation. Start, stop and reopen the destination on the same exact 4.0
artifact. The child phase's five-scenario receipt covers its original artifact
pair and fixture data classes. Rehearse separately for your own data,
configuration and recovery point.

Use the [PostgreSQL deployment guide](../operations/postgres-flint-forge.md)
for the restricted lane and the
[persistence capability reference](../operations/persistence-capabilities.md)
for actual refusal behavior. Store-specific operations can return
`capability_unsupported`. Protected checkpoint resume uses
`checkpoint_resume_unsupported`. Use the
[remote SurrealDB runbook](../operations/remote-surreal-upgrade.md) for an
independently qualified networked deployment.

## Runtime changes and how to verify them

### Images, model selection and destination budgets

The ordinary chat API can carry ordered current-user text and inline PNG/JPEG
parts to a supported generic-compatible adapter. Image-only messages use the
same admission path. The supported slice accepts up to eight images within the
10 MiB whole HTTP envelope. Remote URLs, uploads, audio/video and arbitrary
historical image replay are outside this slice. Keep a controlled provider
capture if you need to prove the exact bytes and ordering. A successful
deterministic response establishes transport and dispatch behavior. Model
understanding requires a separate vision evaluation.

Routing filters candidates by the actual request, current policy, capability
and availability before sending. An explicit or credential-bound target
retains its exact scope. An inherited, verified chat target can use a
verified fallback that the current policy permits. Each attempted destination
gets its own final request fitting, output allowance and accounting reservation.
An unfittable or unverified request fails before dispatch when the contract
requires proof. A provider query and a model catalog entry are advisory.

**Try it:** Start with a small harmless PNG/JPEG and text in one current-user
message. Record the selected model and controlled provider observation for a
successful send. Repeat with malformed input, a non-image-capable target and
an explicit target that cannot use the configured fallback. Then exercise an
authorized inherited fallback and compare its actual final request and budget
evidence with the primary. A refused path should have no provider arrival.
Use the [chat API](../API_CHAT_COMPLETION.md), the
[image contract](../../openspec/changes/carry-inline-images-and-constrain-dispatch/specs/inline-image-chat/spec.md)
and the
[dispatch contract](../../openspec/changes/carry-inline-images-and-constrain-dispatch/specs/constrained-model-dispatch/spec.md)
for precise shapes and controls.

For a small image smoke test, supply a synthetic PNG in `UAR_PILOT_PNG`, an
admitted model selector in `UAR_MODEL`, and the nonsecret workspace and
already-provisioned gateway URL in `UAR_WORKSPACE_ID` and `UAR_BASE_URL`.
Use a controlled provider and omit the convenience `message` field when using
the ordered `messages` array.

```sh
png=$(base64 < "$UAR_PILOT_PNG" | tr -d '\r\n')
jq -n --arg model "$UAR_MODEL" --arg url "data:image/png;base64,$png" '
  {model:$model,stream:false,messages:[{role:"user",content:[
    {type:"text",text:"Describe this synthetic image."},
    {type:"image_url",image_url:{url:$url}}
  ]}]}' |
  curl --fail-with-body --silent --show-error \
    -H 'Content-Type: application/json' \
    -H "x-uar-workspace-id: $UAR_WORKSPACE_ID" \
    --data-binary @- "${UAR_BASE_URL%/}/v1/chat/completions"
```

### Chat history, native continuation and A2UI

Native intent can reserve the original run before dispatch on a capable durable
store. Retain the client turn ID, user-message ID, session and workspace for
read-only reconciliation if the response is lost. An identical replay resolves
to the original receipt. Changing its meaning conflicts. Durable history and
the local journal preserve canonical message IDs, ordered text and rich
segments, and the evidence behind completion, interruption or cancellation.
Unreadable, expired or incomplete evidence remains visible as a limitation.
A browser cache or an old stream cursor grants no authority to rerun a tool.

For declarative A2UI controls, retain the logical interaction ID and original
publication context. A new wire ID with the same logical intent resolves to
the original continuation. A changed payload conflicts, and stale or
unavailable surface authority refuses a new action. Historical controls can
remain read-only when their publication authority is unavailable. This protects
an original action from being repeated after an ambiguous response.

**Try it:** Use an owned session and a controlled tool with observable,
harmless effects. Lose a response after admission and recover from the original
receipt. Compare the run ID, message IDs, order and effect count before and
after reload. Exercise the same logical A2UI action using a fresh wire ID, then
change its payload or generation and check that the original effect count
holds. See the [chat recovery contract](../operations/chat-turn-recovery.md),
[A2UI recovery contract](../operations/a2ui-interaction-recovery.md),
[AG-UI profile](../protocols/ag-ui-profile.md) and
[A2UI profile](../protocols/a2ui-profile.md). Exact mounted browser action and
immediate-reload qualification remain separate from source regressions and
historical client evidence.

For the native intent path, submit `client_turn_id` and `user_message_id`
together with the resolved session. Use
`GET /api/uar/chat-turns/{client_turn_id}?session_id=…` to recover that original
receipt. Omit a caller-owned `tools` field, even an empty array, for this
native-intent path. For a protected A2UI action, keep `interactionId` and
`surfaceGeneration` from the original published control. Read
`GET /api/uar/runs/{run_id}/a2ui/actions/{interaction_id}` after a lost response
and consult the [action recovery contract](../operations/a2ui-interaction-recovery.md)
before any new click.

### Tool effects, teams and cancellation

MCP work is bound to the original governed call, principal and tool schema.
Cancelling a claimed standalone call can end the caller's wait while its
effect remains unknown. Preserve the original invocation ID and use the
owner-scoped tool-outcome read. A timeout or a new connection does not prove
cancellation at the external system. Reconcile with authoritative evidence
before deciding what to do next.

For teams, captured actor policy reflects the registered attempt controls.
The host still enforces role, approval, workspace, generation and current
policy. Defined no-effect refusals can be recoverable, while a denied,
ambiguous or already claimed effect keeps its real outcome. Owned embedded
SurrealKV serializes durable admission and usage mutations on the shared
provider object. The guard covers store operations and releases before
provider execution. The original compare-and-swap, reservation and
known-abort conditions continue to apply.

**Try it:** Run the existing C36 follow-up and C54 same-volume restart
scenarios with the approved case fixtures. Confirm original IDs, exact
provider arrivals and retained accounting. Cancel an owned controlled note
with an uncertain effect, restart the same container and volume, and confirm
that the settled tally is unchanged and the cancelled note retains its
liability without redispatch. Any new replacement work must be explicit.
For production follow-up, use
[team reconciliation](../operations/team-control-reconciliation.md),
[durable accounting](../operations/durable-accounting.md) and
[truthful tool outcomes](../operations/truthful-tool-outcomes.md). A trusted
host may attest exact provider usage with evidence. That operation does not
automatically release a team's separate capacity or settle an external effect.

### Embeddings, ingestion and automatic memory

- **Embeddings.** One admitted `/v1/embeddings` request pins its configured
  backend and space for the whole batch. Counters are independent.
  Check `uar_usage` before treating numeric zero as measured usage. An
  unavailable counter or a malformed batch cannot become a complete
  measurement. Try a controlled backend that reports both counters, only
  one, or neither. Compare vector order and dimension. For an embedding
  model swap, verify generation and retrieval through the new space, including
  swaps where dimensions happen to match.
  [Embedding usage and fixtures](../operations/embedding-usage-accounting.md)
- **Ingestion.** Deterministic extraction rejection becomes terminal and
  inspectable. Transient failures retain bounded retry. The Linux image
  stages the pinned English OCR data for the non-root runtime. Enable
  `kreuzberg.ocr_enabled` when a pilot requires scanned text. Use a disposable
  knowledge base to upload a legible synthetic document with a unique fact,
  wait for the retained ingestion state, and query the indexed result.
  Compare a deliberately invalid or empty source. A terminally rejected
  document should expose the cause and allow an explicit retry after correction.
  [Ingestion job states and recovery](../operations/durable-ingestion.md)
- **Automatic memory.** Opt into automatic context with
  `memory.inject_context` and configure an explicit finite
  `memory.injection_min_similarity` in `[-1, 1]`. The independent memory
  service filters bounded owner-scoped candidates, rechecks current
  content/version/deletion/expiry, and applies the cosine cutoff with the
  configured embedding engine. Omission refuses automatic injection with
  `memory_relevance_not_configured`. Per-turn opt-out and existing tool
  policy still apply. With a fresh owner-scoped fact and empty history, check
  the actual controlled provider input and provenance, then repeat with
  opt-out, below-cutoff and foreign-owner controls. Prepared selection is
  distinct from dispatch and real-model recall.
  [Memory relevance and provenance](../operations/memory-injection-provenance.md)

### Streaming, telemetry and native Wasm

- **Streaming and Messages.** Check the normal completion, cancellation and
  retained-read paths with an owned model fixture that returns explicit
  nonzero usage. Chat terminal streaming carries available provider-reported
  usage through the stop projection. Messages agent mode retains its
  protocol-specific cancellation, terminal and usage contracts. Missing or
  partial reports remain distinct from measured usage and from accounting
  settlement. See [Messages agent mode](../ANTHROPIC_MESSAGES.md) and
  [provider stream completion](../operations/provider-stream-completion.md).
- **Telemetry.** UAR coexists with a host's tracing subscriber and metrics
  recorder. Owned telemetry emits bounded route labels and scoped terminal
  observations. A host-owned recorder and unavailable scrape have explicit
  dispositions. Exporter configuration alone establishes neither delivery
  nor a hard flush guarantee. Use a controlled done and cancelled run,
  inspect application logs and collector observations together, and check
  that private payloads and unbounded label values remain absent.
  [Telemetry ownership and export](../operations/telemetry-ownership.md)
- **Native Wasm.** The image stages pinned Wasmtime tooling and a plain
  component. Arbitrary native precompiled artifacts cross a different trust
  boundary and must be refused unless their verified policy explicitly
  permits them. Use the existing direct component and refusal cases to
  confirm the pinned component path and refusal of malformed/untrusted
  artifacts. Governed Wasm execution and AOT remain outside the selected
  Linux API promotion scope. Browser A2UI renders declarative artifacts.
  [Native component trust policy](../operations/wasm-component-trust.md)

### Build and integration changes

The Rust safeguard now compiles the exact clean committed source across the
three selected feature profiles without temporary source patches. Release
capability checks follow the supervised A2A gRPC scope and distinguish
build-only, internal and exposed features. Container builds require the
committed recursive inputs and fail when needed vendored inputs are missing.
The image pins build/runtime components, leaves private registry and package
material outside the shipped artifact, and records the exact binary, image and
source identity through the existing release evidence workflow. The Liter
routing submodule and embedded SurrealDB remain bound through the pins in
[`versions.toml`](../../versions.toml).

Run from the exact clean committed checkout with the pinned toolchain and
recursive submodules. The acceptance script exercises the compile baseline.

```sh
bash scripts/verify-rust-test-baseline.sh --acceptance
pnpm support-matrix:validate
pnpm release-local-contracts:validate
```

See the [exact-tree Rust safeguard](../development/rust-test-baseline.md),
[frontend test bootstrap](../operations/frontend-verification-bootstrap.md),
[current API contracts](../operations/current-api-contracts.md), and
[release evidence procedure](../release-verification.md). Independently pinned
MCP and A2A counterparts qualify only the role, transport and version exercised.
Protected checkpoint recovery requires the recorded owner, policy, resources
and execution-exclusion evidence. Full-harness process-bound recovery remains
separate from durable native sessions.

Use the [approval recovery runbook](../operations/approval-recovery.md) and
[fresh-process resume](../operations/fresh-process-resume.md) when a protected
continuation actually has a checkpoint and approval. Start with a controlled
owned approval, compare the original checkpoint and resource IDs, then exercise
the same-owner resume and a wrong-owner or incompatible-state refusal.
For replacement after an abrupt shutdown, the
[supervisor recovery runbook](../operations/supervisor-recovery.md) explains
how to establish predecessor exclusion. A process restart alone cannot
establish exclusion or settle an uncertain effect.

## Troubleshooting and rollback

| Symptom | First action |
| --- | --- |
| Container is alive but readiness fails | Check effective provider, storage, gateway and startup settings. Verify the volume identity and permissions, then recheck readiness before application traffic. |
| No eligible model or budget refusal | Inspect the request's required capabilities, verification scope and destination budget. Adjust the request or choose a supported route. Keep existing scope and approval restrictions. |
| A client lost a terminal or tool result | Read the original owner-scoped receipt using its existing identity. Treat unavailable or ambiguous evidence as unresolved and keep its liability. |
| Legacy embedded storage refuses startup | Verify its eligible 3.3.0 format, immutable snapshot and destination lineage. Follow the offline migration runbook with a fresh destination. |
| Post-cutover rollback is needed | Freeze writes, stop the candidate, retain the exact write inventory and obtain a disposition for each post-baseline write. Restore the immutable snapshot into a previously absent 3.3.0 destination and validate the pinned old artifact before restoring traffic. |
| An embedding or memory count is missing | Check the corresponding availability or provenance fields and the actual configured backend. Distinguish missing evidence from a measured zero and an absent cutoff from a successful selection. |

For an expendable fresh-volume pilot, stop the candidate and return gateway
traffic to the retained stable deployment. Keep the pilot volume and receipts
until the operator has made an explicit data retention decision. For a
converted volume, use the [offline rollback procedure](../operations/embedded-surrealdb-4-upgrade.md#restore-the-33-recovery-point).
