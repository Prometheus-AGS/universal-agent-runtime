Executive Summary

Executive Summary

OpenAI’s Codex plugin architecture creates an installable package model for agent capabilities. A plugin can combine procedural skills, MCP servers, authenticated apps or connectors, lifecycle hooks, browser-side capabilities, assets, and reusable scheduled-task templates. The Universal Agent Runtime (UAR) can use this architecture bidirectionally: UAR can be packaged as a Codex plugin, and UAR can invoke Codex as a coding-agent execution backend through Codex MCP Server or Codex App Server.

The recommended strategy is to support the Codex plugin format as an interoperability and distribution format rather than making it UAR’s only extension system. UAR should ingest Codex-compatible plugins, enrich them with Prometheus-specific metadata for policy, memory, artifacts, protocols, deployment, and commercial entitlement, and execute them through a modular plugin runtime.

The initial milestone should ship an official UAR Codex plugin and a UAR-to-Codex MCP adapter. Later phases should add a native plugin host, a full App Server adapter, and a Prometheus plugin marketplace.

01

1. Vision and Strategic Objectives

The program will position UAR as a cross-platform plugin host and orchestration runtime that can both extend Codex and use Codex as an execution agent.

Objectives

  • Make UAR capabilities installable in Codex.
  • Allow UAR workflows to delegate coding work to Codex.
  • Preserve model independence and multi-provider execution.
  • Add durable memory, RAG, policy, approvals, artifacts, and audit around Codex sessions.
  • Reduce UAR core feature sprawl by moving optional capabilities into independently versioned plugins.
  • Support public, private, enterprise, and decentralized package distribution.
  • Create a commercial extension and marketplace model for Prometheus.
02

2. How the Codex Plugin Architecture Works

A Codex plugin is a capability bundle loaded by a Codex host. It is not itself a model or autonomous agent. The package contains a required .codex-plugin/plugin.json manifest and may reference several component types.

Skills provide reusable procedural instructions, activation guidance, references, scripts, and expected outputs. MCP servers provide executable tools through local processes or remote services. Apps and connectors provide authenticated access to external systems and may include custom interface components. Hooks execute commands at lifecycle points after explicit trust. Marketplaces define how plugins are discovered, ordered, installed, and governed.

This design separates instructions, executable capability, authentication, lifecycle automation, and distribution. UAR should preserve that separation internally.

03

3. Why This Fits UAR

UAR already supplies the primary runtime primitives needed for this integration: MCP client and server support, normalized streaming events, tool orchestration, approval workflows, liter-llm provider abstraction, agent and workflow descriptors, SurrealDB-backed persistence and memory, Cedar policy, REST and SSE surfaces, A2A and AG-UI alignment, OpenAI-compatible APIs, evaluation, document processing, observability, and sandbox execution.

Plugins should not create a parallel runtime. Plugin components should resolve into the existing UAR skill, MCP, policy, run, event, memory, artifact, and observability systems.

04

4. Integration Modes

Mode A — UAR as a Codex plugin

An official Prometheus package exposes UAR tools and skills to Codex. Codex can compile and validate agents, run workflows, query memory, ingest knowledge, route models, execute evaluations, and render PAS artifacts through UAR.

Mode B — UAR invokes Codex through MCP

UAR connects to codex mcp-server and treats Codex as an external CodingAgent implementation. UAR owns planning, policy, memory, approvals, and orchestration, while Codex performs repository analysis and implementation.

Mode C — UAR embeds Codex through App Server

A richer adapter maps UAR sessions to Codex threads, turns, items, approvals, sandbox profiles, goals, compaction, resumption, and forking. This is the preferred long-term integration for stateful coding sessions.

Mode D — UAR as a Codex-compatible plugin host

UAR installs and executes Codex-compatible packages independently. Skills are loaded into UAR, MCP servers are registered through UAR, hooks run under UAR policy and sandboxing, and outputs are exposed through UAR protocols.

5. Target Architecture

Layer 1 — Package sources

Git, local directories, HTTPS archives, OCI artifacts, IPFS CIDs, AT Protocol repositories, and enterprise catalogs.

Layer 2 — Plugin package manager

Resolves source, version, dependency constraints, integrity, signatures, installation root, writable data directory, and updates.

Layer 3 — Manifest and compatibility layer

Parses plugin.json, SKILL.md, .mcp.json, .app.json, hooks.json, and optional .uar-plugin/plugin.yaml.

Layer 4 — Capability registries

Registers skills, MCP servers, apps, hooks, schedules, browser requirements, UAR agents, and workflows.

Layer 5 — UAR orchestration kernel

Performs intent routing, context assembly, model routing, policy, approvals, memory access, execution, and normalized event emission.

Layer 6 — Execution adapters and surfaces

Runs native agents, external MCP agents, Codex MCP sessions, Codex App Server threads, and exposes results through REST, SSE, MCP, A2A, AG-UI, OpenAI-compatible APIs, and PAS artifacts.

7. Functional Requirements

FR-001 Discover plugins from project, user, organization, system, and official catalogs with deterministic precedence.

FR-002 Install packages into immutable versioned roots with separate writable data directories.

FR-003 Verify hashes and optional signatures before activation.

FR-004 Parse Codex and UAR manifests without allowing paths outside the package root.

FR-005 Index skill metadata and lazily load full instructions and resources.

FR-006 Register local and remote MCP servers after trust and policy evaluation.

FR-007 Manage MCP startup, health, reconnect, timeout, shutdown, and failure isolation.

FR-008 Register hooks by lifecycle event with timeout, permissions, and failure mode.

FR-009 Require independent trust for instructions, MCP servers, hooks, browser access, filesystem, network, secrets, memory, and publishing.

FR-010 Expose approved UAR capabilities through the official Codex plugin.

FR-011 Start, continue, cancel, and recover Codex MCP sessions from UAR workflows.

FR-012 Create, resume, fork, interrupt, and observe Codex App Server threads and turns.

FR-013 Translate Codex events into UAR normalized events.

FR-014 Route approval requests through UAR’s approval service.

FR-015 Persist approved summaries, artifacts, decisions, and references into selected Surreal Memory namespaces.

FR-016 Convert supported outputs into PAS, Markdown, JSON, files, and A2A artifacts.

FR-017 Select models using capability, policy, health, context, cost, and availability.

FR-018 Import scheduled-task templates without activating schedules automatically.

FR-019 List, search, install, update, pin, disable, remove, and roll back plugins.

FR-020 Audit package version, trust decision, policy outcome, invocation, approval, and result.

FR-021 Run compatibility and conformance suites before publication.

FR-022 Isolate plugin process or hook failures from the UAR host.

FR-023 Scope configuration, secrets, permissions, and data by tenant and user.

8. Nonfunctional Requirements

Security — least privilege, explicit trust, secret redaction, signed packages, and sandboxing.

Reliability — bounded retries, circuit breakers, process isolation, and resumable sessions.

Performance — lightweight startup metadata and lazy loading of expensive components.

Portability — core support for Linux, macOS, and Windows with a restricted mobile profile.

Observability — structured logs, metrics, traces, audit events, and correlation identifiers.

Reproducibility — persist package revision, hash, dependencies, configuration version, and runtime version.

Compatibility — versioned schemas and adapter-based protocol evolution.

Scalability — support many plugin versions, tenants, and concurrent sessions.

Compliance — data residency, retention, export, deletion, and administrator policy controls.

09

9. Security and Trust Model

Trust must be component-specific rather than represented by one Boolean. A plugin may have trusted instructions while its hooks remain disabled. Each operation must produce ALLOW, REQUIRE_APPROVAL, or DENY. Cedar hard denial must never be converted automatically into a human approval prompt.

Hooks should run with a read-only plugin root, writable plugin data directory, no inherited credentials, no network by default, explicit environment allowlists, bounded CPU and memory, execution timeouts, output limits, and secret-redacted logs.

Production distribution should support SHA-256 integrity, Ed25519 or Sigstore signatures, SBOMs, provenance attestations, vulnerability and secret scanning, immutable releases, revocation, and advisories.

13. Codex Event Mapping

Codex agent-message delta maps to message.delta. Command execution start maps to tool_call.started. Command completion maps to tool_result. File changes map to file.changed or artifact.changed. Approval requests map to approval.requested. Thread status changes map to run.status. Turn completion maps to done. Errors map to error.

Persist the mapping among UAR run id, plugin session id, Codex conversation or thread id, current turn id, last received event id, workspace, model, sandbox profile, and approval state. Recovery must resume from the last durable boundary and deduplicate replayed events.

14

14. Memory, Knowledge, and Artifacts

Plugins must receive namespace-scoped and purpose-scoped memory access, never blanket access to user or organization memory. Recommended namespaces include plugin-private, project-shared, organization-shared, user-preference, session-working, and workspace coding-history namespaces.

Persist durable decisions, summaries, codebase facts, task state, artifact references, and approved preferences. Do not persist raw reasoning traces, secrets, unnecessary command output, or excess personal data.

Plugin results should be convertible into PAS artifacts, A2A artifacts, Markdown, structured JSON, downloadable files, and UI events.

15

15. Marketplace and Distribution

Recommended catalog precedence is repository-local, organization, user, Prometheus official, and public community sources. Administrators must be able to disable lower-precedence sources.

Phase 1 supports local paths and Git. Phase 2 adds HTTPS archives and OCI. Phase 3 adds IPFS and AT Protocol. Phase 4 adds mirrored registries and air-gapped bundles.

Commercial plugins may include entitlement metadata. Entitlements should govern activation while declared permissions and package metadata remain inspectable.

17. Testing and Acceptance

Unit tests cover schema parsing, path safety, version resolution, permission evaluation, event mapping, and serialization. Integration tests cover installation, skill loading, MCP lifecycle, hook sandboxing, Codex sessions, approvals, reconnect, and memory persistence. Security tests cover traversal, malicious archives, command injection, secret leakage, network escape, signature failures, and revoked packages. Operational tests cover high concurrency, crashes, reconnect storms, marketplace outages, rollback, and recovery.

Minimum release acceptance

  • The official plugin installs and exposes at least five UAR tools.
  • Codex invokes a UAR workflow and receives streamed events.
  • UAR starts and continues a Codex coding session.
  • UAR discovers and activates a plugin SKILL.md.
  • An untrusted hook cannot execute.
  • A trusted hook remains within declared limits.
  • Cedar hard-deny cannot be overridden.
  • Hash mismatch blocks activation.
  • Plugin failure does not terminate UAR.
  • Audit records connect installation, trust, invocation, approval, and outcome.

22. Risks and Mitigations

Protocol churn — isolate Codex behavior behind versioned adapters and fixtures.

Feature overreach — deliver the plugin and MCP adapter before the full host.

Security exposure — enforce component trust, sandboxing, and least privilege.

Semantic portability — publish compatibility levels and conformance tests.

Dependency sprawl — use optional crates and process boundaries.

Marketplace risk — use signing, scanning, reputation, revocation, and allowlists.

State divergence — persist mappings and use idempotent event processing.

Provider lock-in — retain provider-neutral CodingAgent and ExternalAgent traits.

Mobile limitations — publish restricted mobile profiles.

Licensing complexity — complete legal review before public marketplace publication.

23. Benefits

Product benefits include immediate Codex distribution, cross-host reuse, modular runtime capabilities, and a coherent commercial extension model. Engineering benefits include independent versioning, clearer separation of concerns, improved failure isolation, and reusable external-agent adapters. Customer benefits include faster capability installation, provider choice, durable memory, enterprise governance, and the ability to use Codex without making it the only runtime.

Strategically, Prometheus can become the interoperability layer among proprietary agent hosts, open protocols, local runtimes, and decentralized distribution. Codex becomes both a channel and execution engine, while UAR remains the durable orchestration, policy, memory, artifact, and protocol layer.

26. Final Recommendation

Proceed with this integration as a strategic UAR capability, with strict architectural boundaries. Codex plugin compatibility should be a supported adapter and package format. Codex should be one external coding-agent engine behind provider-neutral interfaces. UAR should remain responsible for orchestration, memory, policy, approvals, artifacts, protocols, and multi-provider execution.

The first technical and commercial milestone should be the official UAR Codex plugin plus the UAR-to-Codex MCP adapter. Those components prove bidirectional value quickly. The native plugin host, App Server adapter, and marketplace should follow after the initial interfaces and trust model are proven.
