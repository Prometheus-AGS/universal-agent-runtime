## Small, nonduplicate behavior candidates

Names are conceptual catalog names, not test IDs. Preserve these as bounded behavior objectives; combine setup and follow-up into a single journey where specified.

1. **Attached skill changes answer** — attach one enabled skill with a distinctive required output; assert answer follows it. Existing narrow evidence has skill attachment/activation paths, while complete skill-family acceptance remains unclaimed per phase matrix lines 42–43.
2. **Catalog suggestion stays inactive until activation** — with catalog mode and a matching prompt, assert suggestion is visible but body/tools are absent; explicitly activate and assert effect. Contrasts the existing legacy overlay mode in one purposeful case pair only if the 35-pass budget permits. Source has the mode and selection mechanism; ensure scenario observes body/tool availability, not merely catalog text.
3. **Scope denial leaves no skill effect** — request a disabled/out-of-scope skill and assert typed failure with no prompt/tool change. This exercises the host authority boundary; it is distinct from positive attachment.
4. **Context strategy preserves a known fact across a long turn** — use one context strategy-specific bounded conversation, then ask for a seeded fact; assert recall or designed refusal. Do not repeat identical journey across every strategy unless registry declares them distinct supported choices.
5. **Memory survives a user-visible round trip** — save a unique fact, query via chat later, assert fact influences answer; attempt a different owner’s access and assert it is not exposed. Combines product utility with the real owner boundary.
6. **Tool result reaches final answer** — one controlled tool request with known result; assert assistant incorporates the result. This is already an explicit BDD requirement in `openspec/specs/chat-scenario-coverage/spec.md` lines 21–29, so count an existing pass if it exercises current source; do not add duplicate tool-loop cases.
7. **Provider route honors capabilities and health** — select a tool-capable route under constraints; for exclusion behavior, make the preferred route unavailable and assert it is not selected. Existing acceptance code mentions fallback/health behavior (`scripts/acceptance/cases_capabilities.py:246–282,466–471`); inspect receipts before adding coverage.
8. **Restart retains effective agent/session configuration** — configure one custom agent/session choice, restart once, continue same interaction and assert identity/route continuity. This provides startup plus persistence evidence without separate boot-only cases.
