The assessment and analysis are written, and a fresh critic is reviewing them now. When it reports, I'll record its findings and the stage handoff, then stop before Plan for your decision.

**The current recommendation is option F: activity surfaces with entity-bound data.**

- **A2UI is sent as AG-UI activities, the way upstream sends it.** Each one carries the surface's full list of operations, and each client applies it with the renderer it already ships. The server never applies data-model updates itself, which removes the problem behind the four failed revisions.
- **The server keeps a durable record of each surface's structure, scoped to the thread or session.** That record is enough to check every action against what the user was actually shown.
- **Application data lives in domain entities.** This is San Saba's entity-graph pattern. A surface changes shape by being reassembled for one user, and nothing they've entered is lost, because the data isn't stored in the surface.

**San Saba already records that it can't use UAR**, regardless of which architecture we pick:
- UAR's user claims don't include a `tenant_id`.
- Its authentication isn't compatible with the workspace's RS256 identity.
- Its A2A task store isn't separated by tenant.

These need fixing before UAR can serve a San Saba-style application.
